## Contract

F1: The attachment request accepts `proofPath` to an existing public `docs/*.json`. It reads bounded receipt bytes (256 KiB) and recognizes top-level `bundleSha256` or `bundleHash`, requiring a 64-character lowercase SHA-256; if both exist they must agree. It also requires a brief `route` and a positive tested `viewport` (string `1920x1080` or numeric width/height). Optional brief `setup` and `fixture` strings retain entry scope. A receipt's proposal ID, when present, must match the saved proposal. Arbitrary metrics, state/release claims and raw fields are not projected.

F2: A sidecar records the immutable report/proposal IDs, requested/resolved public proof path, full proof-byte SHA, recognized bundle field, tested bundle SHA and admitted entry descriptions. Attachment retries reuse the content-addressed sidecar. The existing report and proposal bytes are not rewritten. File resolution reuses the existing traversal, private/sealed, realpath and target-replacement checks.

F3: Listing checks proof identity but does not hash the checkout bundle. The compare button makes a no-store GET that reads the fixed `dist/bundle.js`. Changed proof takes precedence over a build comparison; unavailable proof and unavailable bundle carry separate reasons. Older unattached reports remain readable. The result says which bundle was tested, not that every route was tested or that mismatched builds lack the feature.

Endpoints: `POST /reading-handoffs/:proposal/implementation-reports/:report/playtests` with `{proofPath}`; `GET /reading-handoffs/:proposal/implementation-reports/:report/playtests/:attachment/build-check`. POST retains existing same-origin, JSON and bounded-body checks. No caller-supplied digest is trusted.
