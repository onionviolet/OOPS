# Resident work, needs, relations and stock: internal reader

Scope: source-backed Elin trace for the NPC-work lane, with a check against existing YAIR work and stock owners. This is an internal evidence note, not a direct adaptation request.

## Observed in the pinned source

- **Work is scheduled and destination-bound.** `Chara.GetGoal()` dispatches work/free spans to work/hobby goals, with guest/prisoner/livestock exceptions (`Chara.cs:9400-9450`). `GoalWork.Run -> FindWork -> TryWork` checks the resident's work list against their room, other non-private rooms in the same lot, then the wider map; an entry is eligible only when its `AIWork.SetDestination()` succeeds (`GoalWork.cs:12-19,55-134`). `AIWork` resolves required tagged/trait targets and refuses missing trait types/targets (`AIWork.cs:29-48,56-102`). Research is a concrete work specialization that creates a timed five-unit progress action (`AIWork_Research.cs:1-15`).
- **Needs run alongside the scheduler; no simple stamina gate is visible in this work-selection path.** Hunger and stamina are character stats (`Chara.cs:1203-1207`); tick logic periodically raises hunger and calculates happiness from hunger, stamina, depression, bladder and hygiene (`Chara.cs:3965-3985`). Goal eligibility shown above is timetable/member-status/target based, not gated by hunger or stamina. Do not infer that needs never influence all specialized work actions; the reviewed core caller does not establish that broader claim.
- **Output reaches shared branch stock through a separate daily production path.** The owning branch calls `DailyOutcome` at 05:00 (twice in lucky months) (`FactionBranch.cs:452-468`). For each alive-on-map, non-party member it resolves hobby and work rows; `GetOutcome` derives output from work efficiency/product bonus, awards the work skill experience, scales each declared `things` pair, creates item/category output, and sends non-garbage output through `m.TryPutShared`; failed/garbage meals go through `TryTrash` (`FactionBranch.cs:819-835,887-905,914-977`). `Chara.TryPutShared` inserts into the zone shared container and drops at the actor position when that fails (`Chara.cs:4742-4748`). Livestock output is also deposited in shared storage, while one pasture unit is consumed; an absent pasture skips production (`FactionBranch.cs:836-885`). These are shared zone/branch resources, not necessarily individually owned inventory. `WorkSummary.money/food/knowledge/material` instead accumulates scheduled work ticks (`Chara.cs:9774-9840`); the searched decompile contains no consumer of those totals or of `WorkSummary.things` beyond their declaration/addition. `RerollHobby` resets the aggregate summary (`Chara.cs:9716-9763`; `WorkSummary.cs:78-85`), but this is not daily payout settlement. Commodity creation has no duplicate suppression in the inspected path; production is repeatable, with one explicit duplicate guard for an owner-linked panty and a capacity guard (`FactionBranch.cs:821-830`). Exact job/item rows remain unavailable.
- **Relations are explicit thresholds with a real caller.** `Affinity.Get` maps the character's stored integer to an affinity stage; stages gate invitation, marriage/sleeping beside, card giving and other affordances (`Affinity.cs:38-95`). `DramaCustomSequence` checks `CanInvite()` before adding the invite/bout dialogue choice, alongside instance/boss/survival guards (`DramaCustomSequence.cs:79-90`). Positive modification has chance affected by current affinity difficulty; negative amounts subtract directly (`Affinity.cs:212-230`). This proves a downstream invitation affordance, not every economic/work effect.
- **Failure is observable and bounded.** If the work target cannot be resolved, `FindWork` returns false; `GoalWork.Run` then falls through to idle (`GoalWork.cs:12-19,55-134`). AI work can also reach its `Restart()` path after the action completes (`AIWork.cs:29-49`). No exception recovery guarantee or runtime behavior is asserted from generated source alone.

## YAIR comparison

YAIR already has explicit residents, separated native/simulation inventory owners, claims, vitals, time, finite consented jobs, controller actions, bounded output and refund-on-lost-support paths. For example, the society prototype defines distinct actors and actual per-actor purses/stock/body/vitals, checks alive/location/body/health/trained-source support, reserves materials, wages, stamina and attention for Orr's home repair, and returns reservations if completion support is lost (`src/feature_expansion_society.js:1-58,69-77,104-120`). Its controller chooses among finite authored actions (`:211-220`); `src/simulation.js:415-435` advances living actor controllers at due intervals, evaluates requirements and starts eligible work. `src/simulation_effects.js:165-189,287-289` owns acquisitions, owner transfers, relation memories, and refund construction.

Existing fit is therefore concrete finite resident agency and property accounting, not a blank NPC foundation. The clearest bounded comparison gap is **recurring work tied to a resident's timetable, relevant need state, and accessible worksite/material**, where the outcome is stock or a retained work account that changes a later player choice. Elin's evidence suggests a useful shape: authored job preference -> schedule window -> reachable/owned target -> efficiency/output account, while needs remain independently legible. YAIR's current society controllers are interval-driven finite proposals, and existing nested-life work is player-started bounded contracts; neither should be mistaken for a generalized autonomous livelihood simulation.

## Original candidate, if selected by the lead

One original Village resident workday: meet a resident at their actual worksite during a displayed work window; inspect a small public work account; optionally supply one missing material or give them room to work; later collect or buy one retained useful output. The resident has finite owned stock, work rights, stamina/health support, and a deterministic timetable. Missing worksite/material or lost consent closes the attempt without output and returns unspent reservations. This can extend the existing finite society owners; it does not require a population simulator or alter the current prestige/save policy. Any persistence mutation needs a compatibility decision and save/reload acceptance by the owning GM.
