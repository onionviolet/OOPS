# The Modding Tree and Prestige Tree: source audit (2026-10-13)

**Answer first.** The Modding Tree (TMT) makes layered prestige fast to write with one rule: a layer's row number is its place in the reset order. Any prestige wipes every layer on its own row and below, unless that layer's `doReset` hook passes a **keep list**. That list depends on *who* triggered the reset and *which milestones* the player has earned (F1, F2, F3).

YAIRPG already has the opposite, safer default: a transition keeps everything except a static, named `reset` list of domains. What YAIR lacks is TMT's conditional part, "keep X when reset by Y, once you earn Z". That is the cheapest big win (P1).

Prestige Tree adds two layer structures that fit YAIR's direction:

- **Order cost instead of exclusive choice (F5).** Opening one branch first makes its sibling about 5000x costlier, but never locks it.
- **Mastery (F6).** Re-run a lower layer in an isolated run. Success permanently changes that layer's formulas.

TMT's save, offline and versioning code is simpler and weaker than YAIR's. Two small patterns are worth taking: schema-default merge for new fields, and a visible offline time bank.

Findings and packets are proposals, not accepted decisions.

## YAIR comparison

- **Transitions.** `previewCampaignTransition`/`commitCampaignTransition` (`src/simulation.js` L553-L603) use a declarative `reset` list over 15 domains, validated in `src/simulation_contracts.js` L190-L194, with five kinds: travel, return, ascend, rebirth, replay. Preview is sequence-checked; commit is atomic with a receipt (last 32 kept). `retain` is display text only. The default is **keep**, the opposite of TMT and the same as Profectus. Reset lists are static: nothing can say "keep X if milestone Y" (gap vs F2).
- **Registered prestige.** `frontier.field_renewal` (`src/frontier_campaign.js` L62-L66) has `reset:[]`, a pure-gain prestige like `resetsNothing`. `foundation_start.renewal` (`src/foundation_start_content.js` L74-L82) describes its resets as prose.
- **Heir carryover** (`src/heir_inheritance.js`) derives carry from what the ended life left. TMT has no equivalent; it is closer to reset dial R3.
- **Saves** (`src/save_files.js`) are stricter than TMT's: numeric version parts, newer saves rejected, per-module validators, retired-content retention. TMT's only edge is cheap default-filling, which YAIR does per module.
- **Content.** YAIR forbids code in content ([ENGINE_AUTHORING.md](../../ENGINE_AUTHORING.md)). Keep that; take TMT's "value or derived expression anywhere" uniformity without per-tick code (F8).
- **Offline.** YAIR's advancement is bounded to 512 boundaries per call and reports `remaining`/`budgetExhausted`, more honest than TMT's accelerated ticks, but nothing shows the player a pool (F12).
- **Reset dials** ([death and reset considerations](../DEATH_AND_RESET_CONSIDERATIONS_2026-10-10.md)): TMT covers R3 carry set, R1 trigger and part of R4 cost, with nothing for R2 anchor, R5 witnesses or R6 exit. It is a mechanism library for dial R3, not a model of a reset.
