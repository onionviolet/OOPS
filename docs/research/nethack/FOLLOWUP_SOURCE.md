Read-only, bounded follow-up at the same official source pin as the first report: NetHack `NetHack-5.0`, commit [`8898570da710513f38d81ed973f834863b795217`](https://github.com/NetHack/NetHack/tree/8898570da710513f38d81ed973f834863b795217). This review covers selected additional functions only.

Current local baseline is the 2026-10-06 `PROJECT.md` reference gameplay delivery: bundle `2f04d677a4db`, marked implemented-unverified. Existing NetHack-inspired fieldcraft is present in `src/nethack_fieldcraft_*.js`: one fixed type discovery, full/empty vial, exact dull-to-sharp knife transformation, one finite local feeding/training/hand-retrieval route and one trained retrieval route. That feature is a Notebook/workshop interaction, not general native item identification, food use, or a traveling/battle pet. Root reports the fieldcraft preview was built; this audit did not run a build or play gate. Exact inspected local source fingerprints are recorded in [FOLLOWUP_SOURCE.json](FOLLOWUP_SOURCE.json); the shared tree is dirty and other workers own integration.

## Ranked original applications

### 1. Keep catalogue discovery, item identity, and instance state distinct

**Source facts.** NetHack records an instance's observed appearance (`obj->dknown`) and type-level discovery (`oc_encountered`, `oc_name_known`) separately in [`observe_object` / `discover_object`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/o_init.c#L440-L490). Naming also checks instance flags such as `known`, `dknown`, and `bknown`, while its type data stores the actual and appearance names; see [`xname_flags`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/objnam.c#L581-L639), and its unique amulet path explicitly says individual objects must be identified separately ([same function](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/objnam.c#L671-L684)).

**YAIRPG status.** The inherited `item_log` is a catalogue/seen ledger: logging an item creates an entry and stores counts/quality extrema; `is_known` means a log entry exists ([`src/items.js`](../../../src/items.js#L64-L111)). Some crafting views hide unlogged materials ([`src/display.js`](../../../src/display.js#L3390-L3405)). Fieldcraft separately records the character's learned reed-oil meaning in simulation knowledge ([`src/nethack_fieldcraft_facts.js`](../../../src/nethack_fieldcraft_facts.js#L47-L54)), but its actual native vial names stay “Unmarked pale vial” and “Empty bench vial” ([`src/nethack_fieldcraft_content.js`](../../../src/nethack_fieldcraft_content.js#L14-L17)); ordinary inventory labels/tooltips still render template `getName()` ([`src/display.js`](../../../src/display.js#L411-L420), [`src/display.js`](../../../src/display.js#L1852-L1859)). So there is already seen/known catalogue behavior and one separate substance-identity memory, while a character-aware native label adapter and general per-instance state are absent from these inspected owners.

**Proposed next slice.** Let the already implemented fieldcraft receipt drive one native inventory detail for full versus empty vials and one native name/description projection for identified reed oil. Preserve stable inventory keys and counts; make the Notebook receipt the only authority for character knowledge, not a global template mutation. A second instance-sensitive test can use the existing sharp/dull result to show condition is object data, but avoid adding a broad unknown/curse/charge schema in the first slice. Keep legacy saves reading current catalogue entries as before; no enrollment means no new inference. This closes the existing visible gap between “the character learned it” and “the carried object screen reflects it.”

### 2. Keep native meals covered; target corpse-derived physiology only as a later adapter

**Source facts.** NetHack's eating is a timed occupation: [`eatfood` / `done_eating`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/eat.c#L524-L578) advances to completion, applies post-effects and consumes the actual food. Corpse handling considers species, age/rot, blessing/curse, poison/acid and resistances ([`eatcorpse`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/eat.c#L1860-L1948)). `cprefx` handles pre-consumption species consequences such as petrification and bad reactions ([`cprefx`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/eat.c#L795-L846)); distinct post-consumption intrinsic eligibility and acquisition are handled by [`intrinsic_possible`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/eat.c#L893-L959), [`should_givit` / `temp_givit` / `givit`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/eat.c#L961-L1105), and [`cpostfx`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/eat.c#L1132-L1165), which can invoke those rules after consuming selected species.

**YAIRPG status.** Native food consumption is covered in source. `UsableItem` receives its actual effects and recovery chances and is tagged usable ([`src/items.js`](../../../src/items.js#L481-L490)); existing stale/fresh bread, apple and carrot entries are usable food with actual Basic meal effects ([`src/items.js`](../../../src/items.js#L4130-L4175)). `use_item()` checks native action availability and item custody/disposition, applies active effects and skill bonuses, returns configured containers, grants the matching consumable skill XP, and removes one item from native inventory ([`src/main.js`](../../../src/main.js#L3771-L3822)). Usable items can be placed in consumable favourites for auto-consume ([`src/main.js`](../../../src/main.js#L3825-L3855)). Behavioral validation of this path is not in this audit. The specific missing extension is source-qualified corpse/creature physiology and intrinsic acquisition, not a general meal handler. Generic simulation condition/knowledge/resource/effect machinery does not itself establish eligibility or provenance for a corpse-derived intrinsic. Fieldcraft rations feed only Rill and explicitly do not grant a player meal benefit ([`src/nethack_fieldcraft_content.js`](../../../src/nethack_fieldcraft_content.js#L80-L90)).

**Proposed next slice.** Do not add a duplicate meal handler. A future targeted physiology experiment could use one explicitly authored creature-derived consumable and a bounded temporary adaptation, only after it has an actual source/provenance carrier, freshness/condition semantics, eligibility rule, and a native capability consumer. Permanent adaptation should stay later until retention, stacking and reversal rules are explicit. Compatibility: leave existing `UsableItem`, active-effect, favourite/autoconsume, and old save behavior intact; enroll only through an explicit new action/receipt and use an original YAIRPG species/material rule. Native food consumption is source-implemented but remains behaviorally unverified in this review.

### 3. Let one environmental interaction affect both a native item and a place

**Source facts.** A ray action resolves along its route through `dobuzz`; the per-tile path calls `zap_over_floor`, then reacquires the monster because melting ice can remove/change the target's environment ([`dobuzz`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/zap.c#L4864-L4900)). `burn_floor_objects` consumes selected floor objects and ignites other items ([function](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/zap.c#L4608-L4669)); `melt_ice` changes terrain, applies trap/object consequences and can trigger drowning ([function](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/zap.c#L5054-L5092)). These functions show a shared event resolving actor, object and location consequences rather than a spell merely writing a status effect.

**YAIRPG status.** Existing combat/math, native effects, materials, realm environmental context and simulation conditions are reusable foundations. In inspected local owners, no general shared effect consumer maps an elemental action to both native inventory/material changes and a persistent local terrain/path change. Existing material traits in `src/items.js`, weather/time presentation, and simulation condition handlers do not prove that interaction is wired to a gameplay action.

**Proposed next slice.** The generic shared interaction is still absent from the inspected native consumers. A genuinely new local test would be a hot fitting surface whose heat condition has an authored material consumer and site consumer; it must introduce a new outcome/constraint, not repeat the existing Wet repair stave → Sound repair stave recipe. First name the actual item IDs and establish the site fact consumer; otherwise keep broad elemental interactions in backlog. Do not import a general fire/cold simulation. Keep any future test opt-in and additive to the fieldcraft receipt; cancellation/failure must preserve the input under the existing transaction pattern.

### 4. Expand Rill only into a second local autonomous task, not a full companion system

**Source facts.** Pet movement is goal-based: [`dog_goal`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/dogmove.c#L485-L590) chooses nearby food first, then suitable carry targets, otherwise a follow goal; [`dog_invent`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/dogmove.c#L402-L460) gates pickup by capacity, cursed status and apport, and [`dog_hunger`](https://github.com/NetHack/NetHack/blob/8898570da710513f38d81ed973f834863b795217/src/dogmove.c#L364-L401) ties care to movement/health. The local simulation can travel its declared party as a group ([`src/simulation.js`](../../../src/simulation.js#L478-L484)), and native battle has a party battle path, but current Rill is deliberately omitted from `s.party` by its validator and content ([`src/nethack_fieldcraft_facts.js`](../../../src/nethack_fieldcraft_facts.js#L70-L77); [`src/nethack_fieldcraft_content.js`](../../../src/nethack_fieldcraft_content.js#L96-L103)).

**YAIRPG status.** Rill already has explicit local consent, body/health, satiety, stamina, lessons, feeding, calm handoff, one abstract scent-dependent retrieval, and a native kit material output. He does not have a movement controller, an independent floor-item inventory/carry contract, a route/follow behavior, travel, or native battle registration. Thus companion care/service is delivered as a finite local interaction; pet navigation and combat are not implemented by that fact.

**Proposed next slice.** If further pet work is selected, add one same-Village fetch along a short authored safe path: place a single real pin at a local pickup site, let willing trained Rill move there and back over played time, validate path/site/care at completion, and hand over that same reserved pin. Keep him out of party travel and combat for this increment. The old local feed/train/retrieve state remains the old behavior; only a new explicit follow-up enrollment/action enables the additive controller receipt. This lets the player observe autonomy without turning an NPC into an abstract instant reward or destabilizing all battles/saves.

## Disposition and limits

My top priority is the native inventory knowledge projection because fieldcraft already records the relevant knowledge and the mismatch is visible now. Native food use, meal buffs, and consumable favourites are already implemented in the inspected source, though not behaviorally checked here. A later source-specific physiology/intrinsic adapter can follow only when the item-to-capability provenance path is defined. Environmental shared effects and autonomous pet movement are larger adapters and can remain backlog candidates. The existence of generic actors, conditions, traits, powers, effects, or party travel is not counted as support for these domain behaviors.

The proposed slices are reversible, original YAIRPG work and do not authorize me to edit runtime/canonical owners. The current shared writer is Features `01a10dc5`; ownership/integration and actual player-visible acceptance remain with that active integrator. No tests, browser, save, or library operations were run in this audit.
