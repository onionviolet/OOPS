## Top findings: quest authoring (the authored-arc side)

**Relation to EP.** [EP_PACK_PROGRESSION](EP_PACK_PROGRESSION.md) audited quest books as shipped pack data (graph shapes, what packs do with quests). This lane reads the authoring engine under them: what a quest node can express. Where a pack habit in EP has a source feature here, it is cross-referenced.

- **QL1** (shown, `Quest`, `Chapter`, `BaseQuestFile`) **Three-level defaults with a tristate.** A quest field is default, true or false; default resolves to the chapter value, which resolves to the file value (`canRepeat`, `requireSequentialTasks`, `hideUntilDepsComplete`, progression mode, quest shape and size, auto-claim). So an author sets a policy once per chapter and overrides one node. Stored as a directory of text files: `data`, `chapter_groups`, `chapters/<name>`, `reward_tables/<name>`, `lang/` (the text lives in translation files, not the node). Ids are 64-bit written as hex codes; a write drops dependency ids that no longer exist (`removeInvalidDependencies`). **Mechanism:** inheritance with an explicit "inherit" state beats copying flags onto every node. Pack books in EP still show dangling prerequisite ids (EP table, e.g. Monifactory 41), so those books were not written by this path.
- **QL2** (shown, `Quest#isVisible`, `#areDependenciesComplete`, `DependencyRequirement`) **Visible, startable and complete are three separate questions.** Dependency rule has four values: all completed, one completed, all started, one started, plus `min_required_dependencies` as an integer. Visibility flags: `invisible` (hidden until the node itself is complete), `invisible_until_tasks` (hidden until N of its tasks are done), `hide_until_deps_visible`, `hide_until_deps_complete`, `hide_details_until_startable`, `hide_text_until_complete`, `hide_lock_icon`. With no flag the node shows when any dependency is visible. **Mechanism:** foreshadowing is a dial (show the lock, show only the shape, show nothing) independent of the gate. BQ has the same idea as a six-value enum (QL10).
- **QL3** (shown, `ProgressionMode`, `Quest#checkForDependantCompletion`, `TeamData#setProgress`) **Linear versus flexible progression.** File default is linear: a quest's tasks cannot progress until its dependencies are complete (`canStartTasks`). Flexible (per file, chapter or quest) lets tasks fill early; when the last dependency completes, tasks already at maximum are marked complete. `require_sequential_tasks` forces tasks inside a quest to be done in order. **Mechanism:** "do it before you were told" can count, or not, per arc. Fits a life-sim where a character may already have done the thing.
- **QL4** (shown, `Quest#isQuestObjectExcluded`, `#isExclusiveQuest`, `TeamData#isExcludedByOtherQuestline`; file flag `hide_excluded_quests`) **Exclusive branches.** A parent with `max_completable_dependents = N` lets only N of its children be completed; once N are done, the siblings are "excluded", a dependency from an excluded quest no longer counts as a valid path, and `min_required_dependencies` or one-versus-all decides if a downstream quest is cut off too. Excluded and repeatable and optional quests do not block progression (`isOptionalForProgression`). **Mechanism:** a choose-one-path arc with the consequence computed from the graph, not hand-wired. The default is "all branches open"; the dial is N.
- **QL5** (shown, `TaskTypes`, task classes) **Task catalogue.** Registered types: item, custom, xp, dimension, stat, kill, location, checkmark, advancement, observation, biome, structure, stage (game stage), fluid, interaction (new in 26.1.2.9, right-click a block or entity). An `EnergyTask` class also exists in common code and `ForgeEnergyTask` in the NeoForge module (shown by `grep -rl EnergyTask` across the clone), so energy is a platform-specific task registered outside `TaskTypes` (registration site not opened, inferred). Fields worth noting: item task `count` and `consume_items` (consuming means the player clicks to submit; non-consuming detects on inventory change, `ItemTask#submitItemsOnInventoryChange`); kill task entity or entity tag, optional custom name and NBT filter; xp task counts points or levels; observation task needs the player to look at a target for a timer capped at 1,200 ticks (`MAX_TIMER`); stage task can be a team stage. Progress is a long per task per team, clamped to the task maximum. **Mechanism:** most tasks are "have this", "do this N times", "be there", "see this"; the checkmark task is a manual gate, and the stage and advancement tasks are bridges to other systems.
- **QL6** (shown, `Reward`, `RewardTypes`, `RewardAutoClaim`) **Reward catalogue and claim flags.** Types: item, choice, all_table, random, loot, command, custom, xp, xp_levels, advancement, toast, gamestage, and currency (off by default, needs an economy mod). Per reward: team reward tristate, auto-claim (default, disabled, enabled, no_toast, invisible; invisible chapters force auto-claim), and "claim all" exclusion (choice, all_table, random and loot are excluded by default because they need a decision or a screen). A file-level switch can suppress all auto-claiming. Claim events (pre-claim, grant-item, loot-crate-open) are cancellable hooks (stated, changelog 26.1.2.9). **Mechanism:** a reward is a small program: give, ask, roll or run a command; the quest never contains special cases for them.
- **QL7** (shown, `RewardTable#generateWeightedRandomRewards`, `WeightedReward`) **Reward tables.** A table is a list of rewards each with a float weight, an `empty_weight` (chance of nothing), and `loot_size` (attempts per claim, multiplying the draw count). Draws are independent with replacement. A weight of exactly 0 means "always granted" (filtered out before the rolls). Chance is shown to players as a percentage (`chanceString`, "<0.01%" below the display floor). Tables can be bound to a loot crate item (colour, name, glow) and crates can drop from mobs by entity weight (`drop_loot_crates`, `loot_crate_no_drop`). Choice reward = the player picks one entry from the table; all_table = everything. **Mechanism:** one table shape serves guaranteed bonus (weight 0), random pull, choice and loot-crate, so authors tune one dial per table. Spot-check note (shown, `RewardTable#writeData/#readData`): the writer omits `hide_tooltip` and `use_title` when false, but the reader defaults both to true when absent, so a table saved with those off reloads from disk with them on (the network path uses a flag bit and is not affected). A reminder to write every field explicitly in an authored-data format.
- **QL8** (shown, `QuestKey#forReward`, `TeamData#markRewardAsClaimed`, `#getClaimType`, `Quest#resetProgressIfRepeatable`, `QuestObject#forceProgress`, `Reward#forceProgress`, `BaseQuestFile` `default_reward_team`) **Progress belongs to the team; each reward is either personal or one team claim.** Task progress and started/completed timestamps are per team. A claim record is keyed by (player, reward) for a personal reward, and by (nil id, reward) for a team reward (`QuestKey#forReward`), so a team reward is claimed once for everyone and a personal reward once per member. The default is personal (`default_reward_team` false in `BaseQuestFile`'s constructor), with a per-type map and a per-reward tristate to override. A quest repeats by file/chapter default or per quest. When any claiming player has claimed all of the quest's rewards (`resetProgressIfRepeatable`), the whole team's quest and task progress is reset (`QuestObject#forceProgress` clears started/completed and recurses into tasks), that player's reward records are cleared, the completion count rises, and `repeat_cooldown` (taken as seconds, counted from that reset) blocks new progress. Inferred from `Reward#forceProgress` resetting only the acting player's key: other members' personal claims stay on record after the reset, so they would not be able to claim that reward again on the repeat until their record is reset by hand. That closes O1 for the reset scope and leaves the per-member edge as unverified in play. **Mechanism:** shared household progress, with the author choosing per reward whether it is a household prize or a personal one; repeat is "claim to reset" (the EP2 shop trick is exactly this: submit, claim card, reset).
- **QL9** (shown, `TeamData#mergeData`, `#mergeClaimedRewards`, `#setLocked`, `#setRewardsBlocked`, `#isRewardBlocked`) **Join, leave, freeze.** Joining a party merges the solo data: task progress takes the maximum, started and completed keep the earlier timestamp, claimed rewards are kept; leaving copies claimed-reward records back to the leaver's own team. A team can be locked (progress frozen) and rewards can be blocked globally unless the quest or reward is flagged `ignore_reward_blocking`. **Mechanism:** progress merging that keeps the larger progress and the earlier timestamps and keeps claim records, which avoids lost credit in the paths read (the merge was read, not exercised). Direct fit for a family or household shared arc with an heir leaving or joining.
- **QL10** (shown, `QuestInstance`, `EnumLogic`, `EnumQuestState`, `EnumQuestVisibility`) **Better Questing: six logic gates and a property bag.** A quest holds `preRequisites` (int ids) and two independent gates, `questLogic` and `taskLogic`, each one of AND, NAND, OR, NOR, XOR, XNOR, evaluated as a function of (completed count, total): AND all, NAND any missing, OR at least one, NOR none, XOR exactly one, XNOR exactly all but one. States: LOCKED, UNLOCKED, UNCLAIMED, COMPLETED (`getState`). Visibility enum: HIDDEN, UNLOCKED, NORMAL, COMPLETED, CHAIN, ALWAYS; NORMAL shows a locked quest only when every prerequisite is itself unlocked ("foreshadowing", code comment), CHAIN shows it if any prerequisite is shown. Properties are namespaced keys with defaults (name, desc, icon, main, global, silent, autoclaim, repeat time, sounds), so an expansion can attach its own keys. **Mechanism:** exactly-one and all-but-one are expressible as gates without extra node types, and the property bag is an extension seam.
- **QL11** (shown, `QuestInstance#update/#detect/#canSubmit`, `QuestCache#updateCache`, `NativeProps`, `LifeDatabase`, `EventHandler`) **Better Questing flags.** `simultaneous`: progress resets when only some tasks are done at once (a code comment records an exploit with `lockedProgress`); `lockedProgress`: tasks accumulate while the quest is still locked; `isGlobal`/`globalShare`: one player's completion counts for everyone (claim state is then any-claimed unless share is on); `repeatTime` in ticks, -1 never (the cache multiplies by 50 ms), `repeat_relative` false aligns the reset to absolute multiples of the interval; `autoClaim`, `silent`, `isMain` (optional vs main path), `party_enable`. Hardcore mode is a lives counter (default 3, max 10, a life lost per death, at 0 the player becomes a spectator, `LifeDatabase`). **Mechanism:** global quests (first one to do it for the realm), time-aligned repeats (a market day), and a lives stake attached to the book rather than the world. **EP link:** `lockedProgress` is the engine feature behind EP's "Quest locks" row (Nomifactory 603, GTNH 121 BQ locks), which control what registers rather than what can be crafted.
- **QL12** (shown, `ParticipantInfo`, `PartyInstance`, `EnumPartyStatus`; stated: this clone has no task or reward implementations) **Party sharing is delegated to the task.** A party has member, admin, owner ranks. When a task detects, it receives a `ParticipantInfo` listing the player, the party, and which party members are online; the task decides whether progress is shared. The concrete task and reward types live in a separate expansion repository (the clone holds registries and placeholders only), so the item/kill/etc. behaviour in BQ was not read here. Completion info is per UUID with a `claimed` flag and a timestamp. **Mechanism:** the book gives the participant set; each task type owns its sharing rule (a kill credits the party, a delivery takes from the actor; these two examples are my guesses at what a task could do, not read). **EP link:** EP17's Prominence II shared kill credit (contributors within 60 seconds) is that sharing rule implemented in a task, which fits this seam.
- **QL13** (shown, `SaveLoadHandler`, `bq_db_format.odt` text) **Two storage philosophies.** FTBQ writes the authored graph as text files (JSON5 via `Json5Util` in this version; the extension constant lives in FTB Library, not in this clone, so the exact extension is inferred) and the per-team progress separately (`TeamData#toJson`). EP parsed the older SNBT-era books; this release reads and writes JSON5, and a grep of the clone for `snbt` found no legacy importer, so a migration route from the older format was not found here (searched Java sources only). The file-level `verify_on_load` flag is present. BQ writes one `QuestDatabase.json` (format 2.0.0; sections `questSettings`, `questDatabase`, `questLines`) whose keys carry the NBT type id as a suffix (`name:8`), and keeps `QuestProgress.json`, `QuestingParties.json`, `LifeDatabase.json`, `NameCache.json` beside it; with no database it loads `DefaultQuests.json`; `pack_version` and `pack_name` properties exist for pack authors; a build mismatch triggers a backup (stated). **Mechanism:** authored content, player progress and party data are separate files, so the authored arc can be diffed, validated and replaced without touching saves. Matches this repo's save-privacy rule.
- **QL14** (shown, `BaseQuestFile` fields) **Rescue layer.** File-level `emergency_items` list with `emergency_items_cooldown` (default constant 300; unit taken as seconds, inferred: the use site was not opened), `detection_delay` (default 20; unit taken as ticks, inferred), `drop_book_on_death`, `lock_message`, per-player progression pause (`TeamData#setProgressionPaused`). **Relation:** the same job as the EP14 "Emergency Items" chapter, here as an engine feature instead of a chapter.

**Quest mapping to EP.**
- EP9 (tier walls as single gate quests) is a pure graph pattern: one node with two or three dependencies and `all_completed`; QL2 lets the same wall be shown as a lock, a silhouette or invisible.
- EP2 (quests as a repeatable shop) is QL8 plus a custom reward: repeatable, claim resets, `repeat_cooldown` as the market limit. Nothing here needs the shop to be a quest; the point is "claim to reset".
- EP1 (order by intermediate items, not by locks) still stands: neither engine gates crafting; both gate what the book shows and pays. Real gating is a stage reward or task (QL5, QL6) calling another system, as in EP18.
- EP15 (graph shape by authoring style): flexible progression (QL3) and exclusive branches (QL4) are the engine features that make wide-shallow and braided graphs tolerable.

## Top findings: logistics, only what differs from TB

Reference: [TB_MEKANISM_AE2_IE_THERMAL](TB_MEKANISM_AE2_IE_THERMAL.md) TB1 (Mekanism upgrade exponent), TB7 and TB8 (transmitters, item routing), TB9 and TB22 (storage accounting), TB21 (AE2 channels), TB23 to TB27 (AE2 storage priority, planning, CPUs, patterns, cards), TB30 (cards), TB33 and TB34 (Thermal augments).

### Ender IO

- **QL15** (shown, `data/enderio/enderio/conduit/*.json`, `ItemConduit`, `EnergyConduit`) **A conduit tier is a data record.** Fields: type, texture, `transfer_rate`, and for items `ticks_per_cycle` (default 20). Item 32 per cycle at 20 ticks (32/s), enhanced 64/s, ender 64 per 10 ticks (128/s). Energy 8,000, 48,000, 192,000 per tick. Fluid 200, 1,000 (pressurized), 8,000 per tick (unit inferred mB). Optional-mod conduits (ME, dense ME, Refined Storage, heat, chemical 750) load only when the other mod is present (`mod_loaded` condition). A bundle block holds at most nine conduits (`ConduitBundleBlockEntity#MAX_CONDUITS`). Along a path the speed is the minimum of its conduits (`SpeedAndTickRatePair.minProperty`, `PATH_MAX_TRANSFER_RATE`), so the weakest segment sets the rate. Mixing tiers is allowed by default and a config boolean per kind forbids it; a higher tier replaces a lower in place (`canReplaceConduit`). **Mechanism:** a tier ladder where new tiers are added as data, line speed set by the slowest piece, nine services in one corridor.
- **QL16** (shown, `ItemConduitConnectionConfig`, `ItemConduitTicker#tickChannel`) **Per-side connection config is the whole UI.** Each side of each conduit carries: insert flag and colour, extract flag and colour, redstone control and redstone colour, round-robin, self-feed, an integer priority, and one filter slot for extract and one for insert. 16 dye colours are lanes (not bandwidth, unlike AE2 channels TB21). The tick: per colour, per extractor, scan source slots in order, apply the extract filter, try the insert paths starting at a stored round-robin index, cap each path by its remaining speed this cycle (a per-tick map of amount already sent over each path), apply the insert filter, stop when the extractor's cycle budget is spent. **Differs from TB8:** Mekanism moves stacks as entities with A* cost; Ender IO is instant, capped per path per cycle, with explicit priority and round-robin. No pathfinding display; the lane colour and a probe item are the visual (a conduit probe item exists, `ConduitProbeItem`).
- **QL17** (shown, `CapacitorData`, `LinearScalable`, `QuadraticScalable`, `SteppedScalable`, `FixedScalable`, `EIOItems`) **Capacitor as a tuning part.** A capacitor item carries a base float and an optional map of per-stat overrides over four stats: energy capacity, energy use, fuel efficiency, burning energy generation (plus FIXED, which capacitors must not multiply). `getModifier` returns the override when present, else the base (an override replaces the base, it does not multiply it). Items: basic 1, double-layer 2, octadic 3. A machine declares each derived stat as a formula over its level L: linear base x L, quadratic base x L squared, or stepped base + step x L. Alloy smelter defaults (config): capacity 64,000 and max use 20 per tick, both quadratic, so L = 1, 2, 3 gives 20, 80, 180 per tick and 64k, 256k, 576k buffer (inferred arithmetic from the formula). Machines marked `REQUIRED` do nothing with no capacitor: no energy interaction and a NO_CAPACITOR state (`PoweredMachineBlockEntity`). The capacitor is a tier gate on the machine, not a recipe.
- **QL18** (shown, `PoweredCraftingMachineTask#makeProgress/#getProgressRequired`, `StirlingGeneratorBlockEntity`, Attractor/Aversion obelisks) **What the dial buys.** Crafting progress per tick equals energy consumed, capped at max use, and the recipe's required progress is its fixed energy cost, so a higher capacitor cuts time by about L squared at the same energy per craft (inferred from the two shown methods). Compare Mekanism's exponent with its cost curve (TB1) and Thermal's chip tax (TB34): here speed is free of tax, and the price is the capacitor, the buffer and the instantaneous draw (a 180-per-tick machine browns out a small grid). Generators use other formulas: stirling fuel efficiency stepped 80% + 20% x L multiplies burn time (`burnTime = floor(burn time x burnSpeed 0.375 x efficiency)`, shown), generation linear 40 per tick x L. Obelisk range scales linearly with the ENERGY_USE stat, so reach is bought with draw. Banks (blocks) store 500,000, 2,000,000 and 4,000,000 FE (`EnergyConfig`).
- **QL19** (shown, `SetLootCapacitorFunction`, `LootCapacitorItem`, `common_loot.json`; stated: TODO comments, `ICapacitorExtension` docs) **Found capacitors are rolled specialists.** Chest loot sets base from uniform 1 to 4 and one primary stat override rolled uniformly in the same range; 15% add a second stat, 2% a third (`SetLootCapacitorFunction#run`). Names by base: dud under 1, normal under 1.5, enhanced under 2.5, wonder under 3.5, impossible above (shown) with a modifier word and stat word. Because an override replaces the base, a found part can beat octadic in one stat and be a dud in the rest. An experimental extension interface (since 8.1.0) lets a capacitor compute its data dynamically (for example from enchantments) and gets a callback after each machine operation, which would allow wear. Author TODOs mention soul-type loot capacitors and "capacitor sacrifice" (stated, not built). **Mechanism:** craftable tiers 1 to 3 are the reliable ladder; finds are variance and specialization.

### Refined Storage (RS1)

- **QL20** (shown, `ItemStorageType`, `FluidStorageType`, `ItemStorageDisk`, `ServerConfig`, `DiskDriveNetworkNode`) **Flat storage, flat power.** Item disks 1k, 4k, 16k, 64k plus creative; fluid disks 64k, 256k, 1,024k, 4,096k plus creative; capacity is one integer total (insert refuses past it); no separate type cap was found, and no per-type overhead. Contrast Mekanism's two-axis drive (TB9) and AE2's bytes-per-type (TB22). A disk drive has 8 disk slots and 9 filter slots; a disk records its owner id. Power: defaults are small flat numbers per node (controller buffer 32,000, base use 0; cable 0; grid 2, crafting grid 4, pattern grid 4; disk drive 0 plus 1 per disk and per disk tier 2, 4, 6, 8; importer and exporter 1; interface 2; crafter 4 + 1 per pattern + upgrade use). There are no channels and no bandwidth limit on cables (`NetworkNodeGraph` is a connectivity walk; inferred from not finding a cap). **Differs from AE2 (TB21, TB32):** the only scarcity is power draw and the number of disks, so placement is free and the UI is the product.
- **QL21** (shown, `CraftingCalculator`, `CalculationResult`, `ServerConfig#Autocrafting`) **Autocrafting as one calculated job.** Request (item or fluid, quantity) is planned recursively against a copy of the network's stock: use results of the plan itself first, then network stock, then a sub-pattern for the missing part. Alternatives for an ingredient (tags) are tried in order sorted by availability (`PossibleInputs`), a pattern already in the current chain aborts as RECURSIVE, int overflow or exceeding the calculation timeout (default and minimum 5,000 ms) gives TOO_COMPLEX, and any shortfall yields MISSING with a preview listing what is missing, what will be taken from stock and what will be crafted. On OK it builds a task of nodes, each either a crafting-grid node (crafted by the network) or a processing node (items pushed into a machine). **Differs from AE2 TB24/TB25:** no CPUs (no memory or thread upgrade axis); any number of tasks run on the one manager; speed lives in the crafters.
- **QL22** (shown, `ProcessingNode#update`, `ProcessingState`, `CrafterNetworkNode`) **Processing nodes and crafter dials.** A processing node pushes one set of inputs into any crafter whose pattern matches and whose adjacent inventory accepts the full set, tracks what it needs and what has been received back, and exposes states READY, LOCKED, MACHINE_NONE, MACHINE_DOES_NOT_ACCEPT (the monitor shows why a job waits). A crafter holds 9 patterns and 4 speed-upgrade slots: update interval 10, 8, 6, 4, 2 ticks and 1, 2, 3, 4, 5 successful updates per interval for 0 to 4 upgrades, i.e. 2, 5, 10, 20, 50 operations per second (inferred arithmetic). Modes: ignore, signal unlocks, signal locks, pulse inserts the next set. Compare AE2 pattern provider (TB26): same attached-to-the-workstation idea, with speed on the crafter instead of the CPU.
- **QL23** (shown, `UpgradeItemHandler`, `UpgradeItem.Type`, `ServerConfig`) **Upgrade cards, smaller than AE2.** Importer and exporter have 4 slots (speed, crafting, stack, regulator): each speed card lowers the interval by 2 ticks from 9; stack card raises items per operation from 1 to 64; crafting card makes the exporter request autocrafting for missing stock; regulator keeps a set amount. Each card adds a flat energy use (speed 2, crafting 5, stack 12, regulator 15, range 8, silk touch 15, fortune 10/12/14). **Mechanism:** a handful of cards, each with a printed power cost, no curve. Compare TB1 and TB30.
- **QL24** (shown, `Permission`, `GridType`, `IGrid`, `ItemStorageTracker`, `GridNetworkNode`) **Grid, security, history.** Grid kinds: normal, crafting, pattern, fluid. Sort: quantity, name, id, ascending or descending. Six permissions per player through a security manager: INSERT, EXTRACT, AUTOCRAFTING, MODIFY, BUILD, SECURITY. A per-stack storage tracker records the last change (who and when, shown through the grid tooltip; the exact tooltip text not read). Wireless, portable and crafting-monitor handhelds are energy items (3,200 capacity; open 30, extract 5, insert 5). **Mechanism:** one searchable view with "who last touched this" and per-person permissions is the cheap social layer for a shared home.
- **QL25** (shown, `CraftingPreviewElementFactory#getElements`, `CraftingCalculator`; stated, RS docs `viewing-resources/grid.adoc`, `autocrafting/crafting-monitor.adoc`, `getting-started-with-autocrafting.adoc`, `locking-and-unlocking.adoc`, `keeping-items-in-stock.adoc`, `partials/search-box.adoc`) **The UI surface that makes it feel like one inventory.** Grid: left click takes up to 64, right click 32, shift sends to the player, ctrl-shift forces the crafting window even when the item is in stock; sort by name, quantity, id or last modified; size stretched/small/medium/large; a display filter for craftable-only or non-craftable-only; sidebar filter slots and filter-defined tabs (a filter with an icon becomes a tab, a filter inside a filter gives more than four tabs); the search box takes `@modid`, `#tooltip text`, `$tag`, and can sync with a recipe viewer; the tooltip shows total count and last-modified. The craft request opens a preview before running: one row per distinct item with three numbers merged by item hash, "to craft" (including missing), "available" (taken from stock) and a missing flag (`getElements`: missing first, then to-craft in reverse discovery order, then available). The monitor lists running tasks with elapsed time and a cancel (or cancel-all), and per-cell states Stored, Missing, Processing, Scheduled, Crafting. Keep-in-stock is done with an interface plus a crafting card (set the wanted amount; the network crafts when below); locking lets a redstone signal pause a crafter. A pattern is "exact" by default (only the listed inputs); turning exact off lets the planner substitute equivalent inputs. **Differs from AE2's UI and feeds Q8:** a short vocabulary of statuses on every stalled job, a merged to-craft/available/missing table, and a tab per filter are all cheap, readable and need no knowledge of the graph behind them.

## Donor questions (default, dial, reason, cost)

Proposals, not decisions. Each is framed with an in-world reason and cost, and none is a blanket rule (AD38; WPR5).

- **Q1 Authored-arc node fields (QL1, QL2, QL3).** Default: an arc node has a gate rule (all or one of its conditions), a foreshadow level, and inherits both from its arc, overridable per node. Dial: foreshadow from full text to silhouette to hidden, and whether work done early counts. Reason: a household may have done the thing before the arc offered it; a rumor can show only a rough shape. Cost: showing too little hides the next goal; counting early work needs a record of when it happened. Fits the work-ledger and arc owners; I did not re-read them this run.
- **Q2 Choose-one-path arcs (QL4, QL10).** Default: an arc parent allows N of its follow-ups, and cut-off branches stop counting toward later gates. Dial: N, and exactly-one or all-but-one gates (QL10). Reason in world: a patron accepts one apprentice; a faction offer excludes its rival. Cost: the closed path stays closed unless a world gives a way back with a price.
