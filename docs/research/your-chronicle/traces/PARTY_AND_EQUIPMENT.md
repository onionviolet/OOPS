## T1. Research buys an ally, then levels, then capped luck that feeds later research

**Prerequisite and decision.** Ally-specific research must fund a summon, and there must be remaining level/luck headroom. `SummonAlly.IsMet` RVA `0x83A730`, N`Domain/Allies/SummonAlly.txt` lines 3–100, calls `Ally.GetCanPurchaseSummonLevel` and the SummonCost list's purchase check. GetCanPurchaseSummonLevel RVA `0x8324D0`, N`Domain/Allies/Ally.txt` 5159–5380, takes the minimum of selected summon amount, cost-supported amount and remaining headroom. GetMaxSummonLevel RVA `0x832670`, same file 5381–5661, returns `maxLevel + MaxLuckLevel - Level - LuckLevel`.

**Cost and mutations.** DealInBulk RVA `0x83A7D0`, N`Domain/Allies/SummonAlly.txt` 101–404, clamps an optional requested quantity, calls ExecuteSummon, then passes the actual returned quantity to SummonCost Calculate (`0xC90FD0`). ExecuteSummon RVA `0x83AA30`, same file 405–1292, marks Obtained, allocates the first min(quantity, maxLevel−Level) to Level, then min(remainder, MaxLuckLevel−LuckLevel) to LuckLevel. Interface dispatch indices 2/3 are get/set Level, 4/5 get/set LuckLevel, 22/23 get/set Obtained, identified by original method tokens in A`Domain/Domain/Allies/IAllyRepository.cs`, not guessed from alphabetical display order. Research_BulkDealing.CanPurchase RVA `0x6D28F0`, N`Research_BulkDealing.txt` 23–81, tests `research + factor * value >= 0`; Calculate RVA `0x6D29F0`, 82–146, applies the signed change to CurrentResearch. D`105.txt` slime data row 1, physical lines 2–4, uses research:slime −1, maxLevel10 and MaxLuckLevel5. Bird row 2 has cap12/luck7 and seed caps/passives that differ from slime. The ally's seed upgrades use separate physical/magical/special stocks, not research alone (rows 1–4; native individual seed spend routines not semantically traced in this lane).

**Consumers.** GetLuck RVA `0x831880`, N`Domain/Allies/Ally.txt` 2892–3030, returns initLuck + luckLevel*LuckFactor. ResearchDrop.GetDrop RVA `0x8FB430`, N`ResearchDrop.txt` 178–726, calls Amount and LuckMulFactor, multiplies the result by incoming amountFactor, adds it to save.research_ally[allyId], and records drop count/total amount. LuckMulFactor RVA `0x6CA5C0`, N`LuckBonusCtrl.txt` 399–588, is `1 + (Luck * 0.01)^0.9`, with constants read from pinned x86 native VM addresses `0x349C808`, `0x349C870`, `0x349C590`. The caller stores and multiplies real xmm results; ISIL's missing floating-point operations are not ignored. Help `main_party` states party luck is totaled; exact complete Luck stats aggregation was not traced here. GetLuckMaxNum, N`LuckBonusCtrl.txt` 589–1083, counts eligible allies at MaxLuckLevel; FixedUpdate 3–126 raises the recorded maxed-ally achievement high-water mark. Help `levelup_party` documents the Ally Completion Dark Ritual multiplier, but this lane did not trace that ritual formula. Root retention lane should qualify that join.

**Allocation/time/failure.** AutoSummonToggleFunction.IsMet RVA `0x908270`, N`AutoSummonToggleFunction.txt` 3–144, permits an already selected checkbox or delegates to CanCheck. CanCheck, N`AutoSummonCtrl.txt` 134–172, allows another only while checked count < maximum slot count. OnChanged 145–249 writes the selected ally's saved auto-summon flag. AutoSummonCtrl MaxTime 111–133 uses native float10; ActionIn1Second 520–619 elapses cooldown and calls AutoSummon with duration10 at expiry. AllyAutoSummomer.AutoSummon, N`AllyAutoSummomer.txt` 64–221, loops allies in container order, calls the same Ally.Summon for selected allies and multiplies the quantity by truncated duration/10. Help says display pin order determines uppermost priority; this code confirms container-order spending but the pin-to-container reorder consumer is not traced. If cost is absent or level and luck are both capped, IsMet fails and DealInBulk returns before mutation/payment. Automation does not bypass these costs.

**Original design implication.** Ordinary combat and training can keep feeding an ally's useful noncombat contribution after basic combat growth caps. The opportunity cost should remain visible: research spent here cannot fund another research-cost action, and using a party slot for a passive or luck contributor competes with active combat needs. This is a transferable mechanic, not a request to transplant monster summoning or the entire luck formula.

## T2. Assigned costly skill persists while unaffordable attacks fall back to the ally's default

**Prerequisite and decision.** D`65.txt` slash row4/line5 is weapon, rank1, stamina−1, interval2.7, base value10 and guard_break_p; tackle row3/line4 costs no resource, interval2.8/value7. Power_slash row6/lines7–8 adds rank2, stamina−2 and two additional effects. D`83.txt` You row1 grants CanEquipAllSkill, default Player/tackle and weapon attribute. Native rank filter N`JudgeaSelectableSkill_Rank.txt` 3–323 and attribute filter N`JudgeaSelectableSkill_Attributes.txt` 3–482 reject no-ally selection and accept the CanEquipAllSkill special case; ordinary allies require rank and attribute compatibility. Native attribute path ends at UsefulMethod.ContainsAll `0xE277F0`. SkillSelect_Click.OnClick RVA `0x89B220`, N`SkillSelect_Click.txt` 3–153, stores the chosen skill per selected ally in save.preferredSkills_allyId and resets the current dungeon. This click path does not itself recheck rank/attributes; those are UI-filter conditions. It must not be described as a hardened validation boundary.

**Consumer/cost/failure.** Ally.GetSkillCombination RVA `0x836DF0`, N`Domain/Allies/Ally.txt` 15233–15673, initializes/caches the combination, reads assigned skill and disablePreferredSkill (A`ID/DomainOption.cs` static field0x34), and supplies default or assigned wrapped skill. PreferredSkill.GetSkill RVA `0x867130`, N`PreferredSkill.txt` 1635–1737, constructs Preferred_Skill from underlying skill + costs. DefaultSkillCombination.SelectSkill RVA `0x911210`, N`DefaultSkillCombination.txt` 3–440, returns default if preferred is null; otherwise it chooses preferred only if ISkill.CanCast succeeds, else default. That is interface slot7; slot9 is PayCost and slot10 is NextSkill, established from ascending tokens in A`Domain/ISkill.cs`. The same method also handles condition-specific overrides, an initial skill, and continuations via lastUsed_Skill.NextSkill, so a generic always-preferred-else-default summary omits supported exceptions.

Preferred_Skill.CanCast RVA `0x91A070`, N`Preferred_Skill.txt` 3–68, checks cost availability for factor1; PayCost RVA `0x91A0E0`, 69–200, calculates that cost list into the effect summary. Base_SkillCombination.GetNextSkill, N`Base_SkillCombination.txt` 28–240, pays selected skill cost through slot9 before returning the skill. Slash's real shared stamina thus competes across consumers. When stamina falls below cost, default is used without deleting the saved assignment. Base_Attack_Skill.CanCast/PayCost dump entries have no generated ISIL/body due to recovery/dedup ambiguity; do not interpret those as no-op behavior. Installed Help `main_party` independently documents affordability fallback and disabling assigned skills. The actual attack/damage/effect consumer was not reviewed fully, so exact slash damage, guard-break behavior and combat outcome remain outside this lane.

**Original design implication.** A character can retain a learned/assigned tactic across short resource shortages while performing a cheaper known action. This protects long idle sessions from a hard stop while preserving scarcity, cooldown and tactical identity. The default should be explicit in the player view, and consequential skill prerequisites should also be rechecked by the live command consumer when adapting this pattern.

## T3. Secondary gear connects ordinary kills to retained upgrades, with capacity and destruction consequences

**Prerequisite/cost/time.** EPoint3_Drop.Enabled only returns Unlocked, N`UniqueEquipments/EPoint3_Drop.txt` 1063–1189. Unlocked checks the saved released uniqueEquipment element (A`ID/DomainElement.cs` field0xBC), not inventory capacity. GetEpoint3 RVA `0x739A70`, same file 811–1062, marks the glowing shard resource displayed/released, adds its reward and calls EPoint3Converter.Apply. Converter Apply RVA `0x7393B0`, N`UniqueEquipments/EPoint3Converter.txt` 3–283, loops while current >=1000, subtracts1000, and calculates CreateBase. Threshold1000 is verified at native VM `0x349C740`. Installed Help `second_equipment` documents low-rate dungeon drops and secondary gear leveling from kills; this lane did not review the precise drop probability or kill-to-exp caller.

**State mutation and full-capacity aftermath.** UniqueEquipmentGetDealing.Calculate RVA `0x726FC0`, N`UniqueEquipmentGetDealing.txt` 250–404, requires the released element, seeds serialized random state, calls AddRandomly, and restores random state. AddRandomly RVA `0x74C7D0`, N`UniqueEquipments/AddUniqueEquipmentUsecase.txt` 3–127, generates a piece and resolves duplicate names before Add. Add RVA `0x74C880`, 174–619, returns early when inventory IsMaxed or the new ID cannot be added. Inventory max RVA `0x742400`, N`UniqueEquipments/UniqueEquipmentInventory.txt` 1731–1900, is `100 + save.purchasedNum_RubyItem[DomainRubyItem.uniqueEquipmentInventory]`; A`ID/DomainRubyItem.cs` field0x44 identifies the item, and A`Save/Save.cs` field0x680 identifies the save array. Help's100 is the base cap, not an unconditional current maximum.

**Static failure finding, not live reproduction:** the inspected drop -> converter -> base generation -> Add chain can subtract1000 shards then reject the generated piece at capacity. Enabled lacks a capacity check, and Converter.Apply subtracts before Add. This path has no refund in the inspected chain. Do not assert that a real session suffered loss, or that every acquisition route does this: UniqueEquipmentGetDealing.CanPurchase and EffectIsCompleted explicitly expose capacity for other callers. A later acceptance probe should reach actual capacity, add a threshold of shards, and inspect stock/inventory; no such probe ran.

**Destruction, protection and reinvestment.** UniqueEquipment.CanDelete RVA `0x73ABE0`, N`UniqueEquipments/UniqueEquipment.txt` 293–429, rejects an ID in current UniqueEquipmentParty and otherwise permits only an unfavorited piece. Inventory.CanDelete checks membership then that rule, N`UniqueEquipments/UniqueEquipmentInventory.txt` 1095–1188. UI OpenDeleteScreen RVA `0x747DF0`, N`UniqueEquipments/UniqueEquipmentInventoryUnit.txt` 1736–1863, caches MakeReward and opens a confirmation callback. MakeReward RVA `0x747ED0`, 2349–2870, makes powder for each passive's matching StatsId+EffectKind; base quantity is 1 + integer(innerLevel/2), optionally doubled by Powder+ availability. A`Domain/UniqueEquipmentPassiveSkill.cs` offset0x28 establishes that quantity uses the passive innerLevel, not the piece's exp level. ItemIsEnabled 2871–3050 checks the option and at least one powderAmountUp item; Delete RVA `0x748800`, 3051–3658, deletes the piece, calculates cached rewards, optionally consumes one item, and clears the cached reward. Inventory.Delete 855–1094 removes dictionary/save data and unregisters the piece's LevelEffect client. Powder_Deailng.Calculate RVA `0x73A2F0`, N`UniqueEquipments/Powder_Deailng.txt` 66–155, credits matching powder stock.

UniqueEquipmentService.CanIncreaseInnerLevel RVA `0x743E70`, N`UniqueEquipments/UniqueEquipmentService.txt` 3–361, checks target membership, passive index and nonnegative cost <= matching powder stock. IncreaseInnerLevel RVA `0x7442C0`, 362–693, spends that powder, increases the chosen passive inner level and saves the target's data. UniqueEquipmentPassiveSkill.Calculate RVA `0x87B2C0`, N`UniqueEquipmentPassiveSkill.txt` 632–777, applies the inner-level method multiplier to the ordinary piece-level calculation. Exact diminishing-return formulas are not recovered by this selected trace; Help documents slowing after100. Deleting an unwanted piece has a real irreversible object consequence but carries a typed fragment into useful retained gear.

**Original design implication.** A bounded inventory turns repeated ordinary fights into a keep/equip/protect/recycle decision. Recycling can preserve useful earned work without preserving every object. An original adaptation should reserve capacity or retain unclaimed rewards before consuming a threshold, and perform stock+object+powder mutations through existing atomic owners.
