# Five original implementation proposals

These five proposals are selected from39 findings across 23 finite source paths. They are not the whole system map, accepted YAIR design, or implemented gameplay. Names, costs, timing and fiction remain reversible proposals. The [report](REPORT.md), [findings](FINDINGS.json), [coverage](COVERAGE.json) and [DLC bounds](DLC_COVERAGE.json) own the wider evidence.

## ONI-P01 · Temperature-qualified material work

Make one original workshop process use its actual batch condition, fuel and output, so ordinary material preparation remains useful. Warm a cold owned batch now, spend less fuel after shelter conditioning, or choose a useful lower-temperature process.

Scope: One optional Frontier workshop process with one actual input batch, two supported approaches and useful output/residue. Add a typed per-batch condition only if existing item metadata cannot represent it. No global thermal grid.

Integration: Root-owned exact item/state validation and batch metadata, stable definition/version, material reserve, process completion and native output publication. Current finite crop and stamped strip retain their meanings.

Chain: Known process, owned unencumbered material, usable hands/site and actual disclosed fuel → Exact batch and fuel from their owners; freeze initial condition/recipe revision → Supported played-time conditioning/process step → Consume the reserved batch once and produce exact useful output plus disclosed residue → Later repair/cooking/insulation job must use that produced material function → Cancel/lose support follows declared frozen return policy; completed heating is not retroactively refunded → Retain input/output/temperature-basis receipt and changed site condition.

Time/compatibility: Existing played clock and supported absence policy; no browser-closed heating/loss. Additive optional typed record with explicit version validation; old absence inert. Do not infer arbitrary fields are accepted by existing item validators.

Later playable gate: UI shows actual costs and batch basis; warmer input changes the authored cost; later consumer spends the produced item; cancellation, storage, transfer and generated save/reload prove custody.

Source: ONI-F01, ONI-F02, ONI-F03, ONI-F28, ONI-F29. Risk: Per-batch metadata is shared integration work; simplified source heating is not physical science or selected balance.

## ONI-P02 · Body-specific expedition support

Let a short original flooded or stale-air task distinguish learned movement, actual air support and current body requirements. Use an actual breathing/lining kit, take a reachable recovery route, or use an already-earned supported alternative body where its own sustain law allows.

Scope: One explicitly enrolled local hazard with warning, voluntary retreat and useful result. No automatic body grant, copied bionic lore, world reset or mandatory fatal/offline upkeep.

Integration: Actual current body/function owner and kit/air reserve, supported action adapter, warning/recovery state and completion support. Traveler profiles alone are detached snapshots, not a new native physiology engine.

Chain: Actual supported body, learned route/movement function, known hazard and sufficient support → Owned physical kit/reserve and real attention, not a capability label → Played-time local exposure with a defined safe-recovery window → Useful work consumes support; deficient support pauses/forces a disclosed retreat → Same body can resume only after actual recovery/refill or alternate practical approach → Unsupported body, expired support or unreachable recovery prevents completion; no invented source immunity → Received observations, support spent and recovery retained separately.

Time/compatibility: One existing clock; unobserved/absent region freezes unless its current owner explicitly supports the hazard. Optional new content/version records; existing normal bodies and care jobs unchanged. Schema/validation and generated save/reload gate before verified claim.

Later playable gate: Movement learning unlocks a concrete path but does not conjure air; different supported bodies pay their declared resources; warning/retreat/resume and exact kit custody are visible.

Source: ONI-F07, ONI-F08, ONI-F09, ONI-F30, ONI-F31, ONI-F32, ONI-F37. Risk: Body support integration is broader than a label; fatality and autonomous hazard policies are not selected.

## ONI-P03 · Borrowed competence with earned practice

Make a powered borrowed workshop tool enable a specific operation while keeping learned mastery, rental rights and fuel distinct. Borrow and power the tool for a difficult joint, do an ordinary slower task, or practice toward retaining the skill without it.

Scope: One existing workshop action and one specific removable tool support. No global skill-slot cap or blanket XP/morale system.

Integration: Separate tool-owned derived execution contribution, actual lease/equipment custody and earned practice ledger; integrate with one native command without duplicating source/perk effects.

Chain: Current tool rights/installed support, site, usable body and real funded power → Borrowed item custody/deposit, owner energy and real work attention → Tool-enabled work or slower ordinary practice on existing clock → Tool contribution enables execution; actual earned practice is recorded only from qualified completed work → A later action without the tool tests retained learned capability → Tool return, support loss or exhausted power removes only tool contribution; cancellation follows actual lease/job policy → Returned custody and conserved deposit; lasting learned practice survives removal.

Time/compatibility: Existing work job and energy owner; no render-triggered rewards, passive duplicate drain or new timer. Do not copy ONI UngrantSkill behavior: equipment removal must not delete separately earned skill history. Additive definition/custody validation and explicit effect stacking.

Later playable gate: Borrowed tool enables the named operation; power is spent once; tool removal disables only its contribution; later learned competence still works after return and generated reload.

Source: ONI-F11, ONI-F12, ONI-F13, ONI-F33, ONI-F39. Risk: Derived capability/equipment integration must avoid double bonuses and aliases; aptitude or consent cannot be inferred from tool ownership.

## ONI-P04 · Paid habitat and useful biological output

Add one optional original husbandry loop whose supported habitat and consumed feed affect a useful harvest/byproduct. Maintain a cultivated habitat for reliable production, use a slower wild-compatible approach, or deliberately end the tended cycle and keep remaining means.

Scope: One newly authored optional bed or small husbandry site, separate from Nell's existing finite crop. Explicit renewal spends actual new inputs. No free reseeding, population ecology or unearned companion.

Integration: Existing stock/site/job owner with a named lifecycle phase, habitat support and owned feed/renewal input. Define whether feed alternatives are OR or jointly required.

Chain: Actual site rights, current habitat, known species/process and owned inputs → Feed/seed-equivalent/care materials and real responsible worker → Supported tending/growth phase; unsuitable habitat stalls according to explicit rule → Create a real counted product and qualified byproduct; current cycle ends once → Cooking, refining or medical-fiction preparation spends the produced stock → Insufficient support stalls without invented death; interruption preserves declared phase/input policy → Spent means, current site and cycle result remain; new cycle requires explicit renewal.

Time/compatibility: Supported played-time lease only; preserve old finite-crop and unsupported body/absence freeze policies. Separate stable content IDs and optional lifecycle record; old story receipts/rewards cannot be replayed.

Later playable gate: Feeding actual owned stock changes output availability; unsupported habitat blocks growth; useful output reaches a later native consumer; renewal cannot farm free stock or rewrite old crop.

Source: ONI-F17, ONI-F18, ONI-F19, ONI-F20, ONI-F21, ONI-F22, ONI-F38. Risk: New lifecycle content needs authoring and exact stock conservation; source wild/tame/fertility policies are examples, not universal YAIR ecology rules.

## ONI-P05 · One operator, two work locations

Prototype original remote operation that uses one actual operator and a supported remote device rather than duplicate independent labor. Operate a remote device while staying sheltered, send a willing independent worker with funded means, or travel and do the work personally.

Scope: One existing site and one bounded remote-control job. No mind duplication, free offline factory, native singleton copied world or global automation engine.

Integration: Root-owned binding of operator attention, device body/location/support, actual energy/cargo custody and job participants. Detached profiles must be joined through existing native adapters before claiming playable remote work.

Chain: Known usable endpoint, actual controller/device permission and compatible control method → The real operator, device support, finite energy and exact target stock → One supported control session/job, with any endpoint interruption observed by declared policy → Useful remote site output remains at its actual owner until collected/transferred → Later local use requires real collection/cargo/return rather than teleporting item creation → Lost controller, exhausted fuel or inaccessible endpoint pauses/ends the job by explicit policy; no second person continues as the same mind → Retain remote work result, operator occupation, remaining stock and changed return.

Time/compatibility: Existing played clock and independent region leases; explicit pause/absence policy with no extra world clock. One versioned job/context extension if necessary; unsupported old bodies/regions stay inert. Preserve a single attention/inventory/publisher owner.

Later playable gate: Operator cannot perform incompatible simultaneous work; remote result stays in target custody; lost support stops useful work; personal/independent-worker alternatives remain distinct and generated reload retains the commitment.

Source: ONI-F13, ONI-F14, ONI-F27, ONI-F34. Risk: This is the broadest packet and should follow an agreed shared interface; source terminal/depot internals and whole offscreen simulation remain incomplete.

No gameplay, save, browser or regression suite was run. Source/narrow artifact checks cannot verify these future behaviors. [PACKETS.json](PACKETS.json) retains exact current owner pointers and acceptance needs.
