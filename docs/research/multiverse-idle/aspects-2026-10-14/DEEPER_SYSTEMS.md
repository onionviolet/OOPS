# Three deeper system reads

Public evidence only. No method bodies or data tables recovered. These are deeper interaction analyses, not decompile findings.

## DS1: Training as an explanation chain

SHOWN S02: main-stat heading, next milestone, reset count, speed; secondary numeric rows with individual caps; active slot count, stamina and filtered upgrades. STATED E06 developer explanation: training secondary stats raises their main stat; main-stat milestones offer secondary growth or training-speed improvements. Player reports described conflicting tooltip breakdowns in the old web demo, acknowledged for investigation.

INFERRED diagram: choose secondary → train at governing speed → raise main stat → reach milestone → select a change. This is an explanatory model, not exact code or guaranteed loop order. Complete costs, caps and effects remain unread. The important YAIRPG adaptation is one shared canonical breakdown for row, tooltip and preview (P01/P04), not copying this stat hierarchy. At 1366×768 use two or three relevant rows and an inspectable breakdown while keeping useful action controls visible. Other current actions stay reachable; do not demand six permanent categories.

Future source route: locate training update, display formatting and tooltip consumers; trace a single tick through cap/milestone; verify accelerated spending and UI use the same result. Stop at a named mismatch or one complete chain rather than decomposing the whole game.

## DS2: Origin, formation and local mechanical distinctions

SHOWN S01 places origin filter, formation and details next to each other. Local set progress is separate from player bonus and active skill. S03/S05 distinguish local rewards; S05 adds zone/enemy modifiers. These are multiple axes: where something came from, what it contributes now, and where it is useful.

INFERRED YAIRPG proposal MI-P03: preserve those axes as separate columns/facts. A local credential might be known yet lack jurisdiction; a charged artifact might cross yet lack fuel; affection is not formation eligibility. None of these specific semantics are proven in Multiverse Idle. The existing nested-world owner already owns carrier contracts and changed revisits; this source adds a retrieval pattern, not ontology.

Future source route: selected-entity identity, origin category data, class/set bonus resolver, travel/world selector, and mutable instance/save binding. Need evidence of an actual transition before claiming team/item continuity. At 1366×768 list and detail together can be useful; a permanently expanded grid of every world would spend space without evidence of simultaneous work.

## DS3: Navigation, progress and durable return

SHOWN S02 has an offline allowance meter; S01-S06 have separate help/quest/system regions. STATED E02/E06 old reports missed unlocks, save/options and minimized-window progress. Developer says entering Map stops battle but switching other named views should not (E06); E03 later withdrew the web version and claims Steam autosaves work. Contradictions are temporal/platform differences, not proof that one report is false.

INFERRED design consequence: navigation should declare whether it merely inspects or changes execution; allowance, applied output and stopped work need different labels. MI-P04/06/07 reuse YAIRPG discovery and clock owners. Do not write an offline executor to imitate a bank label. Current integration map requires frozen resting branches and coherent native envelope, so observing a roster cannot advance a second life.

Future source route: page-change handler → battle stop intent → save writer → resume-time calculation → bank/application receipts. Inspect transaction ordering and failure paths. A later native run would need an isolated test profile; none was launched here.
