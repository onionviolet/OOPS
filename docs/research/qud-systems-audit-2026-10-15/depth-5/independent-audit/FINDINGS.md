# Independent branch findings

## AQ1: the actual serializer does not preserve the pending transport

`SpaceTimeVortex` declares public destination ID and delay, plus transient queue, coordinate dictionary, initial-turn flag and summonable cache. The entire captured class has no save/load, write/read, object-loaded, final-read, remove or destruction override. [Part declaration and complete body](private/source/XRL.World.Parts.SpaceTimeVortex.cs).

`GameObject.Save` serializes the object's parts through `IPart.Save`. That writes the concrete part type and stat shifts, then invokes `SaveData`. The inherited `SaveData` invokes `Write`; inherited `LoadData` invokes `Read`. The generic component writer and reader explicitly skip static, literal and NotSerialized fields. The exclusion applies whether or not a private field is enumerated by the cached reflection helper. There is no vortex-specific route here that writes the queue by hand. [GameObject L1903-1964](private/source/XRL.World.GameObject.cs); [IPart L329-400](private/source/XRL.World.IPart.cs); [IComponent L4396-4484](private/source/XRL.World.IComponent`1.cs).

On stock load, `IPart.Load` obtains an instance, sets its parent and stat shifter, then invokes `LoadData`. GameObject loading adds the part with `Initial: false`; `AddPartInternals` calls `Initialize` only when Initial is true, but still calls Attach. The vortex supplies no Attach override. The default `ObjectLoaded`, `FinalizeLoad` and ordinary part callbacks do not reconstruct a transport queue. The loaded object's finalization resolves registered external event binds, finalizes its effects and parts, and clears its serialization flag; reader finalization iterates only tokenized objects, then performs compatibility and invalid-object cleanup. No vortex queue reconstruction appears in these reviewed bodies. [IPart L259-278,351-400](private/source/XRL.World.IPart.cs); [GameObject L2119,10013-10053](private/source/XRL.World.GameObject.cs); [GameObject L2220-2245](private/source/XRL.World.GameObject.cs); [reader L665-680](private/source/XRL.World.SerializationReader.cs).

This closes **whether the stock component serializer writes the queue**, not whether every possible external reference to every queued creature is absent. A creature serialized through another owner's field or event binding could exist in a save independently of the missing queue. Its placement or reattachment would need its own consumer. The exact reflection instance factory, all compatibility routines and all external owners remain unread. The initial-turn flag is likewise excluded; no claim is made here about every pooled versus newly constructed load instance.

## AQ2: scheduler inactivity is a real removal, not a pause marker saved with the queue

The unresolved-destination branch in `ApplyVortex` admits targets passing render, reality, scenery, phase, excavatory and ignore-tag checks. A player, nontrifling player-led creature, important object or interesting object goes through explicit tracking instead. Other eligible targets with a current-cell location are appended to the queue, indexed by that location, removed from context and made inactive. A target without usable coordinates is sent to obliteration. These operations occur without checking that context removal succeeded. Later flushing rechecks actual context, so an object whose other relation survives is skipped. [vortex L330-438,549-567](private/source/XRL.World.Parts.SpaceTimeVortex.cs).

`GameObject.RemoveFromContext` sends an event. Physics handles inventory, equipped and current-cell removal, with local exception handling. `HasContext` asks a context event rather than inspecting the queue or an object ID. The context event tests an object owner or a cell context. Queued ownership itself is not exposed as a context by this vortex part. [GameObject L2938-2941,3032-3035](private/source/XRL.World.GameObject.cs); [Physics L2334-2379](private/source/XRL.World.Parts.Physics.cs); [context query](private/source/XRL.World.GetContextEvent.cs); [removal dispatcher](private/source/XRL.World.RemoveFromContextEvent.cs).

`MakeInactive` calls `ActionManager.RemoveActiveObject`. When removal from `ActionQueue` succeeds, that removes the actor from ability objects, applies active-event unregistration and emits an after-removal event. `ActionManager.Save` explicitly saves its current action queue. A removed victim therefore has no remaining scheduler-queue entry to save on that path. This is stronger than an inference from a transient field, but does not rule out separate external references or event listeners. [GameObject L3521-3532](private/source/XRL.World.GameObject.cs); [ActionManager L85-99,342-362](private/source/XRL.Core.ActionManager.cs).

The generic writer tokenizes only objects actually supplied through its write methods. Writing one object schedules its full body once; the subsequent token loop can grow as body serialization discovers more references. It is not a process-wide sweep of every allocated GameObject. The reference-only overload can instead record an existing object ID without enrolling its body. [writer L3019-3109](private/source/XRL.World.SerializationWriter.cs). Whether another save root enrolls a particular deferred victim remains open.

## AQ3: flush ordering creates meaningful combinations and failure limits

`RequireDestinationZone` first returns immediately if the destination string is already nonempty. Otherwise it derives a world from the current vortex zone and obtains a random destination. Missing queue or dictionary then causes an early return. With both containers present, a nonempty destination triggers per-victim validation and a no-context check. It looks up the saved coordinates, finds a destination cell, calls `Teleport`, then calls `MakeActive`. No check of the teleport return value gates reactivation or reference release. A null landing requests obliteration. Per-victim exceptions are logged, and normal completion clears both containers. If no destination is found, it requests obliteration for valid contextless victims and clears the containers. [vortex L88-140](private/source/XRL.World.Parts.SpaceTimeVortex.cs).

This is not a retry queue. A failed teleport result, or an exception caught for a victim, is followed by queue release if the outer iteration completes. `MakeActive` itself acts automatically only for an actor with a brain unless forced. The scheduler then requires a valid, nongraveyard object with an energy stat; it can admit a contextless object because its zone is null. Thus a failed placement can still lead to an activation request, with the exact outcome dependent on later movement and actor rules. [GameObject L3521-3527](private/source/XRL.World.GameObject.cs); [ActionManager L299-327](private/source/XRL.Core.ActionManager.cs). No native failure has been induced.

The immediate contact path calls `RequireDestinationZone` **before** it selects the current target's landing and fires `SpaceTimeVortexContact`. The queued-victim flush never fires that contact event. Therefore the current explicitly tracked visitor can veto its own contact after earlier queued creatures have already been processed. It is not an all-or-nothing group transaction. The final immediate `Teleport` result is also not propagated by `ApplyVortex`, which returns true after invoking it. [vortex L398-438](private/source/XRL.World.Parts.SpaceTimeVortex.cs).

Teleporting across zones can modify Lost, add Incommunicado for a nonplayer follower and clear a nonplayer's AI goals before the actual forced `CellTeleport` call. The wrapper plays sounds on both sides and increments the player's vortex achievement after the call without testing its result. These are side effects of the attempted transit, not proof that movement succeeded. [vortex L339-370](private/source/XRL.World.Parts.SpaceTimeVortex.cs).

Two eligible vortex-descended objects touching take the collision branch before ordinary queuing. One is sent to obliteration and the other to a neutron explosion; neither branch drains pending victims first. Reality stabilization similarly requests destruction without a queue drain in this part. These are distinct cleanup entry points, not evidence that every explosion destroys its target or that destruction cannot be vetoed. [vortex L64-75,373-397](private/source/XRL.World.Parts.SpaceTimeVortex.cs).

The existing-nonempty-destination early return can bypass a queued flush if some other code sets that field while a queue exists. This audit does not establish that such a stock field-write sequence is reachable. A complete assembly call/write-site inventory remains a separate question.

## AQ4: expiry handles registered contents, not arbitrary list members

The stock XML composition is `Space-Time Vortex` to `Space-Time Anomaly` to `InertObject` to `PhysicalObject` to `Object`. The vortex adds Temporary with default duration20 and the vortex part. Its ancestors supply physical/rendering/sound/damage-rejection behavior. There is no Inventory part or queue-specific contents adapter declared along this chain. The mutation-created lifetime can override the default; the XML default alone is not the duration of every cast. [phenomena L20-49,658-682](private/source/PhysicalPhenomena.xml); [root L22-25](private/source/RootObjects.xml). Full effective blueprint expansion and every inherited part's listeners remain separately bounded by the primary audit.

`Temporary.Expire` obtains contents through the contents-event API, expires temporary children, removes contents, requests owner obliteration, removes the owner from context and optionally emits a replacement. `GetContents` delegates to an event; the vortex part does not register or implement a queue-to-contents handler. Its queue is an ordinary list field, not the standard inventory. Expiry therefore has no explicit queue-drain call in the reviewed vortex/Temporary bodies. [Temporary L220-256](private/source/XRL.World.Parts.Temporary.cs); [GameObject L9583-9611,9640-9643](private/source/XRL.World.GameObject.cs).

Ordinary `Destroy` checks before-destruction permission, sends OnDestroy, then asks Physics to tear down. Physics removes equipped/inventory/cell links, removes the owner from the action queue and adds the owner to a zone or global graveyard when requested. These bodies do not recursively discover arbitrary list fields. The vortex supplies no OnDestroy handler. Therefore one must not substitute a generic child sweep for the missing transport cleanup. [GameObject L4046-4147](private/source/XRL.World.GameObject.cs); [Physics L3862-3931](private/source/XRL.World.Parts.Physics.cs).

The stock zone deactivation method emits a zone event, with no local queue drain. Zone freeze serializes the zone, finalizes serialization, persists compressed bytes and releases the in-memory zone. `Zone.Release` pools the objects still in cells. The queue does not itself place a victim back into those cells. These paths increase the need to examine external ownership; they do not prove the instant of garbage collection. [Zone L2282-2303,2943-3020,7835-7838](private/source/XRL.World.Zone.cs); [manager L885-982](private/source/XRL.World.ZoneManager.cs).

**Fate statement:** under the reviewed stock part/scheduler paths, pending victims are detached, made inactive and omitted from the vortex's save representation; expiry and destruction provide no explicit queue drain. The in-memory queue can retain them while its vortex part remains reachable. The exact ultimate fate of each victim under graveyard lifetime, pooling, external references, save roots, compatibility cleanup and runtime garbage collection is still unresolved. Neither guaranteed deletion nor guaranteed recovery is established.
