# Relationship access, recovery attempts and cleanup

## A7-1: body access and ID fallback are separate consumer policies

The complete PartyMember structure contains only a GameObjectReference and integer flags. PartyCollection is keyed by BaseID and serializes each key, wrapper and flags. Reading reconstructs those entries. Neither class adds cells, starts AI or searches for an absent body. The complete GameObjectReference stores integer ID and cached Object, and serializes the pointer through Reference:true. Its own Read only stores what the reader returns. The depth6 writer analysis establishes when another full-body holder makes that pointer available; that condition is not repeated as a new native result here. [PartyMember](private/source/XRL.World.AI.PartyMember.cs); [PartyCollection](private/source/XRL.World.AI.PartyCollection.cs); [reference wrapper](private/source/XRL.World.GameObjectReference.cs).

Brain.PartyLeader simply returns LeaderReference?.Object. A surviving integer ID alone does not trigger fallback through that property. Leader traversal such as IsLedBy, IsPlayerLed and final-leader selection repeatedly uses cached PartyLeader pointers; it can detect an immediate cycle back to its owner but does not reconstruct a missing object by ID. If a wrapper points to a restored contextless body, the getter can return that body; that still says nothing about placement. [Brain L453-464,1445-1505,1630-1666](private/source/XRL.World.Parts.Brain.cs).

Other consumers explicitly choose fallback. Brain.PartyMemberOrder uses the wrapper's Object or FindByID(integer key), returns true for invalid/missing members or the independent flag8388608, otherwise false. Beguiling.YieldTargets similarly selects flag2 members, uses Object or FindByID and yields any nonnull result. These lookups do not assign the found body back into the wrapper in the reviewed methods. FindByID(int) searches active/cached zones, not the serialization token table, and returns null if not found. A detached body already available through Object can be used; an ID-only missing body is not reconstructed here. [Brain L4350-4363](private/source/XRL.World.Parts.Brain.cs); [Beguiling L243-261](private/source/XRL.World.Parts.Mutation.Beguiling.cs); [GameObject L3122-3155](private/source/XRL.World.GameObject.cs).

SupportsFollower looks up the existing member's BaseID in the leader's PartyMembers collection and optionally checks flags. It neither validates a current cell nor moves the follower. Membership can remain meaningful for a valid but detached object. The flag-specific companion-limit routines sort and remove collection keys when the limit is exceeded, then add/change the new target entry. Removing a collection entry is not a movement or immediate generic effect-removal operation in these methods. [GameObject L4527-4544](private/source/XRL.World.GameObject.cs); [Beguiling L263-299](private/source/XRL.World.Parts.Mutation.Beguiling.cs); [Proselytize L94-141](private/source/XRL.World.Parts.Skill.Persuasion_Proselytize.cs).

Queue eligibility remains a prior condition: a nontrifling player-led actor normally forces explicit vortex tracking instead of the deferred queue. A relationship example involving deferred victims therefore needs an independently eligible actor, such as a qualifying NPC-led actor, a trifling case, or a later relationship change. This audit does not turn normal player companions into queue candidates by assumption.

## A7-2: the stock join command does not discover contextless party bodies

ZoneManager.ProcessGoToPartyLeader issues JoinPartyLeaderCommand. Issue queues its singleton only if that action is not already pending. Execute scans Game.ZoneManager.CachedZones, each zone's cells, and each cell's Objects; it calls GoToPartyLeader on those occupants. It repeats while movement was reported, with an explicit iteration ceiling, and breaks a zone pass if the cached-zone count changes. It does not enumerate PartyMembers, read reference wrappers, scan all allocated objects or traverse the save-reader token table. A body absent from every cell therefore is not selected by this command, even if a leader's relationship collection can reach it. [manager L4599-4603](private/source/XRL.World.ZoneManager.cs); [complete command](private/source/XRL.Core.JoinPartyLeaderCommand.cs); [GameObject L3459-3463](private/source/XRL.World.GameObject.cs).

The ordinary Brain action path has another guard. It exits after spending1000 energy when ParentObject.IsNowhere(), before its later GoToPartyLeader call. IsNowhere is true for a graveyard object or an object with no current cell and no object/cell context. Object context can recurse to an owner's location; a genuinely detached queued actor has no such route. Combined with depth6 scheduler validation, ordinary AI does not use this branch to restore a detached actor's context. [Brain L2355-2402](private/source/XRL.World.Parts.Brain.cs); [GameObject L3005-3025](private/source/XRL.World.GameObject.cs).

IsTryingToJoinPartyLeader is stricter than the direct join function: it requires both follower and leader cells, different valid zones, a non-world-map destination, no staying/DoesNotJoinPartyLeader/player exclusion, a permitted zone property and an event admission check. Its suspension/freezing-advisability use therefore cannot be treated as evidence that a null-context follower is queued for recovery. [Brain L2569-2603](private/source/XRL.World.Parts.Brain.cs).

## A7-3: direct movement is possible in principle, but acknowledgments need checking

GoToPartyLeader requires a non-nowhere leader, no Staying, no Dominated/player state, a real leader cell, a non-world-map destination and no blocked JoinPartyLeaderPossible property. It permits the follower's own cell to be null. A DoesNotJoinPartyLeader check and event admission can still reject it. It clears goals, gathers candidate cells near the leader, rejects combat occupants/solid/high-navigation-weight cells and uses CanJoinPartyLeaderEvent to choose a landing. Null source yields distance0. With a chosen cell, it calls SystemLongDistanceMoveTo, spends1000, sends JoinedPartyLeaderEvent and returns true. The method does not check the movement function's return value before those later side effects. Thus a reported join is an attempted transit, not sufficient proof of placement. [Brain L2605-2677](private/source/XRL.World.Parts.Brain.cs); [GameObject L2798-2806](private/source/XRL.World.GameObject.cs).

An independent cross-check of the primary lane's movement windows confirms the boundary. ProcessTargetedMove tolerates a null origin in its top-level control flow and can attempt adding to a supplied target, but still has movement, target-admission, zone and event gates. Physics.EnterCell rejects an invalid/graveyard object and otherwise sets CurrentCell and clears inventory/equipment ownership. Cell.AddObject returns the passed object even when EnterCell rejects it; it adds to Objects and emits enter/entered notifications only after that rejection guard. RestoreContextRelation needs a supplied previous owner/cell/body part and relation code, with no discovery of the lost vortex coordinates. Its cell branch uses AddObject equality as an acknowledgment, so equality alone is weak evidence. These windows support a possible explicitly invoked placement route, not a stock recovery trigger. [Physics L2121-2174,3783-3860,4199-4234](private/source/XRL.World.Parts.Physics.cs); [Cell L3390-3424](private/source/XRL.World.Cell.cs).

The primary lane separately traces lower-level movement helpers and attribution-field accessors. This independent pass does not claim a complete assembly-wide caller census for GoToPartyLeader or every custom external action. No such movement was executed.

## A7-4: retained targets can change internally while remaining detached

Beguiling.ChangeLevel iterates YieldTargets, finds each target's Beguiled effect and calls SyncToMutation. If a preserved target pointer remains available, this call can reach a contextless body because the target iterator itself only checks nonnull after wrapper/ID access. SyncToMutation ignores independent effects; otherwise it obtains the beguiler's current mutation, marks Duration0 if unavailable, or updates Level and ApplyBeguilement when the rank differs. ApplyBeguilement changes HP.BaseValue by5 times the rank delta, updates an opinion when the Brain/beguiler are valid, then stores LevelApplied. These named consumers have no cell-placement call. Reality-distortion usability and source mutation availability still affect the result. [Beguiling L243-309](private/source/XRL.World.Parts.Mutation.Beguiling.cs); [Beguiled L125-197](private/source/XRL.World.Effects.Beguiled.cs).

Cleanup is distinct. The effect's BeginTakeAction handler marks Duration0 when no longer supported or synchronizes otherwise. That action-triggered check is not a guaranteed prompt cleanup route for an inactive detached actor. Marking Duration0 is also not proof that the separate removal sweep already ran. When Remove actually runs, it can clear the leader/goals if no alternate support remains, remove its allegiance, subtract previously applied HP, remove its opinion and clear Beguiler. A contextless object retained in memory can therefore have relationship/effect state that needs a later actual removal consumer. This audit does not infer the exact removal timing from setting Duration. [Beguiled L101-224](private/source/XRL.World.Effects.Beguiled.cs).

SetPartyLeader changes the cached leader pointer, removes the old leader's membership entry, adds the new nontransient membership and sends relationship events. In its nontransient new-leader branch it also clears the follower's LastDamagedBy and InflamedBy if they equal that new leader. Therefore changing relationships can remove two of the alternate damage-history preservation links traced in depth6. The remaining weapon/projectile fields and other owners require separate inspection; clearing two fields is not collection of the actor. No direct placement call appears in the reviewed setter body; its relationship-event listeners remain separate consumers. [Brain L898-951](private/source/XRL.World.Parts.Brain.cs).

## A7-5: named finalizers reconnect behavior, with composition gaps retained

PartRack.FinalizeRead applies each part's registrar, then invokes its FinalizeRead, handling changes to the part collection while iterating. If the saved extension hash differs from the current extension hash, it additionally invokes configured part-extension finalizers. The generic IPart finalizer delegates to its default empty FinalizeLoad. The rack does not itself assign a context, but arbitrary part Register/FinalizeRead methods and extension migrations can have their own behavior. Those are not dismissed by reading the rack alone. [complete rack](private/source/XRL.World.PartRack.cs); [IPart L259-278,391-400](private/source/XRL.World.IPart.cs).

Two already captured skill-support base classes illustrate a narrower restoration hook: Initialize may create/require an ability, but FinalizeRead only looks up the restored activated ability by command when its transient AbilityEntry cache is null. It does not call RequireAbility in that finalization branch, place the actor or register it in the action queue. Remove differs by class: the skill sends a support query while the support part removes its command ability. These complete small bodies close that named hook family, not every NPC's full composition. [skill-support base](private/source/XRL.World.Parts.Skill.ISupportAbilitySkill.cs); [support-part base](private/source/XRL.World.Parts.ISupportAbilitySkillPart.cs).

No exact stock creature's entire effective inheritance, randomized mutations, inventory/equipment, effects and part-extension set has been exhaustively followed in this independent pass. That remains an explicit composition gap. The result is a precise separation: relationship access can reach an existing preserved body; internal buffs/cleanup can act on it; the inspected ordinary join-command and AI routes do not discover and place a detached victim automatically.
