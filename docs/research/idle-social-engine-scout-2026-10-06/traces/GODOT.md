## Full-task comparison

**Retain JS plus a Godot presentation shell:** keep current registry, command previews/committers, inventories/native classes, one clock and save publisher in JS. Build an observed projection and command bridge, scene UI, stable focus/keyboard behavior and error acknowledgement. This reuses domain state but incurs two UI/language/build surfaces and a browser-only bridge; desktop export would need a different host binding. It adds no new NPC motivation, campaign causality or power combinations by itself.

**Port domain logic into Godot:** migrate native model classes, typed declarative content and all host joins; reconstruct JS save envelopes, retained Ink artifacts/opaque cursors, encoded item keys and optional schema compatibility; reimplement pause/recovery and export/import; then qualify changed timing/number/random semantics. Godot's scene/resource authoring can help spatial scenes but does not supply these game-specific contracts. Full effort is qualitatively high. No conversion, authoring-speed benchmark, export or save test was performed.

**Keep current route:** data definitions and optional compiled Ink already bind worlds/instances to one durable state. For a later finite map, first demonstrate a movement/visibility decision with the existing host and a small read-only map; use an engine scene only if the authoring/presentation gain exceeds the bridge maintenance. This is a conditional alternative, not a sixth ranked candidate or an installation request.

Reconsider migration only after a disposable scene lets the same character choose two meaningfully different spatial tactics and use the same owned means, knowledge and durable result through current commands. A pretty scene or imported tilemap is insufficient. The later gate must preserve interrupted work and generated-fixture save/export/import under explicit compatibility decisions. All gameplay/browser/save/regression/director gates remain deferred.

Unread: Godot scene/editor/resource internals, physics/navigation behavior, mobile/native packaging, accessibility of exported controls, full filesystem C++/Emscripten paths, custom template compatibility, third-party notices and performance. No current hardware/browser behavior is claimed.
