# Rain World: connected rules, consequences and cleanup

Research-only independent code audit, 2026-10-15. Status: PARTIAL. Four connected chains are source-traced; the captured game is far larger than these windows. No native game, save, executable or gameplay test was run. No Rain World code or assets were copied into YAIRPG.

The installed managed assembly was pinned by the extraction lane at Steam build `22785462`, SHA-256 `b6be1d4e18ce219d21091b51564cb6a11c1e4106b41de903eb8e58849cb16fdb`. This audit reads the sibling's ILSpy exports and independently checks consumers. [Findings](FINDINGS.json) contains exact source path, method, line range and file hash for every chain. [Reading ledger](READ_LEDGER.json) distinguishes whole small-class reads from selected windows and unread captured classes. [Unread work](UNREAD.json) names missing consumers. Raw source remains outside Git under the private research archive.

## RW-F1: perception changes the relationship, which changes the active problem

Source: `Tracker`, `LizardAI`, `RelationshipTracker`, `ThreatTracker` and `PreyTracker` windows indexed in FINDINGS.json.

A tracked creature is a representation, not simply a direct pointer used as perfect knowledge. The representation owns last-seen coordinates, age, a forget counter, visual-contact state, priority and an optional dynamic relationship. `VisualContact` clears itself when the realized target is absent, in a different realized room, or a qualifying hidden player. `TicksSinceSeen` subtracts the observer's `seeAroundCorners` grace period. This is a deliberate allowance, not literal proof of line of sight every frame. The update scans target body chunks for visibility, records the target's current washed coordinate only while seen, and increments forgetting while unseen. Hearing can shorten the unseen timer. A configurable negative remember limit disables this particular expiry check.

`Destroy` on the representation only sets `deleteMeNextFrame`. Physical deletion is separate. The enclosing tracker removes flagged representations during its update; `RelationshipTracker` removes associated dynamic relationships when it sees the same flag. A full-capacity tracker selects a weak representation using relationship intensity, sight, distance and forgetting, then flags that representation. Not every creature is represented: dead creatures may be rejected through the AI policy, `DoesntTrack` is rejected, and representation creation can return null. Capture of these methods does not establish all creature-specific policy implementations.

Elaborate representations maintain multiple movement ghosts. The reviewed visible branch discards all but one and resets that survivor when contact returns. The unseen branch updates and prunes flagged ghosts while retaining at least one. Detailed ghost propagation, branching and path validity remain unread. The audit therefore does not claim a complete belief-map model from seeing these containers.

A concrete consumer is the lizard's reading of a player's held spear or vulture mask. It refreshes those fields only while the target representation has visual contact. An unseen target can therefore retain a previously observed equipment state. Black and red lizards bypass the mask intimidation branch. Ordinary masks do not intimidate green lizards through this branch: they yield an ignore relation. Other admitted lizards receive an afraid relation with species-dependent strength. King masks differ from ordinary masks. `usedToVultureMask` increments in this relationship-update branch; the mask window is bounded by 700 ordinary or 1,200 king updates, with an inverse-lerp fear curve beginning to fall at 600. These are updates of this path, not verified seconds, universal species timers or a save-backed trait. The increment is not inside the visual-contact sub-branch, so a retained mask observation can continue habituation while unseen. The counter's cross-load lifecycle is unresolved.

The relation type has consequences beyond a numeric hostility modifier. `LizardAI.ModuleToTrackRelationship` directs afraid targets to `ThreatTracker`, eats/attacks targets to `PreyTracker`, and aggressive rivals to a separate aggression module. When type changes, `RelationshipTracker.SortCreatureIntoModule` removes the target from the old module, then adds it to the new one. The relationship's intensity multiplied by the module weight also becomes representation priority.

Cleanup has an important exception. A transfer sets `ignoreModuleAbandon` while removing old membership. Without that guard, a module's abandonment callback can cause the tracker representation to be destroyed. `ThreatCreature.Destroy(bool stopTracking)` calls the abandonment callback unconditionally in the shown body; the parameter name does not establish a conditional policy. Removal from the old module during a relationship change is protected by the relationship tracker's guard. Ordinary threat deletion still removes both the threat point and threat creature record. A zero-threat reset counter reaches 200 before clearing remembered threats; live threat updates reset representation forgetting, so the generic forgetting timer is not an independent universal upper bound.

The spatial threat consumer uses best-guess position. A threat in an adjacent room may be projected to the connecting shortcut at half strength. Tile threat sums contributions proportional to severity raised to 1.5 and inverse distance raised to 1.25, with clamping near the source, creature-specific accessibility and visibility adjustments. `accountThreatCreatureAccessibility` is accepted by the reviewed tile method but is not read in its body; the accessibility calculation still runs when its own predicate passes. This is another reason to trace code rather than infer semantics from an argument name.

**Inference:** hiding, stealing a visible mask, or moving a predator through a connection can change pursuit and escape decisions without a scripted encounter. The ingredients are shown; any particular encounter outcome and exact timing remain unobserved.

## RW-F2: hunger, danger, rain, injury and companionship compete, then exceptions intervene

`UtilityComparer.UtilityTracker` computes `pow(module.Utility(), exponent) * weight`, optionally smoothed by a supplied tweener. The comparer chooses the strictly greatest result in list order. The constructor stores `continuationBonus`, but the reviewed comparison never consumes it. Calling that field a working hysteresis bonus would overstate this build. Persistence of behavior does exist elsewhere, including module smoothing, prey persistence bias, target memory and explicit overrides.

The lizard registers threat weight 1, prey 0.6, rain 0.9, injury 0.9 (red lizard 0.4), aggression 0.5, mission 0.8, sound 0.2 and friendship 0.9, plus species-dependent modules. These are constructor settings, not immutable live values. In update, aggression weight becomes story/non-story factor times current lizard health. Threat decline smoothing depends on accumulated distress length. Rain weight becomes 0.9 or 0.1 according to friendship's rain concern. Fear is therefore neither a fixed trait nor instantaneous truth.

`DetermineBehavior` maps the winning module to flee, escape rain, hunt, injured, fighting, mission, lurk, investigate sound or follow friend. Utility below 0.05 selects idle. But this is not a pure winner-take-all planner: carrying edible prey overrides any behavior except flee and selects return prey at utility 1. A frustrated non-red hunter can switch to frustrated; a stranded animal trying to return prey or escape rain can also become frustrated. Travel can override a subset of low-utility behaviors, and a spit-position counter can override again. These are ordered rules, so two systems with the same utility can still produce different actions.

Update order matters. `LizardAI.Update` reads the comparer and selects behavior before calling `base.Update` at its end. `ArtificialIntelligence.Update` then updates modules in insertion order; the comparer was inserted before the relationship tracker. The chain is therefore staged across cached/module update state, not a same-instant read of new perception, new relationship and new decision. Exact wall-clock latency was not measured.

The decision has a concrete consumer: flee asks `ThreatTracker.FleeTo` and writes an abstract destination; rain escape, return prey and injury choose the den if one is known; follow friend chooses the friendship destination and changes run speed. Follow friend releases the held friend if the lizard itself has grabbed it. A successful decision is not proof of an accessible den, successful path or actual arrival. The deeper flee-search and locomotion consumers remain unread.

`RainTracker.Utility` is a shared clock rule with exceptions. Night creatures and ignore-cycle creatures normally return zero. A prior scavenger locust check can return 1 when a swarm is progressing and no puffball is held, before that early-out. Other branches include corruption, a configured deer behavior exception with riders, precycle exposure, room danger types and a 0.6 precycle threshold. Story sessions use the 800-to-4,000 time-until-rain range through an S-curve; other sessions use 80-to-400. These values are in the clock's units, not asserted wall-clock durations.

`FriendTracker.CareAboutRain` returns false when the friend is in the same room or a directly connected room, and true otherwise. The lizard consumes this as a weight reduction, not complete rain immunity. Friendship urgency comes from temporary like, mapping 0.25..1 into 0..1. Following usefulness depends on separation, desired closeness, and special gate/shelter behavior. A close friend can weaken rain urgency while threat or injury still wins. This is a specific combination with a visible state cause rather than an assigned companion script.

**Inference:** the same lizard can break off a hunt, hesitate after danger disappears, keep close to a friend as weather worsens, or carry prey home. Exact live sequences are not verified. The rule composition explains how such scenes can arise; it does not prove all scenes happen or replace encounter testing.

## RW-F3: a gift must become a recognized transaction; trust has distinct time scales

A dropped item is not automatically a gift. `OwnedItemOnGround` owns donor, item, chosen recipient, age, active and offered flags. A slugcat moving at least 50 world units away triggers the offering attempt once. An automatically selected recipient must be alive, realized, within the candidate 500-unit radius, have a realized AI that reacts to social events and a tracker, and have a representation of the giver seen within 120 adjusted ticks. MSC adds carried-player and giver-held-target exclusions. Stolen-property IDs reject a slugcat offer before selection.

Ownership expires after a threshold based on whether a recipient exists and whether the item is a living creature. The four thresholds are 600/1,200 updates when offered to someone and 200/400 without a recipient, for living/nonliving respectively. Taking an item makes the record inactive. If the first grabber is the intended recipient, it emits a transaction event and may notify that recipient's friend tracker. The donor leaving the room also inactivates the record. Inactive ownership records are removed by the recognizer's next cleanup pass. Since the age-expiry flag is set before the grab branch and there is no return there, an expiry-frame transaction emission is possible in this method; `FriendTracker.GiftRecieved` still requires an active record to run the AI callback. Those two events are not interchangeable.

For lizards, `FriendTracker.ItemOffered` only records a creature that the lizard's dynamic relationship treats as food. Its update checks actual grasps, then consumes the gift callback once by nulling the stored offer. Inactive offers are cleared. The lizard callback rejects the rot-type case after obtaining a social relationship. Above like -0.9, a dead food creature changes permanent like by 1.2 divided by taming difficulty and temporary like by 1.7 divided by difficulty; living food uses 0.6 and 0.9. A challenge-specific multiplier can replace ordinary difficulty. Separate community influence is requested for player donors. The relationship mutator later reduces permanent influence as familiarity grows, so raw gift constants are not the final like delta.

Social memory is per subject ID with permanent like, fear and know plus temporary like/fear. Like/fear remain in [-1,1]; permanent changes are multiplied by `lerp(1,0.1,know)`. Familiarity approaches 1 but each requested interpolation amount is capped at 0.9. Temporary changes are clamped without that familiarity multiplier. `EvenOutTemps` approaches each permanent baseline with bounded movement, and lizard update calls it with 0.0005. Exact wall-clock decay depends on actual update scheduling.

Recognition of violence is also bounded. Lizard social events reject nonplayers, incompatible ripple layers, missing observer representations and, for attacks on a third party, cases where both participant sightings are older than 40 adjusted ticks. Nonlethal attempt, nonlethal hit, lethal attempt and lethal hit use base magnitudes 0.05, 0.15, 0.35 and 1. An already dead victim divides the magnitude by three. An existing friend is forgiven for attempts and receives half the direct-hit magnitude. Attacking a feared creature can improve relations, with stronger benefit when it currently holds the observing lizard. Attacking a pack member harms relations. The shared change function updates temporary like by 1.5 times change, permanent like by 0.75, familiarity by absolute change times 0.25, and requests a smaller community change. Full community propagation is not independently audited.

Acquiring a friend normally requires both permanent and temporary like above 0.5 and a matching realized creature in the current room. The reviewed loop is not a computed nearest-friend search despite `followClosestFriend` naming; it scans stored relations and current-room creatures. Urgency falling to zero clears both friend pointers. Death-specific clearing of this realized pointer is not present in the reviewed update window, so no universal instant-death cleanup claim is made.

Persistence has a different boundary. `CreatureState.BaseSaveString` includes social data only while alive. The relationship string preserves subject ID, nonzero permanent like/fear, know and recognized-unknown strings. A relation with zero permanent like and fear serializes as empty even if know or temporary state is nonzero. Temporary values are omitted; loading initializes them from the permanent values. `CreatureState.CycleTick` invokes social-memory decay; social cycle decay removes relationships when absolute like and fear both fall below 0.25 after decay. A file format path is shown; an end-to-end save/load or all cycle callers is not verified.

Abstract migration is particularly easy to misdescribe. It samples a social relationship and, if absolute like is above 0.95, searches the world's abstract rooms by subject ID to follow that creature. An existing follow is dropped when its found relationship has absolute like below 0.9. Dead/deleting follow targets cause relationship discard. Because the comparison uses absolute like, this method admits a strong enemy as well as a strong friend. Why and where a species enables that use requires broader callers; it is not evidence that every lizard chases enemies across every region.

**Inference:** rescue, food theft, a missed attack and a landed attack can create different future local behavior even when immediate damage is identical. Memory, temporary affect, faction influence, recognition and physical possession are separate state owners with separate cleanup.

## RW-F4: a selected bite still needs geometry, possession and damage rules

`Lizard.AttemptBite` requires consciousness and an empty mouth, then jaw readiness, bite RNG and a body chunk inside a forward-positioned bite radius. An extended tongue can force retraction instead. `Bite` rejects the new-room invulnerability window, closes the jaws, handles a miss separately, and applies velocity transfer before the grasp/damage decision. A hunt order therefore cannot bypass geometry or all immediate action limits.

A bite may attempt a grasp when the target is food, or through mass/random exceptions. `Creature.Grab` checks ripple compatibility, deletion and the target's `CanBeGrabbed`; it also enforces sharing conflicts and dominance against existing grabbers. It can release conflicting grasps, replace its own current grasp, create the realized grasp and create an abstract grip stick. This permits interactions over the same physical target; exact tug physics and all species overrides remain unread.

A successful grasp and injury are separate. Red lizard bites force the victim to lose its own grasps. The MMF player-friend branch applies 0.1 bite damage; ordinary player branches use bite-damage chance and a player death multiplier before requesting 1.5 damage. Nonplayer branches use configured bite damage times random 0.8..1.2, gated by bite-damage chance. These requests pass into virtual `Violence`, so reading the base consumer does not establish every species' final damage.

The base `Creature.Violence` checks ripple violence compatibility, assigns a kill tag, applies momentum, divides damage and stun by template resistance, then applies damage-type resistance and challenge modifiers. Health-state damage reduces health; quick-death rules involve health and RNG. Damage above the template instant-death limit calls death independently. Stun and physical force are meaningful consequences even if a health threshold is not crossed. Player and species overrides remain explicit gaps.

On death, the reviewed tail marks `dead`, calls `LoseAllGrasps` and notifies the abstract creature. `Grasp.Release` removes itself from the target's grabbed-by list, nulls its owner slot, releases contained sprites, then calls `DropCarriedObject`; that method deactivates matching abstract grip sticks and releases a still-present realized grasp. Nulling the realized slot before abstract cleanup prevents that ordinary callback from repeatedly releasing the same live reference. These are paired realized/abstract ownership operations, not only cosmetic release.

Abstraction has distinct branches. `destroyOnAbstraction` clears realized/real-AI pointers, removes the abstract entity and destroys it. An early missing-realized/not-ready-room branch clears only realizedCreature in the shown method. The normal branch converts coordinates/path state and recursively abstracts carried objects. Under MMF it detects a directly circular grasp or self-grasp and releases it rather than recursing forever. This is not proof against arbitrary longer cycles. RealAI is set null only inside the normal AI/pathfinder guard; realizedCreature is cleared at the end. A missing pathfinder and the early return do not share a demonstrated universal RealAI cleanup guarantee.

**Inference:** an animal's decision can change who carries an object, which other actor gets disarmed, whether a body remains held, and what survives offscreen. The interesting emergence comes from joins among generic contracts. Physics simulation, grasp deactivation internals, save restoration of grip graphs and difficult failure branches still need their own review.

## Proposals and boundaries

| Code | Proposal only | Existing YAIRPG area | Why this source matters |
|---|---|---|---|
| RW-P1 | Keep observed target state separate from current hidden world state. | Actor knowledge and NPC behavior | Mask observations can remain stale; tracking has explicit expiry and resource limits. |
| RW-P2 | Define target-module transfer and ownership cleanup together. | NPC intent, combat and effect lifecycle | A remove callback can mean forget unless a guarded transfer prevents it. |
| RW-P3 | Keep social event recognition, object transfer, transient affect and durable trust distinct. | Character relations, inventory and world events | Gifting depends on actual ownership and time; save resets temporary affect. |
| RW-P4 | Trace utilities through final action overrides and world consumers. | NPC planning, scheduling and movement | A winning hunger utility can still yield return-prey, frustration or travel. |

These are research implications, not accepted product rules or an implementation plan. No new priority, runtime contract, world content or universal constraint is selected. The four traced chains are complete enough to explain their named code joins, but source reading and gameplay acceptance remain separate. The saved flow is [RESEARCH_FLOW.md](RESEARCH_FLOW.md).
