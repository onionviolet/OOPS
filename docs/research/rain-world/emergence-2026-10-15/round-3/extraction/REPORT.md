## RW3-F1: A world snapshot is selective, relocates creatures and separates social memory from temporary AI

Locators throughout this report are exact filenames and one-based line windows beneath the private round-3/extract directory.

`SaveState.SessionEnded:294-340,388-405,450-490` updates cycle/session bookkeeping for a survivor, then calls BringUpToDate before the final SaveWorldStateAndProgression request. `BringUpToDate:632-699` selects a living/any player position, sets den position and next ID, converts actual held items to serialized object/creature strings, calls RegionState.AdaptRegionStateToWorld, and snapshots community liking. PlayerGrasps is a separate array of held-item payloads; this code does not serialize exact physical grasp body-chunk coordinates through that field.

`RegionState.AdaptRegionStateToWorld:1112-1253` clears/rebuilds saved object/population/stick collections. It preserves previously unrecognized entries before rebuilding recognized state. It does not snapshot every world object. For example, shelter objects, wall-stuck spears, creature save flags, quantified-species exclusions, special pending-item transfer and optional friend transfer have different admission rules. It stores a stick only through its A endpoint, and only in a shelter or the designated forced save room. That avoids saving each bidirectional link twice by scanning both endpoint lists; it does not establish global deduplication of duplicate link objects.

`CreatureToStringInDenPos:1487-1527` excludes Slugcat, skips a creature in the active gate, and chooses a save coordinate from spawn den, a valid shelter position or the creature AI's in-region den. Out-of-region selected positions are rejected. Dead creatures are excluded unless the selected destination is a shelter. Serialization can therefore move a saved creature to an abstract den; exact last physical position is not the general persistence contract. The method catches a failed creature conversion and returns an empty record, allowing the outer collection to continue.

`SaveState.AbstractCreatureToStringStoryWorld:1998-2007` writes creature type, persistent entity ID, ripple layer, room/node coordinate and CreatureState string, then custom data. `CreatureState.cs` was read fully in this pass. Its BaseSaveString writes Dead, spawn data, meat and custom flags. Social memory is included only while alive and nonempty. ToString appends unknown keyed state, enabling recognized base fields and preserved unrecognized data to coexist. LoadFromString restores these fields and forwards the Social payload to SocialMemory.FromString.

The prior SocialMemory full read remains valid at the identical hash. Persistent like/fear/know and subject ID are serialized; temporary like/fear are reconstructed from persistent baselines on load. Tracker hypotheses, utility smoother history and realized grasp objects are separate runtime layers and are not shown in this CreatureState payload.

`SaveState.SaveToString:799-869` includes instantiated RegionState.SaveToString or the corresponding uninstantiated regionLoadStrings fallback, as well as unrecognized region payloads, communities, swallowed items, held items and death-persistent state. `RegionState.SaveToString:1364-1432` nests OBJECTS, POPULATION and STICKS with distinct delimiters. These are code-supported encoding layers, not a claim that the final disk write has happened.

**Order limit:** SessionEnded calls BringUpToDate at line399, while a shelter-friend persistent-like boost appears later at431-432. The snapshot list may already hold strings created before that boost. No later recapture of that specific changed creature payload was established, so this pass does not claim the same-cycle shelter boost is durably saved. This is an unresolved source-order question identified independently by the auditor.

## RW3-F2: SaveToDisk acceptance, queued writes and physical storage are three different gates

`PlayerProgression.SaveWorldStateAndProgression:2491-2518` has a distinct malnourished path. Starvation asks for progression/death-persistent updates, optionally uninitializes trackers and backs up region preservation, moves the current state to starvedSaveState, then clears currentSaveState. A later GetOrInitiateSaveState can restore that in-memory starved object. This is not the same as a complete world-state disk save. The normal route requests current world, map and miscellaneous progression saving.

`SaveToDisk:2520-2708` compares current optional modules and every enabled/installed-mod state with the state captured at load. A mismatch returnsfalse before payload assembly. This is an explicit compatibility refusal. If all three save flags are false, it returns true without saving anything. Otherwise it reconstructs a progression string, updates only selected SAVE STATE/map/misc sections, retains other campaigns and uses SaveState.SaveToString for the selected world state.

Its end calls `saveFileDataInMemory.Set("save", Md5Sum(payload)+payload, mode)` only when the file object exists and loading is not in progress. It returns true even when that condition skips Set. With canSave=false, the requested mode is Deferred; otherwise Immediate. Therefore a returned true proves neither a Set attempt, nor queued work, nor storage completion. Some internal log wording reports success while only a string is being composed.

`Kittehface.Framework20.UserData.OperableFile.Set:404-432` assigns the hashtable key under lock and marks modified. Only effective Immediate mode calls Write. Its DataAccessible helper at336-347 always returns true, initializing an empty hashtable if needed. A branch/exception claiming Set cannot occur before load therefore does not represent an effective load-readiness guard in this actual backend.

Write at995-999 calls RequestWrite. `UserData.RequestWrite:2909-2922` queues a FileOperation if an equal pending operation is absent, and starts queue processing when idle. FileOperation equality includes action, owner, filename and override directory (`1874-1945`). Duplicate pending write requests are therefore coalesced by this key, rather than promising one physical snapshot per call. Full queue timing and state captured while writing remain open.

`ExecuteWrite:1001-1090` serializes locked data, optionally encrypts, invokes the platform method, and normally clears modified and completes the operation. The actual platform implementation at1093-1101 directly calls Write_Default in this installed firstpass assembly. Serialize at1112-1149 uses NetDataContractSerializer into XML and returns a MemoryStream backing buffer. Load truncates trailing null bytes before XML deserialization. A map PNG/base64 and progression-delimiter payload can thus sit inside the backend hashtable/XML storage envelope. The progression text is not necessarily the entire physical file.

### RW3-B1: Some default file-write errors can be logged without becoming operation failure

`Write_Default:1508-1548` creates the directory, opens the destination with FileMode.Create/FileAccess.Write, writes and flushes bytes, then closes the writer. This inspected route has no temp-file write or atomic replacement step. It catches exceptions, logs them and does not explicitly rethrow, set Fail or add a failure result. Finally closes the writer/stream if present.

In cases such as directory creation or initial file opening throwing before writer assignment, this catch/finally can return normally. ExecuteWrite then can proceed to clear modified and call fileOperation.Complete. `Operation.Complete:1991-1995` ORs in Result.Success; operation dispatch at2730-2760 forwards the result into NotifyWriteCompleted. Some later-close/log exceptions could still escape and take a different route, so the claim is conditional, not every I/O failure.

This is a static source-supported failure-reporting candidate. No disk failure or corruption was induced, no actual game save was written, and no runtime bug is claimed reproduced. The code includes a separate explicit serialization/encryption failure path; the weak default I/O catch must not erase those distinct guards.

CreateCopyOfSaves (`PlayerProgression:2274-2363`) is a separate backup function, with timestamped folders, a nominal retention target50 and copying several campaign files. No caller timing was established to prove it runs before every write. BackupRegionStatePreservation (`SaveState:741-758`) is different again: it fills missing regionLoadStrings with RegionState.SaveToString to preserve den state; it is an in-memory fallback, not an atomic file backup. Optional vanilla-exploit settings can bypass that fallback.

## RW3-F3: Loading rebuilds an abstract world first, then physical state accepts or rejects restoration

`UserData.Read_Default:1487-1506` reads bytes if the file exists or adds FileNotFound. `ExecuteRead:793-920` captures storage/decryption/deserialization errors in executeReadError, clears unsuitable data as necessary and may still complete the operation after catching a deserialize exception. `Deserialize:936-994` accepts two XML dictionary shapes, reconstructs hashtable values and records unrecognized/failed formats. The higher PlayerProgression layer checks executeReadError separately from the operation result, so Complete is not itself proof of valid parsed gameplay state.

`PlayerProgression.SaveFile_OnReadCompleted:3367-3431` handles FileNotFound by creating a file, corruption by setting an explicit load result, and other failures by terminating load and notifying the platform. On successful storage read it calls LoadProgression. That function at2398-2453 checks executeReadError and presence of the save key before loading miscellaneous progression. Notification behavior differs by branch; do not collapse them into one universal completion callback.

`GetProgLinesFromMemory:2371-2395` splits the first32 characters as an MD5 prefix. A checksum mismatch logs, sets gameTinkeredWith=true and still splits/returns the payload. This is detection rather than rejection. The nonempty string route lacks a length<32 guard before Substring; malformed short-key data is a static exception boundary, not a demonstrated crash. The explicit legacy file route in LoadGameState separately strips32 characters only when length>32 and does not perform the same checksum comparison.

`GetOrInitiateSaveState/LoadGameState:2945-3012` may reuse current matching state or revive starvedSaveState; otherwise it constructs SaveState, selects the requested campaign record and calls LoadGame. Missing/ineligible data starts a clear state. `SaveState.LoadGame:1012-1148` clears several unknown/transferred collections, marks loaded before full parse, splits tagged records and stores known region strings by region name, preserving unknown regions separately. It uses direct numeric parses and indexed arrays in many branches, without a top-level transactional rollback shown in these windows. A fully atomic all-or-nothing gameplay-state load is therefore unproved.

`WorldLoader.cs:1530-1535` calls world.LoadWorld after building abstract rooms. `World.LoadWorld:400-446` assigns room ownership, maps connections, creates/reuses the region state and invokes AdaptWorldToRegionState for a story region. RegionState's constructor at455-585 parses deferred strings into saved object/population/stick lists; unknown creature types go into unrecognizedPopulation. AdaptWorldToRegionState at1027-1070 then constructs saved abstract creatures before recreating saved sticks.

`SaveState.AbstractCreatureFromString:1923-1996` rejects unknown creature types and unresolved room names, can use an override coordinate, and relocates an out-of-region record to its known spawner den when possible. It only calls CreatureState.LoadFromString when a nonnull World exists. The world=null convenience parse therefore does not prove full social-state validation. Successful world-bound construction restores the state and custom flags before the caller adds the creature to its shelter entity list or den. Unrecognized type strings can be retained for later compatibility; unknown rooms and malformed numeric/structural data have different behavior.

RegionState then parses STICKS and calls AbstractObjectStick.FromString with the target abstract room. The previously read endpoint resolver requires both IDs in that room; missing endpoints warn and return. It is not a deferred graph-repair queue. Reconstructed links later reach one-shot PhysicalObject.RecreateSticksFromAbstract and Creature.Grab, whose physical admission can remove a link on failure. The round3 auditor independently deepens destruction/release and duplicate-grip conditions; this extraction does not infer universal deduplication or monotonic link growth.

`RegionState:1109` calls RainCycleTick with elapsed cycles after restoring the region. At737-791 that method subtracts the elapsed tick count from replenishing counters, but calls each creature's state.CycleTick only once when elapsed ticks>0, rather than looping once per elapsed cycle. CreatureState forwards into SocialMemory's decay/pruning. Therefore social-memory catch-up is not simply elapsedCycles multiplied by the single-cycle decay. Optional Watcher rot has a separate per-tick loop, showing distinct scheduling policies within the same method.

### Companion transfer and cleanup limits

Optional MMF snapshot logic (`RegionState:1140-1172`) can move shelter SlugNPCs or living liked lizards into pendingFriendCreatures, drop their stuck-object links and disable their normal saveCreature path. SaveState serializes those under FRIENDS when cleanSpawns allows; LoadGame restores the pending strings. `GrabSavedCreatures:2284-2315` rewrites their location for the new player start, copies original records to spawnedPendingFriendCreatures, clears pendingFriendCreatures and returns rewritten strings. It does not itself instantiate the creatures. The later caller that accepts/rejects those returned strings remains unread here; clearing the queue is not proof all companions appeared.

These paths explain persistence as selective state transfer, not an exact paused world dump. Source capture, semantic reading, a disposable roundtrip, an installed game save and interactive acceptance remain separate. This pass performed capture/reading and artifact integrity checks only.
