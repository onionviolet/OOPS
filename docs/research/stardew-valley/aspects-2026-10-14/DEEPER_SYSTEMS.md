# Three deeper source systems by payoff

## D1: one item with several independent readers

SHOWN: object definition supplies ID/category/base price; held instance supplies stack/quality; sale, gift taste, cooking recipe, bundle predicate and machine trigger read different combinations. A vegetable tag opens generic machine rules while exact bundle ID and quality still matter. Processed flavor retains origin identity for names/tags. This is composition through shared item facts, not proof of one universal action engine.

PROPOSAL SD-P1, owner modular chains/engine: one existing good gets two useful destinations. Quote both with one current stock; each staged host reads the same identity. Validate downstream usefulness and shortage, then save/import the real deltas. Do not clone the donor's whole item catalogue.

## D2: machine admission and custody are separate from clock and transfer

SHOWN: admission checks rule/count/coal, creates held output, saves input snapshot and consumes actual stock. Work time is minute-based or morning-relative. Collection can fail with output retained. Casks change current quality each day and eject current item on a tool strike. Ordinary unfinished destruction drops the machine identity and loses consumed stock.

PROPOSAL SD-P2, owner modular chains/UI: extend current receipt projection first. Existing Village mixing reserves actual inputs and cancels with exact return, so keep that incumbent. If finished-output custody is needed, add one explicit buffer and blocker through its current reducer; define cancellation before admission and prove failure leaves prior output. Do not call an input snapshot owned stock.

## D3: durable knowledge with several acquisition routes

SHOWN: learned recipes are dictionary keys, fed by defaults, levels, TV, mail and purchased recipe items. Current craftability checks actual ingredients and access separately. Cooking can reveal the set as silhouettes; gift profiles instead reveal only known tastes. Acquisition, first useful application, and present usability are different views.

PROPOSAL SD-P3, owner skill mechanisms/skills: add one missing teacher versus manual route to the same usable method. Preserve knowledge if its reference object is lost; show current support blockers from existing technique/lesson facts. Exact friendship-recipe mailing schedule is still unread; no lifetime route cap is proposed.

Priority chosen for the assigned P02/CH/P03 gaps. Other inventoried systems have not become new requirements. No donor runtime or YAIRPG implementation was performed.
