## Register and execute content

`createContentRegistry({ ..., simulation: definitions })` validates immutable definitions. The simulation registry accepts `people`, `commands`, `powers`, `advancements`, `sites`, `events`, `controllers`, `transitions`, `origins`, `conditions`, `encounters`, `energies` and explicit `onEnroll` effects. Native people bind stable NPC registry IDs. New people use a registered simulation template and `spawn` with a unique persistent ID; there is no rerolled cast on reload.

Command requirements use explicit facts with `all`, `any`, `not`, `eq`, `gte` and `lte`. Unknown negated information is not treated as true. `previewSimulationCommand` reads availability/costs without a draw or mutation. The acting and target participants are explicit; `$actor`/`$target` in authored effects resolve to those saved participants.

The effect vocabulary is `spawn`, `fact`, `world`, `resource`, `vital`, `body`, `item`, `transfer`, `custody`, `xp`, `reputation`, `knowledge`, `relationship`, `claim`, `condition`, `life`, `source`, `faculty`, `power`, `progress`, `title`, `equipment`, `unlock`, `event`, `party`, `energy`, `observation`, `site`. The supported operations and validators live in `simulation_contracts.js`; execution is in `simulation_effects.js`. Costs reserve existing negative resources/items/vitals or actual transfers. Output formulas are JSON expressions `{fact, scale, add, min, max}`, resolved and frozen at commitment, never evaluated as code.

`commitSimulationCommand` stages an immediate result, a reserved job or a frozen encounter. A site's capacity is held until settlement/cancellation. Jobs freeze definition revision, costs, selected outcome, effects and participants. Completed unique claims stay settled after display history is pruned. Loan custody distinguishes owner from holder, protects borrowed goods from ordinary consumption/transfer and requires a matching return. Native equipped items are outside carried inventory; simulation gear blocks ordinary transfer/consumption until unequipped.

`setSimulationProgram` reserves only the next batch, with a finite target up to10,000 jobs. Input/access/capacity changes pause the next batch; `resumeSimulationProgram` uses the actual remaining target. Pausing does not cancel already reserved work. Cancellation uses the job's frozen refund/forfeit policy. This limit bounds a single routine request, not skill potential or permanent game progression.

## Distinct power and growth rules

`power_models.js` implements different execution checks rather than a universal learning sequence:

| Model | Execution rule |
|---|---|
| Practice | Authored mastery bands change paid cost or absolute capacity; no universal mastery ceiling |
| Design | Selected functions consume declared capacity, with slots only when that source declares them |
| Investment | Actual invested progress constrains area × intensity; upkeep follows paid scope |
| Authority | Declared custody, jurisdiction and termination must apply to the actual target; it is not converted into a damage multiplier |
| Hybrid | Acquired lineage and declared retained/fused constituents determine eligibility |

Ownership, mastery, fragments, execution count and cooldown are saved separately. `advancePowerProgression` settles costs, an exclusive branch and an enduring advancement receipt atomically. Source lifecycle is separate from remembered procedures; dormant/suppressed faculties do not contribute capabilities. Skill, source and power grades remain authored dimensions, with no global fictional rank conversion.
