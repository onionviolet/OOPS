# Systems front door: one row per in-depth system

**Status: proposal, written 2026-10-30 (item L1 of the [owner docs audit](../audits/OWNER_DOCS_AUDIT_2026-10-30.md)).** Everything here is a proposal (AD32) except the links to existing owners. This file holds no rules and copies no content from the layers it links (one home per fact). It is the place a lane looks first to find every owner of one system.

A system can have up to five layers. A rulebook says how it behaves. A representation says how it is shown. A code map says where to plug in. Palettes hold ideas. An inspector reads it for developers. This index lists, per system, which of those exist and where. If a cell says "none", that layer is a gap (see [Gaps](#gaps)).

Row order follows the three code-map guides: [progression and world state](PROGRESSION_WORLD_STATE.md) (S1-S19), [making, items and economy](MAKING_ITEMS_ECONOMY.md) (MIE, sections 1-12) and [combat, people, sites, UI](COMBAT_PEOPLE_SITES_UI.md) (CPSU, sections 1-4), then systems that only have a representation, then the code clusters that had no owner (audit F4). [SYSTEMS_REGISTER](../SYSTEMS_REGISTER.md) is the older area-to-file list; the guides are its detail.

Defaults for reading it: a cell names the main owner, not every mention. A palette cell lists at most three, the most current first, and a dated palette is a proposal, never authority (default; the dial is that a palette may be cited when a rulebook line links it, the reason is that palettes drift). Maturity is copied from the code map's own word; "no map word" means the guide gives none for that section.
