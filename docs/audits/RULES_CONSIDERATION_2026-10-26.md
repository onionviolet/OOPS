## UI priority: the complaint was saved, but the behavior remains unresolved

The supplied two screenshots corroborate [UI audit round 3, UIS1–UIS14](UI_DESIGN_CORE_AUDIT.md#round-3-2026-10-26-a-stable-screen-item-inspection-hover-and-reports).
That owner already records the same complaint about switching the whole center,
missing hover, empty-slot commands and report presentation. Saving it did not
repair the shell. This pass supplies a proposed append/fold for that owner,
not a competing UI specification. Screenshots are user-supplied observations;
no fresh browser interaction or installed-build identity was obtained.

Target for the eventual changed journey: populated **1920×1080**, actual 14/21px
text; relevant laptop/floor checks 1800×1040 and 1536×864. Visible outcome:
inspect, compare and open commands without losing the current place/work or
making the player rebuild their context. Mobile remains deferred. UI source
paths are shared and dirty; no writer reservation or release is inferred from
an old tooltip-lane message.

**U1 Preserve the task, not just the outer boxes.** A screen can keep exactly
the same rectangles while replacing the list, losing a selected target or
hiding the routine the player was using. Conversely an explicit resize or
Full view may intentionally reflow. The meaningful check is the current task,
subject, selected inputs, work/log access, focus, scroll and return path. This
extends UIS6/14 without a universal one-pixel gate.

**U2 Disclosing commands is not changing task.** More actions currently has an
explicit expansion side effect (`proto23_shell.js:410`). That is stronger
source evidence than `defaultDock:'center'` alone, which only supplies placement.
Plain choose/focus updates eligibility; it does not itself call full expansion.
The CSS has separate selected-item composition rules. A future reproduction
must record ordinary selection, focus, More actions and Full item separately.
Correct UIS1's causal shorthand instead of claiming every selection takes the
same route. Opening the local disclosure should reveal commands in the same
inspection; Full item should be the explicit larger destination.

**U3 One selected subject is not always one physical item.** Current selection
can follow an exact inventory stack or whatever occupies a slot (`:269–278`,
`:398–399`). Taking boots off may leave a valid feet-slot inspector, but “Equipped”
and Take off are wrong for an empty slot. Replacing a slot's occupant must not
silently retarget a pending command. Header should identify either the actual
item or “Feet slot · empty”; useful action is choose fitting held gear, with
absence explained. Automatic selection follows the declared identity contract.

**U4 Hover, pinning and keyboard focus need separate roles.** Source `:197`
suppresses all item hover while a selected inspector is rendered; `:284` also
selects on focusin. A keyboard user tabbing to read can therefore change the
inspected subject. Default proposal: focus/hover offers a public preview,
explicit selection pins, action controls commit. If a pinned box has focus or
an unfinished choice, another hover must not replace that choice. A transient
preview can appear beside it or defer with a clear available route; avoid the
old proposal's “never nothing” turning into a requirement to overlap commands.
Use one bounded preview with Esc, pointer bridge and safe focus return.

UR41/43/51, not a new surface system:
