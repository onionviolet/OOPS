# World authoring and integration audit

2026-10-04. Planning complete; runtime remains held. The useful next step is a small authoring preflight around the existing registries and compilers. It should show which rules have actual consumers, when a package creates state, and what each compiled phase preserves. A new interpreter or a second world engine would add work without resolving the inspected gaps.

The eight prioritized findings are in [FINDINGS.json](FINDINGS.json); five mergeable work bundles and worked recipes are in [DEPENDENCIES](DEPENDENCIES.md). They extend the current plan's mechanic/campaign ledgers instead of duplicating them. The strongest new evidence is the difference between definition acceptance and native binding: `validateItemKey` checks encoded shape, while native publication reconstructs actual items and validates actors/unlocks. Simulation reference checks cover several families, but source/power acquisition still resolves other references during execution. Those runtime guards should remain. Authoring needs earlier diagnostics and a declared native-consumer map, including milestone unlocks and movement endpoints. See AUTH01/AUTH08.

Package activation needs equal attention. `enrollSimulation` scans the composed registry for provisioned people, all sites, automatic events and eligible controllers. That is useful for the current shared services; blindly composing a destination package can change that enrollment surface. Require explicit activation intent for new definitions and report its closure before registration. A package's world label cannot supply independent native state. Keep common enrollment only where deliberately selected. A modest JS package descriptor can name families, required host capabilities, imports/exports, UI routes, versions and source claims. It need not create another inventory, clock, effect vocabulary or mandatory mechanism for every world. See AUTH02/AUTH05.

The existing project and event compilers are worth keeping. `compileSiteProject` emits normal paid commands, claims and completion facts, but omits phase participant/target fields. Its view also uses a field-specific observation namespace. The current single-worker workshop does not prove multiworker construction or reusable project views. `compileSituation` schedules an ambient successor and an offer's expiry successor; a successful response follows only its authored effects. That asymmetry can express a deliberate branch. Show it in generated control flow rather than silently appending a universal next phase. Diagnostics should identify dropped fields, unresolved starts, response/expiry paths and observation bindings, preserving private facts. See AUTH03/AUTH04.

Content compatibility and source correction belong in the same review packet with different outcomes. Commands, events, templates and some policies already freeze commitment data; loaders still require registered IDs, and ongoing controllers use current definitions. A prose correction must not rewrite paid work, ancestry or acquired means. Review correction impact by feature ID, distinguish source evidence from original balance, and require Engine's explicit compatibility decision for persistent meaning or ID changes. Preserve genuinely superior source functions. See AUTH06.

Dynamic actors already have cause-based IDs, frozen templates, role selectors and explicit spawn aliases. Write a concrete recipe around those mechanisms instead of copying a fixed NPC adapter for every helper. Use Frontier's funded helper and paid inspection as first authoring examples; the held Short Measure draft remains useful but has known stock/travel gaps. Book-specific mechanisms still require their reviewed evidence and selected host capability. See AUTH07.

Checks here cover report JSON, local links/anchors, evidence ranges, whitespace, fingerprints and readback. No code, build, game suite, browser, save or benchmark ran. Runtime/token savings are unmeasured. Director review, master integration and later permitted playable checks remain separate gates. [CHECKPOINT](CHECKPOINT.md) records inputs and terminal writer/process state.
