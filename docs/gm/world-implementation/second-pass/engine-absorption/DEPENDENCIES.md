## CDDA patterns without an EOC interpreter

**Route: independently borrow patterns, extend current code only where a consumer is missing.** CDDA exposes dialogue conditions/effects reused by triggers, actor/item talkers and data-authored magic. Its event queues, calendar, map, creatures, components and persistence belong to that game. They are not a JS library that can be dropped into YAIRPG's native command path.

Implement author recipes as current typed conditions/effects with named `actorId`, `targetId`, site and capability dependencies. Keep trigger recurrence as the existing common scheduler and deterministic stable ordering. CDDA's current-turn requeue and deactivation/context behavior are reference semantics, not our selected catch-up policy. Do not port implicit `u_`/`npc_` naming or assume every condition is truly talker-relative: pinned recipe knowledge still consults the global player, while item-count conditions use the bound actor. Use each action's actual knowledge, inventory and receiver.

Magic definitions illustrate separating target, resource, components, failure and effect. Our current `power_models`, energy and source owners still decide acquisition, compatibility and execution. A copied spell JSON or numerical curve is neither source-qualified book canon nor a functioning native consumer. Preserve useful superior effects; don't turn every spell into a damage modifier. For the herb case, existing finite paid jobs suffice; for the roof brace, reach/continuing support needs a real Powers/Combat adapter.

**Dependencies:** EF02/05/08 and AUTH01/02 for selected instance/time/reference consumers; SOC03/WB guarded priority choices for funded NPC alternatives. No mandatory upstream package. **Exit:** ordinary current definitions remain runnable even if the CDDA comparison recipe is removed.

## Inform patterns without its world model

**Route: independently borrow the action recipe.** Map check -> paid candidate carry-out -> durable publication -> observer report onto existing code. Before/after hooks must have declared ownership and receipt semantics if selected; they cannot run arbitrary imperative reward code. Before attempting a command, validate reach, available target, support, ownership, assent and occupancy. Actor request/consent is a real agreement, not prose in the report.

Inform's action result means reaching carry-out; it is not proof that the intended goal succeeded. Preserve a paid failed trial as a distinct supported outcome. Nesting an authored action must not silently advance another clock or pay/reward twice. Prefer one staged command composition with explicit ordering rather than recursive imperative `try` calls. Narration occurs after durable success; a failed write cannot issue a successful repair line.

No generic containment/object-property engine is required for the current native bag, room/site and a few positions. Use the existing physical owners. Inform's implicit taking can mutate possession before a later main-action rejection; that behavior is not selected here. Add material/lot identity or body/source/contact rules only for their named consumers, retaining Items/Micro/Regions/Combat ownership. Inform's turn model and VM save files cannot become YAIRPG's clock or save envelope.

**Dependencies:** same legal-action/native-publication closure as EA-P1; actual source/contact consumer for EA-P4. **Exit:** current definition/command semantics are independent of Inform. No copied Standard Rules or source implementation is proposed.

## Optional Ink/inkjs conversation boundary

**Route: defer adoption now; conditional authoring trial EA-P3.** Existing `pocket_realm_scenes` already provides openings, branching choice-to-command bindings, private/report phases and return rules. Its finite command path is a simpler first route. Ink becomes useful if an actual long scene needs weave/gather/topic/interrupt authoring that these definitions make cumbersome; it still does not solve disputed beliefs, inventory, source/body or contact.

Proposed API sketch: `projectNarrativeContext(episode, observer, canonicalOwners)`, `previewNarrativeChoice(cursor, token, safeContext)` and `planNarrativeChoice(cursor, token, canonicalSequence, context)` in a proposed Engine-owned `src/narrative_adapter.js`. These return typed requests/DTOs, never arbitrary effects or an independent mechanical inventory. A token includes episode/story hash, choice ID, canonical sequence and participants. Recompute legality at commit; do not trust a previously displayed choice.

Suggested saved cursor: optional `state.narrative[episodeId] = {adapterSchema, storyId, storyRevision, compiledSha256, compilerRevision, runtimeRevision, storyFormat, saveFormat, stateJson, boundaryId, lastReceipt}`. Engine decides actual schema placement/validator/migration. The `stateJson` stores story location, visits and prose variables only. It is not authoritative game progress, NPC memory, ownership or obligation. Mechanical truths come from existing command/phase receipts. A recap can be regenerated from those receipts; a missing cursor never auto-enrolls or pays a scene.

Process one user choice in a fresh candidate Story, restore compatible cursor, supply only allowed observer values, select the verified choice, and continue until an explicit mechanical request boundary. External functions must be pure, with unsafe lookahead disabled where the runtime API permits; better emit allowlisted requests for the host. Continuing, reporting or choosing a path cannot mutate live game state, call native grant functions, spend fuel or run asynchronous effects. Staging the resulting legal command and next cursor precedes one existing envelope write; only after it succeeds replace the live Story/state/UI. A duplicate callback cannot replay a receipt. No separate story autosave.

Pin story compiler and runtime with compiled hash and formats. The inspected Ink v1.2.1 and inkjs v2.4.0 sources both declare story format 21/minimum 18 and save format 10/minimum 8, but that alone does not establish semantic compatibility. README's explicit compatibility table stops at Ink1.2.0/inkjs2.3.0. The loader lacks its own maximum future-save/content-hash gate and may approximate moved container paths. Engine must reject an unsupported wrapper/save version, story hash or approximate game-bearing path before any command. Later adoption needs a selected compiler/runtime pair and real feature/save qualification, not a range check. Do not load stale content into a newer runtime and rerun from the start. Compatible prose updates need an explicit boundary mapping; changed choices/path/revision require retained old story, migration or recoverable rejection with canonical game state preserved.

**Optional deps:** pinned inkjs runtime, chosen author-time Ink compiler and compiled story; no remote service, editor or .NET requirement should be imposed without choosing the compiler route. Keep authoring/build artifact separate from browser gameplay and notices. **Fallback/removal:** static current scenes cover all first-pair mechanics. Active adopted cursors must be mapped once to canonical receipt/scene boundaries or retained with the pinned runtime. Removing the library or `.ink` file alone is not save migration; it must not grant new knowledge/rewards.

## Conditional rot.js spatial boundary

**Route: defer package, extend small graphs first.** Existing pursuit routes are directed and have `minutes`; its BFS (`pursuit.js:94-101`) selects the fewest legs, not weighted fastest/safest arrival. If that missing decision is selected, a small weighted directed graph solver belongs to the existing pursuit/Regions route adapter. rot's grid A*/Dijkstra use topology step distance; they do not supply this weighted road objective merely by being pathfinders.

Proposed pure query API `querySpatialSupport({instanceId, geometryRevision, topology, from, target, passability, observer})` returns candidate path/visible cells and blockers. It consumes app-owned instance/body positions and known observations. Canonical action validation still handles actual collision, scope, permission, cargo/body fit and effect reach. FOV means geometric visibility under the chosen cell rule, not hearing, current belief, identification, guard interception or guaranteed damage. Do not use hidden target positions to choose a pursuer's next destination; truthful validator geometry and planning knowledge have separate DTOs. Special guaranteed-location authority retains its exception.

For a selected grid only, compare rot's A*/chosen FOV against a local pure implementation with the same meaningful case. Stable dimensions, topology (4/6/8), coordinate convention, walls/doors, exact effect contact and map revision belong in the consumer contract. Paths are derived; movement spends real time/resources through canonical commands and records actual reached position. No `ROT.Engine`, Scheduler, SpeedScheduler, display loop or global `ROT.RNG` owner. If procedural generation later qualifies, pass canonical saved draws through an explicit approved RNG adapter and persist realized topology once. rot's Uniform/Digger also use wall-clock budgets, and generators import a singleton RNG; cloning or seeding RNG alone does not prove deterministic geometry. Generation remains deferred. Rendering a map never rerolls it.

**Optional dep:** selected rot-js v2.2.1 modules at pinned source/package revision after separate approval. **Fallback/removal:** store app-owned JSON geometry/positions and canonical movement receipts; replace the pure query implementation without changing inventories, time or saved actor identity. Generated worlds retain realized geometry/seed policy. Module/bundle, memory and timing advantages are unmeasured; no performance claim follows from its license or library popularity.

## Gate and order

EA-P1 is the first recommendation and consumes existing integration work. The finite case EA-P2 is optional content. EA-P3 and EA-P4 are conditional, not required dependencies of EA-P1, one another or every future world. Source-bank context is consumed where available, not rebuilt; no full-world bank or whole-book reread blocks the first pair. In all cases, source/definition/link checks, actual runtime implementation, rebuilt behavior and human acceptance retain distinct statuses.
