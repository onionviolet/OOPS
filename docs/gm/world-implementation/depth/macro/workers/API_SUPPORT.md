## Explicit gaps and proposed authoring records

The current primitives are enough to compose small, authored examples by adding native adapters: represent an authored site as a world/site binding; use an actual actor's inventory and a command's item costs for gathering or construction inputs; compile work phases as jobs; settle outputs with existing item/world/relationship/knowledge effects. That composition does not create the missing source-of-truth rules for those domains.

The architecture plan should call these **proposed records/adapters**, not API names: (1) region graph and zone profile with adjacency, layer, terrain, risk, access and encounter bands; (2) resource patch with type, quantity/regrowth/season/harvest conditions and ownership; (3) recipe or production plan separating known design, consumed stock, required tool/facility, labor, duration and output; (4) actor affiliation/relationship/household record plus explicit adult-consent and eligibility rules; (5) body component/organ and source-host compatibility policy, with costs and outcomes explicit; (6) base claim/rights record and construction/maintenance project; (7) timeline branch/loop policy identifying retained carrier state, reset state, knowledge and changed causal history; (8) encounter population/cause budget plus exact fixed-strength actor roles and spatial reach. These are schemas to design, not existing exports.

Examples from the supplemental research index make the boundaries concrete: extinguishing a magical construct versus ordinary burning needs distinct counter functions; a copied competence or blueprint does not create fuel/materials or working stock; a powerful acquired ability may exceed an ordinary path while still requiring a capable host; and changing a past prerequisite must change later event reliability and history. These examples justify explicit function/source/host/stock/knowledge/time ownership, not a universal cap or equal-power rule.

## Ranked staged architecture requirements

1. **Keep ownership and migration additive.** Reuse native actors, inventory/resource owners, shared simulation clock, and world/site/project adapters. Add an optional versioned record family for new local world data; absent records mean legacy behavior. Give each record stable IDs, revision, actual owner bindings, expected revision guards, causal receipts and deterministic settlement. Do not mirror native bags, body or world facts. Define schema migration and unknown-definition behavior before persisted use.
2. **Establish geography, access and time.** Author region/layer/site graph, routes and rights, and distinguish joined clock, local occupied time, subjective effects, and explicit loop/history branch time. Reconcile against the existing clock before jobs, encounters, travel or expiry. Specify offline/absence policy per world; current world instances freeze during absence.
3. **Build resource-to-use and base loops.** Add resource populations and harvest conditions, then connect harvest to owned stock, processing, recipes, projects, facility/tool/labor requirements, maintenance and output. Keep design knowledge distinct from manufactured and equipped objects. Base/farm/workshop/fort/pocket should use the same ownership and project abstractions with local rules and rights.
4. **Model actor functions and social institutions.** Add affiliation and role records, directed tie semantics, legal authority/rights, household/romance only as opt-in authored systems, and body/source-host/organ compatibility only where the world needs it. Native typed effects can settle outcomes; dedicated policy adapters must check consent, identity, control, source requirements, host strain, succession and permission before committing.
5. **Add bounded encounter ecology and chronology.** Author zone-specific populations, strength/reach bands, actor/group roles, terrain/time/resource modifiers, density and cause budgets, scouting/contact/evasion/pursuit/front/aftermath rules. Promote only relevant residents or situations to durable records; aggregate distant ordinary activity. Keep fixed source actors at authored capability. Extend existing transition reset/retain lists with explicit scoped history restore, time-domain and branch/reseed rules; declare retained carriers, reset body/stock/ties, changed causes and reveal timing.

## Acceptance descriptions for a later implementation pass (not run here)

**Positive coverage:** An ordinary durable route finds a known material patch, checks access and a tool, harvests a bounded amount, processes it at an owned or permitted worksite, consumes real stock/time/labor in a project phase, and yields an actual item that can repair a base or trade with a resident. A refusal/delay leaves the player with a useful alternate path; a resident or institution reacts later based on witnessed information and the committed outcome. A separate exceptional function has its own required source, host, reserve, reach and consequence, and can be superior when those conditions hold. Travel updates only occupied local time under its declared policy; a selected loop branch resets only named state and later encounters reflect changed causes. Encounter tests would check local strength bands, role-specific scouting/attack/reach, terrain and visibility, an evasion/contact/pursuit route, finite spawn/cause budgets, and aftermath without scaling fixed source actors.

**Counterexamples to reject:** A material label creates infinite harvest; learning a recipe creates the item; opening a site grants land ownership; generic relationship `trust` silently means romance or consent; a source label is treated as an organ or host effect; a displayed energy reserve passively refills without policy; knowledge survives a loop but the plan silently preserves body, inventory, relationship and permission too; distant NPCs all receive per-tick simulation; encounter range is inferred from player level; absent old-save records are interpreted as zero-owned world data that overwrites native state.

## Compatibility and limits

`world_instances.js` currently defines strict world-instance and binding schema 1, with exact known fact/site keys. `realm_clock_leases.js` has its own schema 1. Simulation supports schemas 1–3, and situation records require schema 3. Generic campaign transitions already support authored reset/retain lists, including named actor domains and optional native patches, but do not define the semantics for scoped restoration of a past world state, separate time domains, carried-state completeness or deterministic branch reseeding. The current `realm_state.js` has a separate realm envelope/prototype owner. New broad systems cannot be silently added to those strict shapes; use a separately versioned optional record family, explicit migration/defaulting and owner bindings. Old saves with the optional family absent should validate and behave as before. Never rewrite user saves during design or migration planning. Save/reload verification remains a later implementation acceptance gate.
