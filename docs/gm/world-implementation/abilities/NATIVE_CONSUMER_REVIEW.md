# Native consumer review: bounded skills expansion

Read-only source review at dirty baseline `97c28efe`; no source edits or runtime checks. Four proposed functions should reuse existing native systems as consumers and use the existing skill XP ledger where that is genuinely the same competence. These names/numbers are proposals, not accepted balance.

## Reusable native records

- **Combat/control:** current native catalogue has `Shield blocking`, `Evasion`, `Defensive measures`, `Tight maneuvers` and combat-weapon skills. `party_battle.js` has a real guarded contest: Lio's `guard` command spends 2 stamina and one `brace_effort`, covers only the next attempted hit on the player, then the same native strike resolves against Lio; current aftermath records guards taken and helper state (`party_battle.js:67-94`, `:45-55`). Extend/use this exact guard action. A skill milestone should alter a real guard choice or resolve a distinct control action, such as a once-per-exchange *intercept* that redirects one hostile strike to a willing guard after checking the same consent, presence, stamina and effort rules. Do not just add block chance or a second renamed guard stat. Existing player block skill is passed to native combat in `native_battle.js` via `readNativeFighter`; the helper's `PARTY_METHOD`/control eligibility is separate and explicitly checked in `party_battle.js:15-26`.
- **Trail reading:** reuse `Perception` for general observation XP, and its real current caller `frontier.inspect` (3 min; anchor notes plus possible Field eye, `expedition_content.js:53-66`). For the distinct pursuit skill, `pursuit.js` already models evidence with location/source/observed/expiry, then investigation, movement, search and resource-funded polling; see definitions/validation `pursuit.js:11-27,41-55`, start `:65-88`, search/step logic `:93-178`. `rival.hide` is a real counter-action spending 2 stamina and 2 minutes (`frontier_campaign.js:35-38`). Have trail-reading produce a player-owned clue/action that changes a later route/search result or yields an additional known lead; do not reveal Mara's private position. `pursuitView` and notice knowledge are the observation surface, with hidden pursuer state withheld (`pursuit.js:188-198`; `simulation_effects.js:60-65`).
- **Timber/material judgment:** reuse native `Woodcutting` + `Gathering mastery` for harvested-wood competence (`skills.js:1940-1963`) and `Woodworking` + `Crafting mastery` for processing logs (`skills.js:2100-2247`, especially `:2238-2247`). Real outcomes exist: `town.timber` consumes two `Rough wood logs` and records shipment (`town_content.js:28-36`); workshop kit production consumes log + coin + a declared focus/drive use and yields one real `Prepared survey kit` (`field_workshop.js:86-89`); campaigns also make rope/rack/batch outputs from logs (`frontier_campaign.js:48-56`). Best distinct function is judgment at an authored material choice: inspect/grade actual supplied timber, then choose a sound/poor cut that changes repair/kit durability or preserves a log. Route quality should be committed to an effect/item/result, not a tooltip-only bonus. XP settlement already accepts `{type:"xp",skill,amount}` and applies through the supplied gameplay adapter (`simulation_effects.js:167`), so existing XP IDs need no extra state owner.
- **Cooperative investigation:** reuse `Perception` as broad sensory training; do not merge social coordination into it. Existing town investigation is a real alternative to material work: `town.scout` compares the road with the clerk's sketch, costs four game minutes, grants six Perception XP, and can be cancelled before choosing timber (`town_content.js:24-36`). The workshop also pays a named pathfinder and lets the player inspect observed project/road facts (`field_workshop.js:78-84`). A new cooperative skill should require/consume an actual participant contribution (NPC attention, their evidence or a paid assignment) and combine it with player evidence to change a frontier case result or available solution. The current `site_projects`/simulation job path can reserve workers and schedule work; avoid granting success merely for having met the NPC.

## Proposed consumer chain and ownership contract

1. Ability authors a finite original skill/effect record and learning source in the owned `src/skill_expansion_content.js`, keeping existing native IDs above as XP training where compatible. The future reservation `src/world_ability_runtime.js` should be used only if a real caller needs its own saved competence; do not duplicate `character` skill XP or technique proficiency.
2. Engine registers definitions/source/unlock triggers and projects discovery into existing skills/technique UI. `Skill` itself stores `skill_id`, level/Xp configuration and `get_stat_modifiers`; its availability only gates XP gain and visibility (`src/models/skill.js:20-62`). Actual XP is applied via `add_xp_to_skill` and native `character` state (`src/main.js:2577-2600`). New records therefore need Engine-owned native registration if they are added to the native `skills` map; Ability's allowed module does not own `src/data/skills.js` or the renderer.
3. Each action gets its training from its own completion/response: guard/control on a guard/intercept actually taken; trail reading on an inspected real clue and useful route/search resolution; material judgment on a completed graded timber decision; cooperation on a completed joint investigation. Route `{type:"xp",skill:"...",amount:n}` through the current simulation effect adapter, or the native `add_xp_to_skill` bridge if calling a legacy native activity. Do not grant on preview/render, enrollment, mere source visibility, or attempted/cancelled work.
4. Engine alone edits callers: `party_battle.js` (guard result/eligibility), `pursuit.js`/`frontier_campaign.js` (clue and route outcome), `town_content.js` or a field work command (graded stock decision), and `site_projects.js`/a new command for paid cooperative evidence. Ability module can declare simulation-native definitions, but it cannot safely alter these native call sites. If caller inputs need a generic skill level query, Engine must freeze an explicit adapter, e.g. a read-only callback in native `context.gameplay` that maps skill ID to the committed actor's level; never import the global `character` singleton in a pure simulation module. Simulation's `type:"xp"` currently settles native XP through `applyGameplayEffect` (`simulation_effects.js:167`), while current facts/effect records have no generic skill-level predicate. Existing capability providers can check specific facts (`expedition_content.js:19-28`) but are not a scalable substitute for live level reads.
5. UI discovery/visibility is Engine-owned. `Skill.getName()` hides records below their visibility threshold or while unavailable (`models/skill.js:141-153`); native renderer adds a skill bar after actual XP crosses threshold (`main.js:2588-2600`). A campaign source/unlock must explicitly gate the content action; hidden skill bars alone do not hide any future simulation command.

## Minimum real milestone

Ship one complete connected example per requested function, not just four catalogue rows: acquired/discovered source → legal practice/XP → an ordinary repeatable or idle route where appropriate → changed native result → readable result/recap → cancellation/blocked reason. At minimum, retain the existing guard's actual target redirection and aftermath, make a witnessed pursuit clue change a viable path while preserving private location, make a timber grade produce distinct durable stock/repair result, and make a paid NPC-supported investigation provide evidence unavailable from solo inspection. Existing stage facts, knowledge, source, resources, item costs and results are simulation-compatible; completion mastery should remain in native `character.skill_xp` unless the skill truly has a distinct saved method/proficiency model. New gameplay remains implemented-unverified until Engine rebuild and its later deferred browser/save/keyboard gates.
