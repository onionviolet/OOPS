# ACS-P03 duty leaf join contract

The leaf adds a reachable optional prebooking after the player hears Hessa's actual terms and sells her the existing two logs, but before Hessa's home authorization or repair starts. It uses exact IDs from `feature_expansion_society.js`: Hessa `feature_society.hessa`, Orr `feature_society.orr`, Vale `feature_society.vale`, repair `feature_society.orr_repair`, teaching `feature_society.orr_teach`, home `feature_society.home`, and bench `feature_society.bench`. Each one-minute choice occupies the player and all three residents at the existing bench, spends one actual player coin, pays Orr the same one-coin lesson fee, transfers Hessa's existing limited home-work claim to Orr, and records three actor-attributed assent statements. Admission checks Hessa's live repair need and actual logs/coins, Orr's own `ordinaryIntent`, actual kit/attention/stamina and active method, Vale's current `willingBounded` and own effort, and both existing site rights. Coins/attention/repairDemand come from `state.actors[actorId].resources`, items from the existing simulation owner, and body/stamina from the existing person owner. No status, relationship or affection value supplies consent.

The three options are repair first, lesson first, or the controller's ordinary order. The optional world fact is `worlds["base.frontier"].facts["feature_society.dutyPreference"]`; missing or `false` means no active preference. A separate additive `feature_society.dutyPrebooked` marker prevents duplicate old offers while leaving their completion IDs untouched. The early path sets the real home authorization, funds Orr's existing one-coin lesson, records the exact three assents and opens the two existing offers; it never marks `authorize_home`, `fund_lesson`, `request_apprentice` or a report command complete. A separate `feature_society.dutyTerminalCommand` marker suppresses only the exact refused/cancelled/stopped selected candidate, preventing an immediate retry after the preference clears.

`joinAgreedDutyDefinitions(existingDefinitions)` appends the five command definitions and decorates only the existing revision-1 `feature_society.orr_controller`. With no preference its original repair priority 2 and teaching priority 1 remain unchanged. A repair-first preference suppresses the teaching candidate; lesson-first suppresses repair. The common controller still previews each action at a free boundary, so the selected action stays pending while its real stock, effort, support, site or consent gate is blocked. The one-minute booking reserves the actual bench site and one player coin. Its completion support requires current intent/need and returns the coin if any of the three participants loses support or assent during that minute.

Join `agreedDutyFacts(state, context)` into the existing `simulationFacts` composition before preview and completion validation. It derives prebooking readiness, support for the exact in-progress meeting, and one-time follow-up eligibility. During `completeJob`, the engine pops the completing job from `simulation.jobs` before checking its `completionRequires`, while its site reservation remains held. For one of the three exact duty-choice IDs only, root must pass the actual popped job in the local completion context as `context.agreedDutyReservation = job` before recomputing `simulationFacts`. `agreedDutyReadiness` accepts that transient binder only if `agreedDutyReservationValid(state, job)` verifies the exact command revision, sequence/id, player actor/target, frozen context, participant list, costs, effects, completion support, cancellation policy, bench site and held site reservation. It ignores only that exact job's participant/site lock; every other reservation still blocks. Do not persist this transient field. The player's one-coin means stay under ordinary native resource preview. Repair/lesson work costs and support remain owned by the existing duty definitions.

On a successful selected repair/lesson, let the original job effects and `actor.completed` bookkeeping finish, release its site reservation/remove the job, then call `agreedDutyCompletionEffects(state, job)`. Apply the returned existing `world` and `knowledge` effects with `job.id`, then run ordinary state/persistence validation before publication. The exact receipt uses its own player knowledge key, independent of bounded relationship-memory eviction.

After cancellation has returned the original reservation and removed that exact job, call `agreedDutyCancellationEffects(state, job)` with the committed `cancel:<sequence>` cause before final validation/publication. In the unsupported-completion branch, after its original refund/cleanup removes the job, call `agreedDutyStoppedEffects(state, job)` with that branch's `unsupported:<sequence>` cause before returning. Call `agreedDutyRefusalEffects(state)` only from a genuine participant refusal branch, with the committed refusal cause. These hooks do nothing unless that exact job/choice is active, and they do not alter duty price, duration, site, worker, escrow, output or accepted-job payload.

Join `validateAgreedDutyState(state)` to the optional society reader and central `persistExpansionPlan` validation path after ordinary completion bookkeeping. It needs no registry or transient binder, so it remains callable during persistence revalidation and is inert for saves without ACS-P03 fields. It verifies the agreement, three same-cause attributed assent receipts, terminal status, exact duty/job, result note, situation and sequence. The terminal receipt contains a typed JSON value with schema, status, selected choice, agreement cause, exact duty command/job and account. The optional follow-up commands require that valid result and a later cause; one accepted follow-up sets the existing Village world fact `feature_society.duty.followupUsed`, reserves no work and assigns no future duty.

`agreedDutyPresentation(state, registry, playerContext)` returns current previews for all five controls. `commitAgreedDutyAction(state, registry, playerContext, commandId, sequence)` commits only those exact definitions through the common simulation path with ordinary costs, participant locks and sequence checks. Mount those controls in the existing Household panel; its `societyDefinitions.commands` loop does not see additions automatically. Apply `agreedDutyFilterSocietyActions(state, rows)` to that panel and `agreedDutySocietyCommandAdmission`/`assertAgreedDutySocietyCommandAdmission` to both preview and dispatch. They block only original `authorize_home`, `fund_lesson` and `request_apprentice` attempts when the early booking marker is present. Do not cancel or rewrite accepted work; later `hear_home`, `hear_lesson`, shelf work and reports remain available. Join `agreedDutyPeopleView(state)` into existing People rows.

This leaf leaves the shared registry, `simulationFacts`, `completeJob`, `cancelSimulationJob`, People/Notebook surfaces, persistence readers and build integration with the current root lease. It adds no scheduler, actor, relationship axis, inventory, item, save schema, publisher, UI mount or domain.
