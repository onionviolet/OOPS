Refinement commands use the separate `cooling_refinement` group and typed `cooling_refinement` action, so generic `reference_gameplay` command projection does not duplicate them. Their durable command IDs remain namespaced under `reference_gameplay`. The source joins needed for a playable build are:

1. Register the five frozen commands in `coolingRefinementDefinitions.commands`; `conditions` is intentionally empty. They use the existing `body.sore_hands` condition, whose `bodyFacts` projection already blocks hand work. No source, power, inventory template, new currency, condition, or mastery rule is added.
2. Merge `coolingRefinementFacts` after the existing `referenceGameplayFacts` projection. It composes `statusCareSupportedBody(state, context)` with existing supported-workshop, current-hands, real native inventory and vital facts. Its calendar input is the already-published `context.remainderLivelihoodClock` (saved Village calendar minute plus played-clock anchor), with `context.nativeCareFrame` as fallback. Preparation uses the player's own active `status.care.focused` condition or the declared 06:00–08:00 window.
3. Route the five new command IDs and typed `{type: 'cooling_refinement', id, sequence}` action through `commitCoolingRefinementCommand`; merge the returned `sections` into the existing feature panel; call `validateCoolingRefinement` from the current expansion/state reader. Add `cooling_refinement` to the normal `cancel` action's accepted group list so the panel's existing cancel-work control can return reserved costs. The panel uses existing feature action and cancel-work shapes, shows the current paid quote and frozen accepted quote, and does not register these controls in generic `reference_gameplay` projection. The adapter reuses `commitSimulationCommand`, which reserves paid costs, freezes outcome weights/one RNG draw in the saved job, and returns reservations with no result on cancellation or lost completion support.
4. Extend only `validateReferenceGameplayWorkshop` in `src/reference_gameplay_host.js` to admit this additive same-condition receipt: `reference_gameplay.steady_hook` knowledge, the same `reference_gameplay.hook_cooled` condition, and its exact five-played-minute expiry. Keep its existing `reference_gameplay.cool_hook` receipt at four minutes and preserve old frozen jobs. The actual combat consumer in `src/feature_expansion_battle.js` already reads the shared condition and does not impose a four-minute limit; the common played-clock boundary already expires it.

The accepted attempt descriptor is frozen as a `fact` effect inside the actual job effects, alongside the simulation job's `roll`, `outcomeId`, costs, duration, command ID and revision. Its serialized schema-1 fields are `result`, `commandId`, `cause`, `acceptedAt`, `acceptedSequence`, `calendarMinute`, `quietWindowOpen`, `quietWindowRemaining`, `prepared`, `preparedByFocus`, `retryCountBefore`, `baseProbability`, `successProbability`, `roll`, and `outcomeId`. Thus completion uses one existing simulation RNG draw. `failedAttempts` is persisted as zero on a first success and advances only with a completed failure; cancellation or lost support records no outcome. Each retry job is validated against this leaf's immutable command map when the registry is absent, including exact reservation costs, accepted time, cause, roll/outcome, participants, support predicate, site reservation and frozen result effects. The optional registry is checked against the same map when supplied. Application and result knowledge must have matching completion receipts; foreign actor copies, automation and parallel pending jobs are rejected. A successful outcome creates one attributed boolean application; use consumes that fact with the actual charged sleeve and stamina. There is no quality bank, source grant, rank increase or second draw.

## Evidence boundary

Existing source facts: the optional workshop already requires actual enrollment, learned cooling, mastery three after three one-coin/one-salt paid trials, an owned charged sleeve, a supported local body and real native inventory; current `cool_hook` applies `reference_gameplay.hook_cooled` to Oren for four played minutes and returns an empty sleeve. The actual hook-control combat rule checks that same field. `world_rhythm.js` computes recurring windows from a saved calendar-minute anchor. `status.care.focused` is an existing 12-minute player condition. `statusCareSupportedBody` composes native body ownership/control/hands and actual alive state; `body.sore_hands` is the existing max-stacking condition read by `bodyFacts` and native hand-work gates. Simulation jobs already freeze one weighted outcome and roll and return reserved costs on cancellation/support loss.

Original reversible proposals in this leaf: optional refinement costs one native cooling-salt packet, two actual stamina and three played minutes; quiet window is 06:00–08:00 local Village game time; quiet-window presence or an active `status.care.focused` condition counts as prepared; ordinary/prepared starting success probability is 0.50/0.70; each completed failure adds 0.05, capped at +0.15; a completed failure applies the existing max-stacking `body.sore_hands` condition for five played minutes. Existing `body.handsTender` work gates then apply. The refinement can only start and complete with actual supported human native body, living state, usable hands, native stock and vitals. Pre-existing palm marks are untouched; active hand soreness blocks starting/completing the job and is not shortened or replaced. Validation scopes the exact five-minute expiry check to a soreness condition whose cause is this leaf's latest failed attempt; it places no new limit on ordinary body soreness. Success earns one reusable-after-consumption steadied-hook application. Applying it costs the same actual charged sleeve and two stamina, returns one actual empty sleeve, and reuses the existing hook-control condition for five played minutes. These values and the added descriptions are original implementation choices, not ACS balance claims or human acceptance.

The probability quote reports the current retry count, quiet-window state, focus preparation, base and final probability. Preparation and odds are sampled at acceptance, are stored with the one roll/outcome, and cannot drift while the three-minute job runs. Current previews disclose only the player's own active condition, actual workshop/method state and current calendar. They do not read hidden NPC facts.
