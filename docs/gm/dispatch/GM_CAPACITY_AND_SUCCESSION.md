## Fresh context is a new task with a checkpoint

The [official glossary](https://learn.chatgpt.com/docs/glossary) defines a thread fork as a branch from stored history. Our native fork_thread tool preserves task history. Use create_thread with a compact self-contained role/checkpoint when fresh context is the objective; do not claim a fork clears context. User explicitly authorizes such successors now, superseding earlier no-new-chat-as-refresh wording for this task. Ordinary automatic compaction/checkpoint recovery still works and need not create a new task.

Before succession, save the current role, exact objective/latest steering, accepted versus provisional choices, input revision/hashes, exclusive writer scope, actual exports, completed/deferred evidence, child IDs/status, pending process/operation IDs and one concrete next action in the role's existing checkpoint. No credentials, personal saves or raw source book text. Preserve qualified-reader/repair state and do not restart useful live children merely to refresh context.

Create the successor only when context pressure, a changed independent lane or an unavailable session makes it useful. Its prompt points to that checkpoint and live owners, states the prior chat ID, and requires a writer handoff before editing. Original role finishes its pending call, records uncertain effects and releases its exclusive reservation. Successor checks actual predecessor/child/file/process state, confirms release and resumes only unfinished work. A potentially active or unknown predecessor keeps its reservation until reconciled; two clones must not write the same scope. Creation receipt alone is not a completed handoff.

Record every successor/child ID, source checkpoint and ownership transfer in the master queue. Tool-unavailable roles prepare the checkpoint/request for the coordinating chat's native tools rather than inventing calls, bypassing thread locks or starting an untracked CLI clone. Do not fork/relaunch a healthy active GM just because successors are permitted. New tasks use configured defaults unless Weibao requests a particular model; existing chats retain their settings.
