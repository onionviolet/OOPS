## Concrete source → state → command → effect → UI chains

D1. **Current Gu novice comparison, source-traced, current journey unverified.** `guAcademyLife` in `world_packs/book_gu_life.js` defines the actual `refine` thirty-minute command: one primeval essence at admission, same Gu participant reserved, completion changes the claim holder, titled carrier custody and `body.controllerId`. Its `cut` command requires controlled living carrier, learned Moonblade and held bamboo, spends one essence and one bamboo, then produces cut bamboo and Woodcutting XP. Preparing petals instead transfers food to its larder; daily simulation checks consume four fresh petals, without paying activation energy. `guCareStatus` reads the same `simulation.people/claims/owners/energies/checks/conditions` and `gameplay.player.inventory`; `validateGuEnvelope` validates identity, calendar and stock/meal conservation. This supports MC90/119/120's distinctions, not a full lead-life adaptation. Exact costs/condition policies are pack-authored proposals, not newly verified canon. Cancellation, stock expiry and same-identity round trip remain required current proof. Keeper `keeperHouseView` uses the incumbent keeper's own diet and nonlethal starvation policy; it must not inherit novice death/use rules.

D2. **Incumbent LOTM lead command chain.** `getPrivateLotmCast` loads validated optional `lotm-cast/cast.json`; `defineCastAbilities` compiles its source-linked encounter moves to native command definitions. Each move writes its own phase, attributed knowledge receipt and only supported physical effects. `castAbilityOffers` calls `quoteCastAbilities` with `previewSimulationCommand`; `createLotmHost`'s lead read branch returns `abilityConflicts` alongside the actual place/local clock. The `act` boundary and native transaction own payment and completion. `commitCastAbility` is a conflict-frame bridge, not an independent saved battle. Unknown-amount effects currently become explicit `owner-needed` facts, which are not physical effects and cannot count as completed mechanics. The UI consumes the host read; no renderer grants an ability. This is H source wiring, U current earned route and physical-completeness proof. [Lead brief](LEAD_WORLD_ENGINE_SLICE_BRIEF.md) selects the bounded route and its remaining qualification.

D3. **Why the probationer bench is not the lead's missing engine.** `lotmBrewCommands` supplies buy/start/collect for a different entry profile. `brewFacts` derives readiness from an owned start note's timestamp and the current played clock; collection allocates the same physical dose, while ingestion is separate. `benchRowCommands` and `benchEnvelope` additionally track held/sold/drunk/made balance. In `createLotmHost`, the `lotmBe` branch returns a resident lead view before the probationer bench projection, and `book_world_lotm_ui.js` hides that bench for residents. These existing commands cannot establish a natural lead acquisition/practice route by reusing their screen. The first implementation must bind the real lead's source scene, authority and means, not enroll the lead as Hale's probationer.
