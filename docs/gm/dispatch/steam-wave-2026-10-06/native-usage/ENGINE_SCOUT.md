# Native-method retort integration scout

**Use two conserved native tray objects with empty/filled variants, the existing simulation job executor, and a generic three-step work-plan cursor.** A batch cannot start unless both actual empty trays are held. Completion returns two filled native objects. Resin collection returns its empty tray plus the existing Set repair resin; residue collection or disposal separately frees the other tray. This gives a genuine receiver-capacity stall before another batch without another inventory, timer, publisher or fictitious tray person.

Five new ordinary native item IDs suffice: Empty retort resin tray, Filled retort resin tray, Empty retort residue tray, Filled retort residue tray, Spent retort residue. A filled resin tray represents exactly one held resin unit; a filled residue tray represents exactly one held coproduct unit. Their static native descriptions disclose that content. Use plain `JSON.stringify({id})` keys, with no custom keyed metadata or renderer reward. The fixed site object/installation receipt is the apparatus owner, and the two native objects are its physically conserved receiver carriers. Require the actual rack/bench rights, not only a historical completion flag.

This bounded model avoids adding a general site fluid inventory. The current `inventory(plan,id)` requires a real `simulation.people[id]` and an actor; `simulation.owners[id]` is also restricted to real simulation-bound people. A fake `resinTray` actor/owner would violate those contracts. The current site capacity limits concurrent reservations, **not stored products**. Receiver capacity must therefore be established by the actual empty/filled native object count, rather than reusing `site.capacity` as a product counter.

Fuel is reserved, unburned stock until this recipe's settlement. `cancellation: 'refund'`, `completionFailure: 'refund'` and `reservationReturns: 1` return the same input/fuel/trays if the accepted preparation is cancelled or unsupported; they create no outputs. This is an explicit original discrete-batch policy. It does not claim Factorio's progressive burner/energy-buffer behavior. Do not choose `forfeit` casually: generic forfeiture would also destroy the reserved tray objects. Progressive fuel burning would require a separately qualified typed partial-consumption state and settlement repair, outside the smallest complete slice.

An immediate once-only installation wrapper is the simplest way to create the receipt coherently after the ordinary staged setup command succeeds, like existing `commitReferenceGameplayCommand` records its opening. Store only `{schema:1, installedAt, installedSequence}` and use fixed IDs from definitions. Verify the corresponding completed installation count is exactly 1, retained reference workshop permission, current retort site owner/player, and definition revisions. The receipt is not a second output inventory.

Native conservation needs a leaf validator called by `validateSaveEnvelope`, not just the ordinary item-key parser. For each tray family, sum Empty + Filled quantities across `save.inventories` including shops, legacy character inventory where present, `player_storage.inventory`, simulation owners, and negative item costs in actual accepted jobs. Each family total must equal 1 after enrollment; before enrollment every new tray/material/retort job/plan/site must be absent. Use the existing saved envelope's container conventions and avoid counting aliases twice. Reject equipped trays, new quality/components variants, unsupported keys/counts, orphan reservations, two contradictory variants and a fabricated installed receipt. Raw residue may exist only with this reader and an actual retained retort production/collection cause; do not infer production from a display fact.

A sold/stored full tray remains a real full object under its current holder and cannot secretly free this player's receiver. The next batch requires the actual Empty pair held by the player. Buying/withdrawing the same objects can restore access; UI should explain that stored/other-held trays are unavailable. Do not duplicate trays on reinstall or return. These ordinary inventory moves use the current native storage/trade owners and stay subject to full-envelope conservation. Do not make the tray objects loaned merely to preserve them; that would incorrectly forbid ordinary collection/transformations.

For unprocessed reservations, cancellation returns both exact Empty trays and input/fuel/effort once. Completed tray variants return with `reservationReturn:true` so the existing acquisition log does not count an old tray as a newly acquired container. Resin and loose residue are real new material acquisitions. Accepted two-output effects remain pinned together; one output cannot publish without the other through the durable envelope. Plain static variants mean no `items.js` custom key preservation is needed.

The finished-state material invariant can use existing actual completed-command counters rather than add saved tray counters. Let `B` be completed batches, `R` completed resin collections, `C` completed loose-residue collections, `D` completed filled-residue disposals and `L` completed loose-residue disposals. Across the native containers plus actual negative accepted-job costs, require `Filled resin = B-R`, `Filled residue = B-C-D`, and `Loose residue = C-L`, each nonnegative; Empty + Filled for each tray family remains exactly 1. These are validator equations over real stock and actual completion receipts. They are not the UI's stock owner. Transfers/storage/shop ownership changes leave the totals unchanged. Do not apply a similar global resin equation: existing sleeve work also produces Set repair resin and the existing kit recipe legitimately spends it.
