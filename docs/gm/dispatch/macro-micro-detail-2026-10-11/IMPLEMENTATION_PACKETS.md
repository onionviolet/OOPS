# Macro/micro implementation routes

Status: planning proposal, source-inspected on 2026-10-11. No runtime assignment,
runtime edits, build, test, browser journey or private save access. These four
packets route MM01–MM10; they do not implement or accept the detail cards.

The finite primary mapping is MM-P1 → MM01/MM05, MM-P2 → MM02/MM03/MM04,
MM-P3 → MM06/MM07, MM-P4 → MM08. MM09 learning/transfer joins P1/P2 and MM10
ending/succession joins P3/P4 conditionally. Those links do not require a universal
teaching, inheritance, economy or absence system before one selected journey.
All numbers and proposed new content remain proposals. Existing numbers below
describe inspected definitions, not source canon or newly accepted balancing.

## MM-P1. An agreed tool job with a real recipient and accountable return

**Leaves and antecedents:** MM01 work/custody, MM05 legitimacy; MM09 only for
the selected teaching response. Refines PLAN-P4, G3-009/013/019, G5-07/08 and
G8 contact/continuing-use concerns. Can start at an existing enrolled location;
PLAN-P2 random initialization is not a prerequisite.

**Finite target:** one local instrument task with three viable methods: own and
operate it, borrow the actual owner's instrument under agreed terms, or pay the
owner to operate theirs. The useful output supports one actual repair or work
decision. Return/refusal and a later recipient response complete the slice.
Institutional recognition records who performed, who supplied and who vouched;
it does not grant all witnesses the operator's understanding. A fee-free favor
can be authored alongside the paid method when that particular person agrees.

**Existing scaffold:** `world_completion_lens_content.js:24–111` defines owned,
loan and owner-operated examinations, actual co-location, room/outdoor variants,
effort, one conserved deposit and local return/refusal. The matching host/facts
modules freeze the exact loan cause. `simulation_effects.js:200–224` admits
`custodyUse` only through the narrow existing lens validator. `realm_cargo.js:171`
has pure permission planning, but `native_realm_traveler.js:8–20` supplies empty
consents and rejects borrowed cargo. These establish a reusable *pattern*, not
generic authorized loan use or export. Do not copy the lens special case to every
tool by asserting it is already generic.

**Functional order:** meet the actual supplier → receive terms → select one
method → refresh current sample/held key/loan cause/body/recipient support →
reserve operator and means → complete or stop → publish measurement/output and
scoped performed/received accounts → offer the resulting useful work → return
the same free instrument/deposit where applicable → recipient responds to the
actual supplied result. The physical output can be useful before formal
recognition; recognition and personal friendship remain separate facts.

**Files and ownership:** selected content owner first audits the existing lens
content/host/facts and `world_completion_learning_*` consumer rather than adding
a second tool system. Shared integrator owns `simulation.js`,
`simulation_effects.js`, definition composition, `main.js`, save validators and
native panels. A new non-lens consumer, if selected, requires a new exact
held-use admission and completion adapter. Proposed new module names must be
reserved at dispatch time; none exist by implication here. Actual counts remain
native bag/equipment or `simulation.owners`; right/loan remains `simulation`
custody/claims; accounts remain `simulation.knowledge[recipient]`.

**Positive cases:** owned work changes the exact sample and supports later work;
borrowed work returns the same key once without acquisition XP; service spends
the operator's own effort and the agreed payer's money; an authorized recipient
can use the result while only its actual operator learns the procedure; ordinary
return works after narrow new-service refusal.

**Counterexamples:** equipped, foreign-held or different-key tool cannot satisfy
the quote; stale sample cannot become a current measurement; absence or withdrawn
support at completion follows disclosed refund/forfeit policy; reserve+cancel
does not duplicate stock/deposit/XP; merely hearing a report does not acquire a
source; another institution's refusal is not propagated by registry membership;
borrowed cargo cannot pass the current conventional doorway.

**Persistence decision:** extend the existing selected meanings additively;
absent enrollment remains absent. Existing exact lens jobs retain their frozen
meaning. If a broader held-use descriptor is necessary, its validator/version
and old-reader rejection policy must be chosen before dispatch. Load, import,
view and retry do not teach, issue recognition, replenish effort or reopen a
settled loan. Same-cause replay is suppressed; a genuinely new repeatable task
has a new cause and its real inputs.

**Future observable gate:** fresh native journey through all three methods,
later useful consumer, withdrawal/cancel/late return and save restoration during
held work. Inspect inventory, payment, actual operator effort, recipient options
and Notebook accounts, not just a completion log.

**Exact open dependencies:**

Borrowed cross-world passage stays excluded unless a real consent UI, directed purpose and return obligation adapter are separately selected. |

## MM-P2. Household repair, material quality and one downstream route

**Leaves and antecedents:** MM02 household care, MM03 repair quality, MM04
ecology/routes; MM09 selected practical transfer. Refines PLAN-P4, G3-005/010/012,
G6-011/016/017/021 and G5-09. Depends on MD1–MD3 only when using P1's instrument
or recognition; owned ordinary material work can proceed independently.

**Finite target:** a household names one concrete need, obtains an actual
repair/service, and changes its ordinary routine. Player learns what quality
means by comparing an observed defect with an actual later use. Offcuts pass
through one drying/fitting route into one supplied repair or survey kit. Waste
handling changes the actual drain/route condition before or after its real event
boundary. A household can prefer a quieter cheap repair, skilled service or a
powerful replacement when these are actually offered. Their responses concern
usefulness, trust and their own commitments rather than a universal demand bar.

**Existing scaffold:** `agreed_duty_facts.js:50–86` requires actual Hessa/Orr/Vale
availability, original agreement, finite household coins/logs and craftsperson
kit; `agreed_duty_host.js:83–114` has actual commit/completion/cancel/stop routes.
`home_furnishing_content.js:67–105` has supplied fixtures, repeated dry batches,
mundane notebook adaptation, fitted stave and sharp-to-dull knife kit work.
`world_completion_materials_host.js:15–61` freezes exact measured strip key,
sample/measurement cause/body and due work. `world_completion_materials_runtime.js`
joins only the actually popped supported job to cover/disposal consequences;
its root-provided `drainEffects` is deliberately narrow. These do not establish
arbitrary durability simulation, demolition, autonomous wages or an industry.

**Functional order:** hear household need from an actual person → inspect current
site/material → agree funding/roles → reserve real participants and supplied
materials → dry/fit/repair → check actual retained quality/sample at completion
→ apply physical result before the relevant weather/route boundary → settle
contract once → have the household change its selected routine → discover the
next useful upkeep/recovery option. Ordinary handling remains useful even with
superior output: matching a fitting, delivering locally, testing safely and
learning the recipient's need are distinct tasks.

**Files and ownership:** content builder samples the cited furnishing/material
and duty families; shared integrator owns the common clock, popped-job hooks,
`simulation_content.js`, main context/dispatch/publication and validators.
Material identity belongs to actual item keys and existing
`world_completion_strip.js` stamps when that precise measurement is selected.
Drain/cover/weather state belongs to existing opted-in lore/crop world facts;
do not mirror it in a household ledger. Finite funding and labor remain each
actor's resources/vitals/inventory and existing agreements. A passive fixture
bonus is allowed by PROJECT.md, but it needs a real projection/consumer and
removal rule; the sampled rack's timed job benefit is not evidence of an
already implemented generic passive bonus.

**Positive cases:** same typed output supplies actual repair; cheaper rack method
converts actual pieces rather than yielding free elapsed-time stock; paid service
spends its real supplier means; household follows only the agreement it accepted;
pre-event blockage changes that event, post-event blockage changes current access
without replaying the storm; MM09's notebook yields a mundane fitting procedure
without importing another world's mana or innate source.

**Counterexamples:** old sample/template-only key fails precision work; missing
room right or changed body stops unsupported work under its terms; dismantled or
unavailable fixture cannot provide its continuing selected function; loaned knife
does not satisfy owned transformation; repeated batch neither repeats first-use
recognition nor refills customer money; expensive/superior repair does not make
the recipient consent automatically; a rumor does not set the current drain.

**Persistence decision:** retain existing old crop/weather policies and accepted
jobs. New selected output stamps and causes remain in their actual item/job/world
owners. Fixture removal/replacement is a proposed extension requiring an exact
state transition; no universal demolition model is assumed. Save validators must
reject unsupported new meanings without deleting dormant state. Save a fixture
job and a repair job mid-reservation; restore held material, actual quality and
funding once. No history is backfilled on load.

**Future observable gate:** native household need → chosen material chain →
useful supplied work → household routine/route result → repeat or maintain.
Include removal/lost access, exact event tie order and save/reload/import. The
claimed macro response must appear as an actual changed offer/action/site path.

**Exact open dependencies:**

| MD5 | Materials/native item owner | Select precise quality meaning and later fitting/repair consumer; reuse stamps or define additive validated variant. Decide salvage/removal outputs only for the selected fixture. |

## MM-P3. Powerful creation and changed body with honest target consequences

**Leaves and antecedents:** MM06 creation/duplication, MM07 body/equipment;
MM10 only for selected ownership/succession aftermath. Refines PLAN-P5/9,
G2-001/003/015/017/029, G5-05/06 and the G5 join's conservation correction.
Requires P1 custody semantics when using another person's held object; requires
P2's quality consumer only if creating its selected repair material. A new start
or arbitrary duplicate world is outside this packet.

**Finite target:** one explicitly authored exceptional function acts on one
ordinary local object class and its real later user; one supported body/equipment
change alters a meaningful verb. Preserve the promised power: if it truly makes
matter for free, its receipt says so and no scarcity debit is invented. A copied
specimen can differ from copying the supplier's claim, loan obligation, memories
or certification. Institutions can assess a safe useful result, decline an
unverified use or accept a new proven method without a global anti-cheat rule.

**Existing scaffold and limit:** `simulation_effects.js:198–225` stages item
creation/transfer/custody and acquisition records; explicit positive `item` effects
can create authored stock, but generic copy semantics and target identity are not
established by that primitive. `backlog_expansion_body.js:90–117` builds trusted
native body/fresh-opening evidence; the finite installed lung and consenting clay
host paths elsewhere in that module demonstrate explicit body/controller/means
handling. `simulation_effects.js:177` sets a body property, while sources/faculties
and conditions have separate consumers. `native_realm_traveler.js:22–49` is a
conventional one-body view, not travel for arbitrary hosts, hives or object minds.
Native care effect readers do not prove a generic physiology adapter.

**Transformation manifest required before code:** exact original/result key or
identity, count, holder/body and owner; target scope; copied material traits vs
omitted private information; source/faculty/function and current support; true
input/cost/repetition policy; included/excluded body/equipment/vitals/condition
domains; custody and external exported links; observer accounts; cause and
ordering. This is a proposed packet contract, not a claimed existing API.

**Functional order:** acquire the real function and understand its selected use
→ choose exact target → refresh target/body/source/ownership context → stage
the promised effect and true costs → apply body/equipment legality and the real
native target result → publish atomically → deliver/test the created item or use
the changed body's verb → permit receiver/witness responses from actual evidence
→ retain, reverse or continue under the selected function's own rules. When
changes invalidate accepted work, stop/refund/forfeit according to that work's
frozen disclosed policy, rather than silently treating an old body as current.

**Files and ownership:** power content owner declares function and causal order;
shared integrator owns actual stock/gameplay/equipment publication, native body
and effect consumers, completion context, schema validation and UI. Reuse existing
backlog body seams only within their qualified scope. Any new creation manifest
validator or body-action adapter is an explicit proposed extension. No powers,
knowledge, stock or rights are granted by rendering a catalogue row. A new body
can retain learned method knowledge while losing its usable faculty; these are
separate owners and player-facing reasons.

**Positive cases:** repeatable free creation executes again with a new legitimate
cause; created material reaches actual repair/use; copying an owned specimen gives
the promised material state without falsely copying its certification; transformed
body uses its actual supported verb; changed equipment actually changes native
fit/action/effect; reversion preserves only the manifest's promised domains.

**Counterexamples:** one committed cause replay does not duplicate stock; rejected
publication creates no half-copy and no half-spend; borrowed original does not
silently cancel lender rights; reports alone cannot operate innate sources;
private NPC knowledge is not copied unless the actual function includes that
domain and qualified recipient; incompatible body cannot continue a hand-bound
job; old equipment stats do not persist after actual removal; a powerful output
does not automatically rewrite every shop, institution or price.

**Persistence decision:** selected creation provenance is optional additive state
in the actual existing item/cause owner, or a narrowly validated new field only
if needed. Frozen manifests survive reload/import without reroll. New body
schema/control mappings need an explicit compatibility decision; no blanket old
save backfill or implicit human conversion. Exported object references and retained
external claims must be declared before any restoration operation. Broader time
rollback, identity duplication and whole-world cloning remain PLAN-P8, not a
shortcut through this packet.

**Future observable gate:** fresh native acquire → create → actual consumer and
repeat; change body/equipment → changed usable verb → interrupt/recover → save/
reload/import. Inspect native bag/gear/vitals/options and receiver account. Pure
executor tests later can support this proof but cannot replace it.

## MM-P4. A return that preserves different clocks, causes and accounts

**Leaves and antecedents:** MM08 absence/return; selected MM10 continuity and
P1/P2 commitments. Refines PLAN-P7 and the ordinary return portion of PLAN-P8,
G4-05/06/07/14, G3-021 and G5-04/10/11. Depends on each selected earlier packet's
exact durable commitments, not every broad world or temporal idea.

**Finite target:** leave one already-supported local world during one explicit
commitment, use its actual selected absence policy, and return to changed or
retained facts. Demonstrate contrasting contexts: unobserved freeze versus a
supported paid Glasshouse observation interval. An independently evolving society
remains a later selected adapter if the source requires it. The player learns
through current inspection, delivered reports and interlocutors, with their gaps
and interpretations retained. An ending can close a contract while people and
owned things continue; succession must explicitly transfer what the previous
holder actually left.

**Existing scaffold:** `world_instances.js:111`, `:271–310` validates/creates the
generic freeze-only clock. `realm_clock_leases.js:122–214` validates exact supported
observation/work intervals and unions them with visits. `realm_state.js:93–136`
supplies actual Glasshouse sync/open/close/boundary integration; its host opens
activity only after actual observation activation. `observation_channels.js:195–313`
has activation/sample/detect/notice/identity/closure and recipient-scoped replay;
a received anonymous trace does not grant verified identity.
`world_completion_materials_runtime.js:15–28` shifts admitted local material-job
due and paused accounting under unsupported body/realm time. Those selected lanes
have different policies; neither generic freeze nor paid viewing is a universal
offscreen rule. Existing jobs on common played time may complete without new
local autonomous decisions when their own support contract permits it.

**Functional order:** review actual outstanding stock/jobs/obligations → close
unsupported observation/travel interactions as required → depart the actual body
and cargo → advance only the declared supported domains on the shared scheduler
→ at each boundary settle current supported completion, lease expiry and reports
in declared order → retain unsupported due/remaining time once → return actual
body/cargo → inspect or hear current accounts → offer recovery, renegotiation or
continuing work from retained consequences. No wall-clock catch-up, absence tax,
automatic punishment or deadline pause is added unless the selected local rule
actually requires it.

**Files and ownership:** temporal integrator owns existing world/realm clock
adapters and shared scheduler/main publication; content owner declares the one
event/contract policy. Existing person inventories/body/vitals, job/loan/claim
and world-instance facts remain their owners. Knowledge owner supplies received
vs performed timestamps and uncertainty; native UI consumes that projection.
World-local autonomous controllers, succession/departure removal or local-clock
jobs need exact new consumers only when selected. A returned player must not see
private stock or an NPC's unspoken plans just because time advanced.

**Positive cases:** body visit plus supported viewing overlap advances local
activity once; exact lease expiry stops new local decisions; unobserved freeze
retains its local state; committed supported common-clock work retains its actual
outcome; return inspection can disagree with an older report without overwriting
its historical basis; obligations persist under their chosen clock; settled
ending retains actual life/stock/rights and permits the selected continuing verb.

**Counterexamples:** save/load/import does not open a viewing lease or rerun jobs;
tab wall-time does not simulate unsupported production; expired observation gives
no fresh sample; absence grants no automatic identity/source disclosure; a lease
plus visit does not double-progress; a returned tool/deposit is not acquired again;
post-event repair does not erase earlier injury/history; inheritance cannot copy
resources into both departed holder and successor; freeze in one world is not
imposed on another source-world calendar.

**Persistence decision:** preserve current instance/visit/clock ledgers and absent
optional namespaces. New policy, local controller or succession descriptors need
additive validation and a selected missing-content suspend/recovery policy;
unsupported build cannot silently migrate a continued life to Frontier. Save
mid-absence, at lease expiry and after return; reload/import must restore exact
remaining time, cause, held commitments and recipient accounts. Restore is not
permission to replenish attention or repeat rewards.

**Future observable gate:** fresh native leave/observe-or-close/advance/return
journeys with exactly disclosed differences, completed/lost-support work,
inspection vs report, repeat return and generated save/reload/import. Measure the
selected finite schedule and receipt workload; the engine's boundary/storage
guards are not a performance acceptance result.

## Order, dispatchability and close gate

1. Freeze MD1/MD3 and selected local context; P1 is the smallest ordinary
   existing-entry journey. Its broader held-use MD2 is conditional, not mandatory
   for the current lens path.
2. Freeze MD4–MD6; P2 can use owned work independently or join P1's demonstrated
   measurement/recognition. Audit before extending already implemented recipes.
3. Freeze MD7–MD9; P3 then consumes selected P1/P2 ownership/material semantics.
   A promised powerful function does not wait for a universal economy/body engine.
4. Freeze MD10–MD12 and selected prior commitments; P4 proves the return joins.
   Stronger PLAN-P8 histories/rewinds remain separately selected work.

One integrator owns shared native/registry/scheduler/save/UI/build writes. Disjoint
definition authors can proceed only after their interfaces are fixed, with exact
file reservations. Each runtime packet ends at a playable checkpoint before the
next gameplay slice. Planning close here means these targets, source limits,
cases, compatibility choices and exact owner dependencies are reviewable; it does
not mean MD1–MD12 are accepted design decisions or that gameplay is complete.

Readback coverage: MM01–MM08 each has a primary packet; MM09 and MM10 have named
conditional routes. Declaration, caller, native model/UI and save layers are
separate. Every new generic loan/body/quality/absence capability above is marked
as proposed or dependent; every future runtime proof remains unrun.
