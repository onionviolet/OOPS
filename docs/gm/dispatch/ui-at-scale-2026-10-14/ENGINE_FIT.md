## F4. Compatibility boundary

**SHOWN C1:** layout version is 1 (`workspace_state.js:2`); docks left/center/right/float (:3); exactly three column weights (:6-8). Keys: `yairpg.workspace.v1.desktop`, `.narrow` (:52), plus `.authoring` (`workspace_layout.js:33, :383`). Narrow breakpoint is 1000 px (:308), so both requested sizes use desktop storage. Fields are ID, dock, order, width/height, collapsed/pinned/hidden, x/y plus mode, columns, density. No preset name or contribution-home/form field is persisted (`workspace_state.js:13-23`). Presets are computed configurations, not saved named workspaces.

**SHOWN C2:** normalization retains only supplied registered IDs and recognized fields/docks. Unknown IDs are discarded; extra fields such as home/form disappear. Late additions receive defaults/anchor handling (`workspace_layout.js:36-42`); existing saved entries win. Unregister normalizes and saves, deleting that ID's placement (:351-355). Therefore removing a pack is not proven to preserve its layout for reinstall. A registry that registers all stable presentation IDs could retain placement while marking them unavailable, provided it does not expose unknown names. Do not export hidden-content truth through new metadata.

**SHOWN C3:** `yairpg.display.v1` stores browser presentation preferences only (`display_settings.js:1-6`), panel keys `panel.<id>.<key>` (:38-45). Its normalizer drops unregistered/unknown setting keys (:48-53). Settings register only after known state (`panel_kit.js:13-15`). On late registration, values can be re-read from browser storage; importing then replacing settings before discovery can lose an unregistered panel's imported values. Test this order in any adapter. Do not put ownership, discovery facts, digest cursor or arbitrary layout data in this key.

**SHOWN C4:** layout export includes colors and display preferences; v1 import explicitly rejects any other version (`workspace_layout.js:57-62`). Reset touches the layout, not gameplay (:56). Colors and crafting placement also have separate browser keys (:81-86). Layout changes must not modify game saves or award anything. Summary/search can derive current known views without a save migration; durable attention acknowledgment/away history needs a separate decision about per-save/profile identity and storage.

**INFERRED default C5:** retain v1 for adapters representable as existing module IDs and three docks. For real fourth-column storage, contribution promotion/home state or new arrangements, introduce a v2 layout reader/migration while keeping a v1 import route and untouched v1 fallback. Map old left/center/right/float and critical states exactly; do not blindly Reset. Preserve authoring independently and dormant placements for temporarily absent contributions. Old code's version check otherwise rejects v2. Display settings can remain v1 with additive, validated, namespaced definitions; replay order and unknown-key preservation need deliberate handling.
