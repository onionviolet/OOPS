## P1. Smallest seam, without a new lens

**Proposal:** Add one `src/information_view.js` module containing a small readable descriptor table, observer resolution and one pure `redactObservation` function. It can be split later if a second consumer makes the separation useful. Initial descriptors: `self.level`, five `self.stat.*` rows, `self.titles.held`, `card.system.points`. Native character, titles and card state remain the truth owners. Do not register unearned title catalogue names: `titles.js:105-110` returns every catalogue row, whereas the current host filters to held rows (`main.js:8380`).

An observer could describe `{id, actorId, scope:'self', precision:'exact', facts:[…]}` inside the existing observers array. Its permitted precision is a capability constrained by the authored fact policy, actual access and discovery, not an import-provided permission to read arbitrary registry keys. The returned projection could be `{factId, kind, value?, range?, asOf?, source?, precision, status}`. Unknown results omit value and undiscovered label together. Presence/category/range would carry only their permitted payload. Labels, tooltips and share summaries would consume that projection instead of reopening the truth reader. Rendering would use text nodes; existing `log_message` ultimately writes HTML (`display.js:1035-1038`), so receipt formatting would escape any dynamic text there.

**Inferred:** The grade ladder is a precision axis, not a replacement for AP depth or epistemic stage. A numeric range for Strength does not authorize reading intent, an unknown name or a future outcome. Sealed IDs would expose only authorized route/status until the discovery owner authorizes the reading. A failed lookup should not produce a hidden-content count. `rules.js` has a mechanical “known” meaning, namely a supplied defined fact (`:24-29`), which is not proof the player knows it.

**Proposal compatibility:** No new top-level save field, no duplicated native values and no expansion/simulation schema change for this seam. New observer descriptors fit C0's JSON array; missing built-in legacy observers can get an effective read-only default at resolution, without mutating the save on render. Older C0 readers accept the JSON but ignore the semantics, so storage compatibility would not prove equivalent behavior. Preserve legacy message-bearing informational cards (`cheat_cards.js:82-87`) rather than silently turning them dormant. Optional per-card version changes are the II9 step, not required to save live numbers. This estimate excludes R1 fixes and future board hooks.

**Proposal:** Redacted share summaries can reuse the same projection. Raw backup/export remains a complete restorable envelope, as the audit F9 describes; routing the actual save through redaction would destroy compatibility. Leak lint should consume descriptor policy to generate expectations, then independently scan rendered DOM/ARIA/tooltips/settings/export-summary text. Calling the redactor inside the lint alone could let the same bug agree with itself.

## P2. Stage 1 and changed facts on the seam

**Source:** `quests.js:267-269` distinguishes absolute skill events from additive counts; `:127-175,287-288` automatically completes story tasks/rewards. `titles.js:7-38,69-77` already expresses counter thresholds; `main.js:7757-7777` supplies real counters. Bestiary counts, not `game_stats.total_kills`, are authoritative (`:7762-7763`). Craft successes and output quantities differ (`main.js:4283,4299-4304`).

**Proposal:** Start with one known native skill milestone and manual claim of one unspendable point, following the audit's narrowed recommendation and S1D palette (`CHEAT_LIBRARY.md:996-1002`). Extend the same descriptors with selected known `self.skill.<id>.level` readers. Eligibility would reuse unlock/visibility and an available ordinary training route, not registry membership (`main.js:3808-3829`). Persist immutable offer baseline, target, offered time, opened/completed/claimed markers and a unique row ID in versioned held-card state. Current have/need remains derived; no second skill XP counter. For already-awake legacy cards, baseline begins at migration/admission, with no invented past level changes. A fixed first row needs no seed.

Opening can compare a recorded awakening baseline with current known skill levels or elapsed played time. It should not count the awakening-causing victory/title as later progress. Exact trigger, unsupported-world counting and inheritance remain proposed choices. A known-skill level is permanent enough to recompute progress; a recipe-specific “make N” task needs a settled recipe success/output event or existing retained receipt, not inventory subtraction. Add generic craft counts before recipe counters if that is the next useful slice.

**Proposal change contract:** An internal packet `{cause, changedIds, at, mode:'live'|'restore'}` can mark a bounded dirty set. Owner mutations mark it; the settlement boundary reads only subscribed descriptors and computes observations/quest transitions. Repeated packets become harmless through lifecycle IDs. Restore reconstructs rows without new completion messages unless an explicit overdue reconciliation policy is selected. This is scoped invalidation plus existing pure readers, not facts emitting events from getters. Reads/hover/focus remain mutation-free. A first bounded implementation may compare the few subscribed values at a settlement hook; the cost can be measured before replacing it with broader owner instrumentation.

Estimated later host work, **separate from P1**: import/setup, settled skill-change marking, end-minute flush, completed travel/clock flush, post-combat-reward flush, craft durable flush and restore reconstruction, plus a shared durable publication binding. Approximately seven to eight main hunks depending on R1's final hook. This is a planning estimate, not a diff. Skill changes inside craft/restore would be queued under their existing transaction scope, not claim immediately from `add_xp_to_skill`.

## P3. Named streams and peek without advance

**Source:** TE2 is correct for its pinned `cc5fa556` build, but current HEAD has `src/seeded_streams.js`. `STREAMS` separates encounter/core combat, loot, market, craft, gather, rewards and local-life events (`:3-4`). Cells have ordinal/salt and a bounded receipt log (`:23-36,59-77`). `unitDecision` is pure and returns a value/receipt (`:46-51`). `drawUnit` advances a cursor; `keyedUnit` still appends a receipt even though it does not advance a cursor (`:70-77`). `streamSeed` calls `ensureStreams`, which initializes missing streams (`:38-40,56-58`), so it is not a strict immutable-view function on an uninitialized state.

**Source:** Native combat now keys decisions by encounter, side, fighter, turn, target and decision (`models/combat.js:61-80`); encounter snapshots retain turns/enemies/loop state (`:65-68`). Craft rollback includes stream state (`main.js:4166`). Import validates stream/encounter linkage (`save_files.js:81-83`). Expansion xorshift still owns `state.rng` (`expansion_engine.js:517-521`); simulation owns independently derived checks and manual-choice seed (`simulation.js:39-40,70,183-187`). Remaining `Math.random` sites include particles/display jitter, background lines and action flavor (`main.js:2530,2605-2629,3521-3523,7634-7641`); combat-math defaults and `misc.js:69` remain fallbacks. These facts do not establish universal deterministic simulation or identical rendered logs.

**Proposal smallest safe design:** A fixed board skips RNG. A variable board could use an existing allowed family such as `deck:system-quests@base.frontier`, keyed by card/board instance and definition revision, on a staged state. Persist the selected row IDs/targets before presentation. No new root or combat cursor is needed. Validate candidate ordering and content revision so the same draw cannot select a different target after an update.

For peek, pass an already-admitted immutable stream snapshot to `unitDecision` with the actual future key, ordinal and salt; do not call draw/keyed/live wrappers or initialize streams in a read path. Sequential peek uses copied current `n + offset`; keyed combat peek needs the exact encounter/turn/decision key. There is no generic “next combat roll” independent of chosen action, target or callback order. A conditional one-decision preview can name its assumptions and horizon without exposing other stream contents. Future precision requires a forecast provider, not permission for the redactor to turn a present value into prophecy. Grade/access, cost and interference still constrain delivery. A cloned speculative resolution, if later needed, belongs to the existing forecast/simulation boundary in F3.

## P4. A second lens that proves reuse

**Proposal preference:** SH4 True Appraisal on the same bounded self-stat fixture is the clearest proof of numeric reuse. It would reuse stable descriptors, observer scope, timestamps/provenance, range formatting, discovery and redaction. Add one observer policy/card definition and a small CH7 hover/focus view, following `PANEL_KIT.md:51-59`; no new native truth, stat store or RNG. A synthetic lower-grade observer can show Strength 4–6 while a higher-grade observer shows the same fixture's exact value 5.2. This demonstrates two observers of one fact; it does not require downgrading the already-exact CH1 self window or inventing unknown NPC stats.

What SH4 adds: narrow per-field precision eligibility and a target identity within allowed scope, plus one real acquisition/discovery route if it becomes playable. Costed actions would run through an existing transaction, not hover. Exactness does not overcome unsupported means, hidden identity or stale input. This is the small new behavior; a universal appraisal contest is deferred.

**Proposal alternative sequencing:** SH3 Freshness Sense may be cheaper for an existing report. Reuse `knowledge.at/cause/basis` (`simulation_effects.js:284`) and explicit world observation stamps (`:231`). Add age formatting and one known-only report adapter, not an “age of all information” index. Distinguish observed time from last world change; a reader cannot infer staleness from hidden changes without a supported freshness capability. No stored value means no honest historical reading after the world changes. SH3 proves provenance reuse more strongly than range reuse; either second slice can stay small without posing an either/or decision to Weibao.

## Result

**Inferred:** YAIRPG can obtain one shared information model by adapting existing owner facts and knowledge into a small observation projection. The largest missing piece is durable transition integration, not another registry, RNG engine, log or save owner. Current named streams reduce the proposed II6 work. Historical knowledge, appraisal depth, panel discovery and sealed routes remain distinct constraints. This report contains considerations only; no implementation or acceptance status changed.
