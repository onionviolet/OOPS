Lane A1: core consolidation plan (docs only)

Read COMMON.md in `docs/gm/dispatch/core-foundations-2026-10-14/` first, then
the scorecard. Own: `docs/gm/dispatch/core-foundations-2026-10-14/a1/`
(`CHECKPOINT.md`, `PLAN.md`, `REPORT.md`).

Goal: a stepwise, low-conflict plan to pay down F2 and F3 without stopping
feature work. Read the live tree to confirm every claim.

1. World registry (M3): list every world-specific import and hardcoded ID in
   `src/simulation.js`, `src/simulation_effects.js` (`simulationFacts`),
   `src/simulation_resolution.js` and the boundary loop, with file:line.
   Design a registration API (facts, gates, boundary skips, controller
   allow-lists, schema steps) and an order to move worlds onto it, one world
   per change, each with a test that proves identical behavior.
2. Migration chain (M4): map how engine schema numbers 5-11 and
   `save_migration.js` / `save_compatibility.js` work today; propose one
   global chain with per-world sub-versions and fixture tests. Name the
   compatibility decision for existing saves.
3. Read APIs (M5): for each duplicate pair in F2 (person, relationships,
   conditions, actions, capabilities, battles), propose one read shape over
   both stores, who calls it first, and whether store unification is ever
   worth it. Rank by worlds unblocked.
4. Ratchets (M2) and monolith seams (M11): propose concrete counters and the
   first three seams to cut out of `main.js` and `display.js`.
5. Cross-check with `docs/worlds/world-core-kit-2026-10-14/W6_ENGINE_TEMPLATE.md`
   if it exists and with `docs/worlds/WORLD_CORE_KIT_2026-10-14.md`.
End PLAN.md with "More to consider" (new angles) and at most five ranked
first changes, each small enough for one worktree.
