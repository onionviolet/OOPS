## Reproduced transport follow-up

This follow-up supersedes the preceding unresolved status. Multiple later normal playtests reproduced the synthetic close error after saving their successful results. Scope remains Node proof plumbing, AR3/AR6/AR9 and AD36; no gameplay, bundle, save format or readiness behavior changes. The observable outcome is normal process exit after a successful proof, with an earlier assertion preserved after teardown. Failure cases are a stalled server close, an underlying close error and an absent browser executable. Desktop native consumers retain their own rebuilt-route gates.

The minimal public `chromium.launchServer`/WS probe showed why owning a BrowserServer in the same process was insufficient: Chrome's native pipe streams closed, but the public ChildProcess emitted neither `exit` nor `close`. Guarded termination left a Windows process with native exit code `0xFFFFFFFF`, while its process handle still returned `WAIT_TIMEOUT`; `Get-Process` omitted that PID although WMI retained the row. Thus neither waiting longer nor destroying the owned stdio alone completed Playwright's cleanup promise. This was observed on Node 22.22.3 and Playwright 1.62.1.

On Windows, the shared launcher now owns a hidden Node helper hosting the public BrowserServer and connects with public `chromium.connect`. Close attempts both client disconnect and graceful server shutdown. After the same five-second grace, the existing exact marker/parent-tree capture and PID/start-time guard stop all captured processes before checking their native termination exit codes against `STILL_ACTIVE`. Only after verified termination does the caller release this helper's public IPC, stderr and process handles. No private Playwright attributes, global process exit, name-based kill or unrelated browser is used. Non-Windows still calls the original `chromium.launch` directly. Unexpected helper exits and underlying close errors remain errors, with multiple failures retained in order.

The helper owns a dedicated temporary root. Normal close removes it. A terminated Chrome can leave its private `lockfile` Windows-locked; this is reported as `OWNED_CHROME_PROFILE_BUSY` with the exact retained directory, separately from transport or assertion failure. Other deletion errors still reject. Removing per-file retry multiplication prevents profile cleanup from holding a finished proof for minutes. Startup failure also waits briefly for the failed helper's natural exit before attempting guarded cleanup.
