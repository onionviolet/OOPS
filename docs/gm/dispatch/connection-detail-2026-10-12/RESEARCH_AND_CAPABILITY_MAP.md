## Tiny original author recipe

This is an original unrun recipe, not a complete installable pack. Take the public
synthetic workshop fixture in `tests/structured_pack_definitions.test.js:6–19` as
shape guidance only. It does not initialize stock. Do not copy a private world or
call a test fixture gameplay proof.

1. Author namespaced schema-2 `connection_demo` world/location, one item
   `connection_demo.brace` and one provision:false simulation-inventory resident
   `connection_demo.recipient`. Add `presentation.people` introduction key and two
   knowledge-gated status rows. Use exact native JSON item keys. Keep current
   compatibility `{legacy:'preserve-dormant',origin:'mandatory'}` and only needed
   admitted capabilities. Bind an owner-approved compatible beginning; have its
   effects introduce the resident and give exactly one actual initial brace to
   its declared owner. Typed beginning body and hashes come from actual host
   registration, not handwaved IDs.
2. Add immediate, once-only inspect command with actorId:'player', declared
   targetId, world/location, coLocated:true, audience:['$actor']. Its knowledge
   effect identifies only the recipient's spoken need, with basis if supported.
   It neither transfers stock nor accepts work.
3. Add explicit transfer command gated by known need and actual held brace,
   using `{type:'transfer',from:'player',to:'connection_demo.recipient',key:
   JSON.stringify({id:'connection_demo.brace'}),count:1}` plus attributed player
   and recipient knowledge. Transfer updates both real inventory owners through
   `simulation_effects.js:255–262`; once prevents repeated promise/reward. A free
   refusal command closes only this offer. No coin or XP reward is necessary.
4. Recipient use is a real missing authored consumer until supplied: a declared
   NPC command consumes its own brace with `{type:'item',actor:
   'connection_demo.recipient',key:...,amount:-1}` and changes one namespaced
   world fixture fact. A later report command, gated by that fixture, tells the
   player what this recipient did. If autonomous use is wanted, define a controller
   and explicitly initialize it. `beginStructuredCampaign:68–72` provisions
   people but does not visibly initialize their controllers; no assumption that
   adding a controller definition alone starts it. The safe first version uses
   explicit native host dispatch for the recipient action, which is itself a
   required adapter: the structured public host only dispatches player actions.
5. Compile against actual registry, stage native objects, merge via actual host;
   begin/action/cancel return plans to the existing publisher. Use the existing
   observer-safe view. Prove actual consumer once native adapter is implemented.

An even smaller already-supported loop can transfer useful stock into the named
resident and hear their acknowledgment, but should claim only delivery, not
installation or autonomous repair. This distinction is the point of the recipe.


## Additional exact dependency: NPC enrollment

`beginStructuredCampaign:68–72` provisions people/owners but has no controller enrollment loop. `spawn` in the effects owner initializes qualified controllers. An author must explicitly choose CD-D1 enrollment or recipient dispatch before claiming autonomous use. Player delivery and received acknowledgment can form a smaller complete supported loop. No new API is inferred from a controller declaration.

## Revised evidence policy

U9: `simulation_effects.js:271–274` replaces a knowledge entry only when the new
stage is equal or higher. A lower-stage doubt cannot overwrite an understood
entry through that primitive. CD-P3 must keep original observation and revised
interpretation as distinct attributed keys/receipts, or reserve a precise selected
knowledge-revision adapter. The historical observation remains available; current
belief must not be inferred from the highest old stage after contradicting evidence.
This is a source constraint, not a claim that characters never change their minds.
