## Future ideaboard and engine direction

The future board should connect **idea -> evidence -> current owner -> proposed experiment -> implementation -> verification**. Research depth, source coverage, design selection, code delivery and playable acceptance remain separate fields. Cards link to these existing documents and source locators rather than duplicating accepted rules or storing recovered proprietary code. Small feasible patches remain visible beside deeper unresolved system questions.

Retain five engine considerations beyond appearance:

1. **Rules and state boundaries.** Commands and eligibility/cost/outcome resolution act on authoritative actor/world/stock/knowledge state. Visual scenes consume projections and report actions; stable content IDs and versioned definitions survive scene unloads. Moving JavaScript rules to another runtime requires an explicit port or bridge, not assumed drop-in reuse.
2. **Time and simulation scope.** Distinguish game time, animation frames, real elapsed time and each region's supported absence policy. Independent tasks reserve actual people/sites/materials. Data/event scheduling for distant actors should not require every person or world to exist as a rendered scene node. Pauses, interruption, background work and catch windows need explicit semantics.
3. **Persistence and transitions.** Save people, property, pending commitments, retained history and causal outcomes independently of graphical nodes. Migration, load validation, durable publication and error recovery remain explicit. Travel, life changes, successors and resets retain their own domains; no renderer chooses an offline-loss or rewind policy.
4. **Authoring and observability.** Content definitions, dialogue/quest/event graphs, conditions, material functions, NPC profiles and dependency inspection need coherent tools. The board/editor should expose why an action is available, what it spends, who owns the output and which later consumer uses it. Store source-era truth, beliefs and original branches separately.
5. **Presentation and spatial rules.** Decide whether a scene only illustrates an existing action or adds reach, distance, obstacles, cover, sight, paths or physical interactions. Keep typography, discovery disclosure, accessibility, asset/style consistency and 2D/3D production effort visible. Check the selected engine/version's desktop/web exports and language integration when a prototype is selected.

Phaser and Godot remain comparison candidates from the earlier discussion, not selected engines. A future Village workshop proof could compare text and visual entry, actual material handoff, independent work, collection, departure and changed return. Its rule/state/time/save/authoring requirements should be observable before a larger port is approved. This note does not start that prototype or alter current gameplay-test deferral.

## Assignment and ownership standard

Future authorized game/DLC assignments should reuse exact existing source pins and read/reviewed coverage, then name a concrete unfinished dependency chain or exception. Preserve decision, prerequisites, expenditure, mutation, downstream consumer, time policy, failure and aftermath, including exceptional or late-game branches. Keep the larger original YAIR implications in the dossier before selecting a few feasible implementation packets. A five-path packet is a bounded completed pass, not an instruction to stop thinking about the source forever.

Completed sources keep their completed scoped status. Do not re-export unchanged binaries, reread every source, relaunch historical leaves or let current implementation wait for blanket audits. No new reading or runtime lane is dispatched here. [RECONCILIATION.json](RECONCILIATION.json) records verified human authority, dossier fingerprints, current routing and validation. The shared runtime/canonical integrator retains its current reservations; this dispatcher writes only this source-research index. ACS chat receipts remain in its [FOLLOWUP_MESSAGES.json](../../../research/amazing-cultivation-simulator/FOLLOWUP_MESSAGES.json).
