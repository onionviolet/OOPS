## One downstream contract, one durable host settlement

PC1-D1, **PROPOSAL / INFERRED:** every **new** refine/assemble/repair/salvage stage should produce an unpublished operation plan and route through the existing host `persistExpansion(plan)` → `persistExpansionPlan`, using `applySimulationEffects`/`applyGameplayEffect` for ordinary deltas and narrow domain adapters for source/product/condition truth. This is a settlement seam, not a new chain-owned save envelope. `src/expansion_persistence.js:7` retains the current envelope, writes expansion/gameplay/ownership/native patches, validates it, then calls storage at `:49`. `src/main.js:985`, `:995`, `:1014` publish only afterward. `src/gameplay_publication.js:18` stages reconstruction/XP before the write. This seam already spans native inventory, XP, NPC stock, sites, energy, equipment and physical world effects.

PC1-D2, **PROPOSAL:** reuse `commitSimulationCommand`/existing jobs for paid staged work (`src/simulation.js:244`, `:305`, `:327`), freezing actual source/input/tool/actor references and declared output/support terms. A cause/expected revision rejects replay or stale admission; source debit, job escrow, work/time, losses, useful output, XP, discovery and saved draw changes settle in the same envelope. A clone helper or key validator alone cannot enforce this. The existing simulation scheduler is the clock owner; no independent setInterval, split save write or post-publication reward callback.

PC1-D3, **PROPOSAL:** retain current native craft/HV1 entry points. For legacy mutations, `beginNativeCraftTransaction` remains the rollback bridge, with explicitly captured owners and markDurable immediately after successful storage, before UI/events. It does not own persistence itself. New staged stages need not mutate live native components first. P2 currently has its own sound stage/validate/write/publish flow (`src/mixture_native.js:42`); joining P2 to an expansion stage requires an explicit mixture nativePatch/validator/publication adapter in the single host commit, not invoking both publishers sequentially. No such generalized adapter is claimed implemented here.

PC1-D4, **PROPOSAL:** extend M1 downstream by changing source meaning, not role count:

| Stage | Source and template meaning | Operation/output/observation constraint |
|---|---|---|
| Refine | Selected actual lot and composition/process law | Account feed, useful fraction, residue/emissions and required heat/charge; separate process outcome from scoped assay. A learned-method refinement is a different law from material refinement. |
| Assemble | Exact component references and declared interface graph | Reserve parts and tools; output references installed parts where gameplay needs them. Returning a carrier does not create a spare; disassembly cannot pay installed and loose parts together. |
| Repair | Same owned/custodied target and repairable defect, plus suitable feedstock | Update selected condition owner or authored variant once; retain object identity where supported; observations report repaired scope, not perfect universal condition. |
| Salvage | Actual object/remaining installed parts, recovery law/tool means | Destroy or debit target, recover supported fractions/parts with explicit loss; transfer identity where conserved. A second legal object permits a new receipt; replay of one object does not. |

PC1-R1: **INFERRED:** a universal batch save added now would duplicate mixture products, native keys, E2 identities and installed world state. Introduce read-only M1 adapters first. Add rich output fields only when a chosen downstream predicate actually reads them. Legacy absent state stays inert; supported old pending jobs keep their old interpreter/result, settled discarded stock never returns, old items acquire no fabricated origin/age. Every persistence extension names migration or retained-version compatibility before exposure.
