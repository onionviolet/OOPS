# Proposed card and persistence format

Proposal v1. [cards.schema.json](cards.schema.json) gives the structural contract; [examples.json](examples.json) contains seven filled cards. These are authored engineering examples derived from WORLD_CARDS.md, not new verified book lore, selected balance or executable content. `origin` records the exact card section and the invented fields. `schemaVersion` versions the interchange format, `revision` versions a definition, and `packRevision`/hash pins the baseline used for a saved instance. Never conflate these with the native or expansion save schema.

## Loading and execution

Public packs: committed JSON plus a JS manifest that imports the JSON and references trusted registered adapter IDs. First implement this as build-time validation/compilation using existing content modules. Static JSON has no functions, arbitrary expressions or save-supplied executable imports. A trusted adapter can calculate stock, prepare native effects or handle a distinct growth family. IDs stay stable; a pack's revision cannot silently reinterpret a frozen job or acquired fuel policy.

Private packs: a proposed gitignored local folder, `private-packs/`, discovered by a local build manifest or supplied through an explicit pack import UI. A browser cannot enumerate an arbitrary local folder. Do not presume a folder on disk is already available to a hosted build. Pack import validates supported adapters, namespace, references and dependency versions before registration. Do not execute downloaded JS as part of importing data. Keep raw source prose and source libraries out of packs and repository output. Pack installation is separate from loading a save.

Manifest contract: `packId`, `packRevision`, `formatVersion`, `visibility`, `dependencies[{packId,versionRange}]`, `adapterRequirements[{id,version}]`, `cardFiles`, `definitionHash`, `migrationIds`. Register in dependency order; reject cycles, duplicate IDs and unknown rule/effect handlers. References in examples to unimplemented adapters are deliberate proposals: structural validity cannot make them playable. Full pack validation must resolve all world/place/deck/project/operation/item references, all typed rule keys and every adapter requirement before marking it available.

Missing pack state remains opaque and dormant, tagged by pack ID/version/hash. Unentered destinations become unavailable without revealing unknown lore. A save whose current location, body, custody or active job requires a missing pack pauses mutation with restore-pack/export choices. An automatic safe return is allowed only if an already-selected contract provides it and all actual domain owners can perform it. Read-only biography may show previously known entries. Independent available work can proceed only when its dependencies are proven disjoint; do not partially tick unavailable world jobs. Reinstalling the same revision resumes without enrollment or reward replay. Incompatible revisions require an explicit migrator or remain dormant.

## Structural and semantic rules

Each card has required `schemaVersion`, `kind`, namespaced `id`, `revision`, `label`, `origin`, `data`. The discriminant chooses a closed payload shape. Text is display/source attribution, never a legality predicate. World cards choose growth families and absence rules; the proposed validator requires one to three signature laws and at least two absences. That is an authoring convention for these drafts, not permission to invalidate historical vanilla saves.

Rule values use a registry of keys and types: for example `concepts.maxTier` integer, `revival.default` boolean, `preparation.staminaExtra` integer, `time.ratio` rational pair. `undefined` means inherit, `false` means explicitly disabled; zero remains zero. Array and numeric modifiers declare `replace`, `add`, `multiply`, `min` or `max`; they cannot rely on incidental object merge. The compiler validates allowed operators and bounded values by key.

An explanation returns `{value, policyId, contributingDefinitionRefs, evidenceRefs}`. Engine truth and the player-facing explanation are different projections. A hidden absence does not reveal its exact rule when a button renders. Known limits can show an in-world explanation; unknown mechanics and registry contents remain undisclosed. The knowledge record keeps learning stage separate from belief status, source/basis, confidence and disproval.

Card declarations cannot claim player ownership or manufacture a consenting teacher. Research inputs bind to actual owners/sites/text/items. Stages compile to shared staged commands/jobs. Failure progression is a capped per-project fact with defined evidence, not a reward for clicking a preview. Partial outputs must point to an executable limited procedure. Selling a blueprint copies or transfers a declared license; it does not move the researcher's comprehension by default.

Faction definitions describe charters; instances separately own members, funds, branches, duties and seats. People refer to existing actor/body/resource owners. A paid follower uses their own condition, capacity and possessions. World-local laws can restrict branch activity without erasing membership. A world will is an actor with declared reach and evidence, not global knowledge by definition.

Event cards compile eligibility/chance/repeat/guarantee fields to existing event checks. The new deck scheduler arbitrates cooldown groups and a disruption budget before occurrence. Save the selected occurrence, check-stream state and next check; rendering the feed never rolls. A successor is an aftermath dependency, not an immediate undisclosed future event. Chance is per eligible attempt at a specified cadence.

## Powers, edges and operation semantics

Additional card families should use the same envelope: `power` has family-local tier/stage, learning/ownership/execution and compatibility adapters; `edge` retains actual connection endpoints, direction, cargo/source requirements plus barrier state; `person` binds authored identity/aptitude/agenda/knowledge to existing simulation owners. They are not included as executable fixtures in v1's seven required example families. Do not force one universal power ladder.

Rules resolve defaults, baseline multiverse modifiers, world, place and owned exceptions for ordinary overrides. A barrier event that overrides a place needs an explicit targeted patch. Conflicting absolutes require a declared collision policy (tier priority, partitioned domains or authored tie result). Unsupported collisions reject enrollment/activation before a guarantee is sold. A clean absolute cheat has no hidden price unless the selected card explicitly says there is one. Harmful cheats need separate truth and discovered symptom records.

Operations need typed restore/retain domains and an anchor reference. `restoreDomains` and `retainDomains` must be disjoint; every affected domain is explicitly handled, rejected or left unchanged. Schema validation alone cannot establish referential closure. Restore body/equipment/stock/custody/job/site/quest dependencies together or deny the operation. Preview the material loss and retention the player can know. Freeze a plan against save sequence, definition revision, anchor revision and history epoch; one durable transaction applies it.

Keep the causal sequence/commit clock monotonic. A rewind changes local historical state under a new epoch with translated deadlines and a selected RNG policy. It is not setting `expansion.clock` backward. `rewardScope` may be campaign, life, branch or loop: reset only the selected receipts. Loop farming is permitted when the card says so, including free loops if selected. Retained goods must be added only after the restored inventory and custody owners reconcile, so carrying an item backward cannot accidentally duplicate it.

The filled operation example is the Crucible's **proposed origin gift**, not a sourced guarantee of how A Novel Concept revival works. Its body-only revival restores a registered living-body template, retains the same world's aftermath, and requires a handler. A separate rewind card would also require bounded world/native snapshots, observer-memory and RNG policy; do not call body revival a rewind.

## Save growth and storage

Current storage is whole-envelope, uncompressed JSON in localStorage; UTF-8 base64 export is a compatibility format, not compression. The current guard counts other origin keys, so active, development and backup saves compete within its conservative 4 MiB budget. Two equally sized ASCII save strings consume approximately four bytes per JSON character combined, before keys and other values. With just active plus backup, each cannot reach the full 4 MiB. The live guard, not an assumed browser quota, decides today's writes.

Proposed save vNext: `nativeCore` retains native ownership, current activity/calendar and options; `core` holds life/actor/current endpoint, commit generation and known indices; `packRefs` pins compatible baselines; `worlds[instanceId]` holds visited-instance deltas; `authority` holds cross-world claims/debt/custody/observers; `history` holds compacted biography; `operations` holds bounded anchors and reward epochs; `dormant` preserves unavailable namespaces. Serialize each domain once. Deltas record changed fields and tombstones against the pinned definition, not against whatever content ships next week. Unvisited worlds need no mutable save record.

Compact read models by year using the existing biography pattern. Authority compaction requires proofs: retain active obligations and referenced causes, collapse settled repetitive counters only when all consumers accept that summary, and keep singular claims plus operation reward receipts. Keep essential birth/death/lineage/major vows in dedicated bounded identity records; biography highlights currently choose the first four strings, not “all important events.” Pruning ordinary history cannot remove obligations or amnesia-resistant mechanical skill. No exact complete millennial transcript fits a bounded browser save.

Use IndexedDB for asynchronously stored core/world/snapshot records after the publisher is changed to await transaction completion. Keep generation manifests and referenced records in one database transaction; retain one previous valid generation until the new one can be loaded. Never publish native changes on individual request success before transaction success. No atomic transaction spans localStorage and IndexedDB; the database generation is authoritative and any small localStorage locator is advisory. [IndexedDB transaction model](https://w3c.github.io/IndexedDB/) supports this boundary.

A versioned gzip codec is suitable for compact blobs and portable export; feature-detect [CompressionStream](https://developer.mozilla.org/en-US/docs/Web/API/CompressionStream) and retain a raw codec fallback. Record codec, uncompressed byte length, schema and checksum, with bounded decompression/import size. No compression ratio was measured here. Binary storage avoids base64 expansion; if compressed data is kept in localStorage, base64 plus UTF-16 increases cost and does not solve synchronous publication.

Quota depends on browser and origin; persistence requests are not a backup. Use estimates, handle failed writes, preserve the last valid generation and keep portable export available. [MDN storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) documents quota failures and eviction; no fixed IndexedDB capacity is promised.

Proposed planning budget, **not measured performance**: core/native <=512 KiB raw, authority/knowledge <=512 KiB, 20 visited instances at <=64 KiB each, history <=256 KiB, two anchors at <=512 KiB each totals about3.5 MiB raw before manifests. Twenty is a sizing scenario, not a world cap. Retaining a prior generation needs additional capacity. Measure actual native saves and worst-case deltas with generated fixtures before selecting limits; fail or require export at a chosen bound rather than truncate authority.
