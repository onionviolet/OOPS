# How cheat acquisition and creation become gameplay

2026-10-13. Weibao asks how to implement the preceding directions: RNG, scripted content, grind, and deeper possibilities.

Status: source-informed implementation proposal. No runtime edits, selected feature, build or browser verification. Continues the [five-lane synthesis](README.md). [USER_VISION](../../USER_VISION.md), [accepted rules](../../RULES_FROM_SCRATCH.md), [library](../../CHEAT_LIBRARY.md) and [cosmology](../../CHEAT_COSMOLOGY.md) remain owners. World-local absolutes, freely carried or granted powers, instant creation and unchecked lives remain possible; this proposal does not mandate balance, difficulty or a universal progression ladder.

## D1. Assign different jobs to authored content, rules, RNG and work

| Mechanism | What it determines | What it should not silently determine |
|---|---|---|
| Authored premise | What exists, meaningful methods, source/AU differences, special events | A predetermined outcome regardless of the player's actual actions |
| Simulation rules | Eligibility, compatibility, resources, custody, consequences | Universal moral judgment or automatic compensating punishment |
| RNG | Selected unknowns: opportunity, variant, quality, event or experimental outcome | New truths every time the same object is inspected or the save reloads |
| Timed work | Study, fabrication, practice, search and other supported processes | An automatic solution to every novel unknown |
| Player choice | Goal, method, source, recipient, deployment and disclosure | Control the selected premise does not actually give this character |

The recommendation is a hybrid. An authored research method can execute through simulated requirements and timed work, with a seeded chance of an unexpected property. Once the player understands a repeatable method, its ordinary output can be deterministic. Pure story events, pure random draws and immediate power grants remain valid when that is their actual premise.

## D2. Author a project graph, not one universal progress bar

A project contains distinct states: lead known, evidence obtained, method understood, prototype available, working function, preservation arranged, recipient designated, delivered and activated. The states need not be linear. A found working artifact can skip invention; a borrowed laboratory can allow testing before ownership; teaching can deliver a method before the founder dies.

Each selected step declares its action, known requirements, optional costs, duration, outcome semantics, knowledge revealed and useful effect. The UI shows the currently meaningful steps. Hidden future steps stay behind the appropriate discovery route. A named state is an implementation proposal, not a new mandatory schema.

A completed fabrication job should produce its defined output. A completed experiment may instead produce evidence. Acquiring ownership should not automatically grant expertise. Successful local use does not establish survival through death or compatibility with another universe.

## D3. Four research modes can coexist

| Mode | Actual implementation | What makes it enjoyable |
|---|---|---|
| Learn a known method | Obtain instruction, meet requirements, queue learning/practice | Reliable progress and specialization |
| Discover an authored rule | Choose experiments; compare reproducible observations | Deduction without repeated blind failure |
| Generate a new variant | Select permitted functions/components; validate a combination; resolve optional seeded variation | Authorship and surprising usable results |
| Pursue open-ended invention | Search or invest in an eligible authored possibility space | Long projects, collaboration and discovery |

For a first implementation, research should operate over a finite declared possibility space. Broad themes can be numerous, but unsupported free text must not masquerade as an executable new rule. A later natural-language designer could propose a definition; the engine would still need to validate and persist actual supported effects. Writing “a system that creates anything” is not implementing that system.

Experiments can reveal component dependencies, target restrictions or a mistaken hypothesis. Useful negative evidence changes future choices. A recipe hidden from the player can already be defined, or it can be sampled once into a world instance and then discovered. In both cases repeated identical tests should observe the same settled rule unless the experiment itself has declared noise or variable conditions.

## D4. RNG needs a sampling moment and scope

| Unknown | Suggested resolution | Retention |
|---|---|---|
| Existence of an opportunity | World/start generation or a declared event occurrence | Keep that world's actual state |
| Artifact identity and hidden mechanism | Creation, placement or first committed generation | Preserve the generated instance |
| Experimental noise | Per paid/committed experiment when relevant | Retain the observation and applicable conditions |
| Craft quality | Defined craft resolution | Keep quality on the resulting object |
| Evolution branch | Defined milestone or deliberate selection | Preserve the chosen branch and derivation |
| Future recipient/destination | The transition's declared commitment point | Preserve the pending and resolved transition |

Current action commitment chooses an outcome and freezes its effects in a pending job. That is a useful seam, not a rule that every future event must be sampled at commitment. A process whose outcome truly depends on later intervention needs a separate supported resolution design. Do not recompute frozen jobs from later conditions, and do not claim a fixed job reacts to those conditions.

Separate streams or stable keys are worth considering for unrelated generation so cosmetic or unrelated actions do not accidentally change an artifact's identity. Current engine action draws advance a shared RNG; a generalized independent-stream generator is not established by this note. Seed, table revision and resulting instance serve different purposes. The saved result remains authoritative after a table update.

Chance can be modified only by a relevant declared influence. Training may improve precision, samples may improve inference, and a luck cheat may alter a roll. If a deterministic or absolute variant is selected, it should actually skip the unnecessary lottery.

## D5. Grind should have a function

Repeated activity can build mastery, gather inputs, improve tools, survey unknown territory or run production. It becomes empty when it asks for repetitions without changing a decision, function or useful outcome.

Recommended default: repeat routine work through queues or bounded batches; stop for genuinely new evidence, a design choice, missing supplies or a milestone. Let improved skill alter something tangible such as time, precision, output, permissible targets or new uses. A long ordinary route can coexist with teaching, purchase, collaboration or a different functionally similar source where authored.

Audit clarification: new evidence does not require a pause for every observation. A selected queue policy can accumulate routine results and stop only for a material discovery, unapproved method/resource change or player-defined condition. Long production, collection and mastery loops can themselves be the chosen pleasure; novelty at every batch is not mandatory. Distinguish duration, randomness and interaction burden when evaluating grind. See [gameplay audit F3–F5](audit/01_GAMEPLAY_AND_PROGRESSION.md#f3-every-new-observation-should-not-become-a-queue-interruption).

Do not require every breakthrough to be an active minigame. A supported research process can progress while queued; a sustained condition can teach adaptation; a workshop can finish established work. Offline progression is separate from played-time idling and requires its actual clock policy. A progress bar continuing after a life ends requires a surviving operator, self-operating source or explicitly permitted process.

Repeated independent 1% attempts have about a 63.4% chance of at least one success after 100 attempts, not a guarantee. If dependable eventual acquisition is desired, implement an actual deterministic route, accumulated evidence or explicit pity rule. Do not describe a random tail as certainty. Hidden pity also changes the actual distribution and should be recorded as part of the selected mode.

## D6. Original worked project: a future-life research capsule

This is one possible project, not a mandatory start.

| Step | Authored content | Rule/work component | Optional randomness |
|---|---|---|---|
| Choose purpose | Preserve one learned procedure for a later holder | Player selects a procedure they actually know | None needed |
| Find a method | Teacher, document, existing device or research lead | Access and comprehension requirements | Which lead appears in this life |
| Prototype | Supported recording function | Materials and fabrication, if this form requires them | Quality or a compatible secondary trait |
| Test now | Another supported user tries the recorded procedure | Real useful result; record what the test establishes | Noise only if the test has uncertainty |
| Improve | Add durability, translation, identity recognition or capacity | Actual available functions and chosen development | Optional evolution possibilities |
| Arrange continuity | Cache, entrust, inherit, carry in soul or deliver across a defined edge | Preservation and recipient policy | Destination only where the premise makes it uncertain |
| Later activation | The recipient obtains and uses the capsule | Custody, recognition and a supported useful task | None if delivery and activation are deterministic |

A perfect creator can instead make a finished capsule immediately. An ordinary scholar can leave only a useful manual. A source-grounded world may permit inheritance while leaving soul transfer unavailable. An AU can explicitly change that rule. These forms need different implementation, not different flavor on the same bar.

## D7. Deeper joins

| Code | Join | Implementation consequence |
|---|---|---|
| J1 | Reproducibility | Decide whether the result is an individual anomaly, repeatable recipe or freely teachable procedure. This changes later production and institutions. |
| J2 | Shared research | Contributions and ownership differ. One actor can hold materials while another supplies expertise; support only declared participant roles first. |
| J3 | Changed conditions | Some jobs freeze their inputs; others allow interruption or redesign. Define which applies rather than retroactively changing every pending result. |
| J4 | Abandoned work | Preserve useful notes/prototypes and actual missing steps. A later actor can resume without inventing knowledge or replaying already completed work. |
| J5 | Authoring a system | UI, rules, energy, rewards, information access and enforcement are separate functions. A quest panel does not create its own reward supply unless the power grants that. |
| J6 | Self-improving cheats | A cheat can research or produce modifications under an authored policy. Record authority, stopping points and actual results; generic autonomy is future work. |
| J7 | New AU laws | Adapt eligibility, effects, growth and delivery, not just names. Separate mutable instances and pin definition versions. |
| J8 | Counterfactual testing | A simulator tests its actual model, not automatically reality. Real experiments can corroborate or correct it. Perfect prediction remains possible when explicitly granted. |
| J9 | Discovery versus unlock | A phenomenon can exist before the character knows it. A library reveal, legal access, ownership and actual execution are separate transitions. |
| J10 | Infinite or absolute effects | Use explicit semantic authority and supported operations rather than numeric overflow. Technical execution limits need not become fictional costs. |

## D8. Existing seams and missing work

* `src/power_models.js`: practice, design, investment, authority and hybrid previews offer bounded calculation/validation seams. Selecting designed functions is not arbitrary generation of new executable cheats.

Suggested build order: one authored project with reliable useful output; add one meaningful seeded variant; exercise a selected delivery route; then expand reusable project patterns. RNG cannot substitute for missing effects or content. A broad generated library, dynamic definitions, natural-language invention, general multiversal delivery and unattended research agents remain future capabilities.

For a selected implementation, record the active writer, target desktop/laptop viewport and exact visible outcome. Require source checks for commitments, interruption, repeated settlement, RNG retention and actual useful output; rebuild and play from a fresh origin, then save/reload/export/literal import and verify compatibility. Include a failed-save case where inputs/rewards are involved. This documentation pass ran none of those gameplay gates.

## D9. A script is an executable causal claim

For each step, specify inputs, participants, authoritative state, the sampling moment, clock behavior, outputs and what observers learn. Narrative text describes those results. It cannot substitute for them: “the capsule remembers you” needs a recognition rule; “your system rewards effort” needs a defined eligible event and reward-producing effect.

An authored event may be deterministic, conditional or random. A simulation step may use the same content as a scripted scene. The useful division is not scripted versus emergent: it is which truths are authored, which decisions belong to the player, and which consequences the runtime computes. Emergence occurs when supported rules interact, not merely when a prose generator invents a result.

At completion, generate separate result and observation projections. The engine can know an experiment changed a hidden variable while the character observes only a faint response. Later experiments can improve confidence. Saving the event must preserve both the actual result and the knowledge actually acquired.
