## What exists already, and what it does not prove

**F1, shared infrastructure exists.** `simulation_contracts.js` has actor knowledge,
faculties, powers, progression, conditions, claims and jobs; `simulation_effects.js`
projects these to action facts and applies their typed effects. `power_models.js`
has practice/design/investment/authority/hybrid calculations. These can support
qualified local rules. They do not define every world's acquisition, energy,
advancement or exceptions. Do not invent a universal numeric rank conversion.

**F2, source-analysis code is not native world behavior.** Current HP roster data
explicitly has `nativeBinding:false`, no actual existing consumers in that profile,
and an unactivated household/nursery/tool/registry join. The recognition module's
native-mode checks for MoL, LOTM, COI and Shadow Slave return no grants/commits and
`nativeWorldActivated:false`. This says nothing against MoL's separate actual
visitor implementation. Likewise, the original Frontier reference desk reads a
bounded LOTM-inspired institutional comparison; it does not instantiate Backlund.

**F3, ordinary native examples already show useful seams.** The existing paid
datum lesson in `world_completion_learning_content.js` separates teacher source,
learner procedure, material, bodily support and actual product. MoL has an actual
supported-device path. Paradise has actual carrier/mission/clock joins. Use these
as code patterns, with their original-world boundaries, rather than saying all
teaching, carrier handling or material work needs building from scratch.

**F4, supplied-book analysis is broader than activation.** The situated profiles
for ORV, Worm, Legendary Mechanic and Labyrinth explicitly name absent native
instances/actors/effect owners in their respective paths. They are useful qualified
inputs to later world work, not four playable destinations. No global full-book
completion count was recomputed here.

## Resolve straightforward design now

**D1, feature-first admission:** a feature brief names the local rule, its source
qualification, actual state owner/producer, executing consumer, useful consequence,
refusal/recovery and evidence. An objective is optional as the test setting, not
the required unit of design. A lore paragraph or a new resource name is insufficient.

**D2, keep existing authorities:** generic knowledge/source/progression/condition/
inventory/job/claim/instance owners remain authoritative. Use namespaced local
rules and narrowly typed handlers only where existing semantics are insufficient.
No duplicate purse, calendar, relationship store, reward ledger or universal magic
compiler follows. No new subsystem merely because a world uses unfamiliar words.

**D3, distinguish four paths:** source/content completion, native binding,
semantic handler, and behavioral proof are different work. For N add the actual
native join, not more profile prose. For C author the missing consumer. For H first
validate the narrow local invariant. For P exercise existing behavior before adding
code. S requires the exact selected claim, not rereading every book by default.

**D4, make growth useful:** acquired progress must change available execution or
another real opportunity. Generic XP, social approval, skill knowledge, source
eligibility and bodily conditioning cannot substitute for each other. Compare
later consumers without requiring equal rewards, forced combat or a mandatory
objective chain. Strong acquired ability may solve an older problem outright.

**D5, preserve history and disclosure:** selected edition/profile/era and committed
branch facts survive relevant restore/import. A relationship AU changes actual
people's histories/rights where authorized; it cannot merely rename them or mint
affection. Unknown rule, hidden Flaw and future plot do not become tooltips. Expose
known eligibility/cost/reason using existing UI homes; future UI claims need rebuilt
populated 1366×768 desktop evidence. Mobile remains deferred.

D1–D5 are resolved authoring constraints/recommendations derived from standing
direction, not five newly accepted runtime systems.

## Recommended implementation order, not a new dispatch

1. **A1:** Bind one source-qualified book profile to actual bodies, places,
   inventory and at least one executable local rule. The later
   [REC1 comparison](HP_LOTM_NEXT_PLAYABLE_FEATURE_2026-10-15.md) recommends early
   LOTM acquisition/control/use; HP remains a later qualified candidate. Select
   actual runtime scope with its live owner, not by profile count. Original HP
   ordinary-life content remains possible without claiming its spell gap closed.
2. **A2:** Connect learning/acquisition to an actual method and later reuse, using
   existing teacher/source patterns. This addresses BF1/BF3/BF6 instead of adding
   another detached progress bar.
3. **A3:** Add the selected world's semantic seam only: e.g. one qualified digestion
   condition, imposed restriction, or trait-settlement rule. Prove its negative
   case before broadening to the whole power system. These are alternatives.
4. **A4:** Exercise native lifecycle and discoverability for that feature, including
   real inputs, interrupted commitments and relevant save/reload/import. Source
   assertions cannot substitute for this. Finish the playable feature first.
5. **A5:** Extend to the next feature/world from its owner. TTKS B2/B3 settlement,
   large sleep/trial systems and general parallel actors have larger semantics;
   keep their plans, without making them prerequisites for ordinary book play.

The order selects a sensible workflow, not a new book roster or a requirement to
finish every shared framework before shipping. Other source-qualified situated
books remain worthwhile later candidates: Legendary Mechanic needs actual owned
prototype/signal/material consumers; Worm needs a source/target/effect binding;
ORV needs scenario/recipient/stock/contract settlement; Labyrinth needs actual
class/source/party/guide means. These module-declared gaps do not supersede the
existing source-priority order. FMA/Frieren remain useful later comparisons; this
request does not move them ahead of the book priorities.

### ACCOUNT FOR NOW: BF28, author a life through rules and consumers

A **life profile** is proposed authoring data describing a situated person and
their opportunities. It is not a second actor model, a permanent class or an
implemented pack-schema field. One actor may hold several memberships, earn
income in several ways and change circumstances without becoming a new person.
Titles, demonstrated competence, formal rights, perceived identity and actual
faculty remain distinct. A source can grant a real class power; that grant needs
its own qualified mechanism rather than arising from a job label.

| BF28 facet | What the selected profile must specify | Existing owner / failure to avoid |
| --- | --- | --- |
| a. Source and scope | Work/edition, claim locators, era/place, ordinary population versus exceptional holder, canon/authored/generated status | WA3/WA8/WA10; unknown law is not forbidden action or automatic canon |
| b. Situated start | Body/age, learned methods, belongings, custody, housing, debts/agreements, actual local contacts and known facts | S02/S04/S05; `start_records.js` composes starter fields but does not itself instantiate every obligation, person or faculty |
| c. Time and routine | Class/shift/travel windows, deadlines, preparation, chosen idle plan, stop/absence policy | Existing world/job clocks; do not add a timer per career or silently spend unused offline time |
| d. Access and enforcement | Physical reach, institutional policy, authorization, practical bypass, detector, witness and response as separate questions | AD38/ECR/PIR/SR; breaking a regulation is not physical impossibility or automatic discovery |
| e. Production and livelihood | Who supplies inputs, who owns output, who pays, ongoing demand and useful noncash results | Existing stock/custody/transactions; wages need work and a payer, not a profession label |
| f. Learning and growth | Specific practice, instruction, experiments, bodily support, acquired source, progression conditions and a later useful effect | SLR/MR/WA4; attendance, credential, mastery and supernatural advancement need distinct readers |
| g. Knowledge and identity | What this person starts knowing, learns on the job, may report or conceal, and what each observer believes | Existing knowledge/relationships; the player remembering a novel does not inform every inhabitant |
| h. Failure and transitions | Cancellation, missed work, lost tool, injury, debt/dispute, change of role, recovery and retained means | Existing jobs/conditions/life owners; leaving school need not erase learned methods or silently settle a loan |

| j. Proof | Positive case, changed circumstance/refusal, later useful consumer, pending/final round trip and visible controls | S14/AD36; a selected slice needs its own rebuilt desktop evidence, not proof of every proposed profession |

**How to encode one rule:** record `operation + world/instance/era + supporting
source facts + actual prerequisites + input reservations + completion effects +
effect owner + knowledge recipients + interruption policy + later reader +
counterexample`. This is a design worksheet, not loadable JSON. Keep physical
law, institutional policy, learned technique and character choice distinguishable.
Default: evaluate the actual mechanism; dial its local conditions/costs; reason:
the same act can be physically possible, institutionally prohibited and unknown
to the authorities at the same time.

Current implementation fit matters. `simulation_contracts.js` already owns
people, custody, knowledge, faculties, powers, conditions, jobs and other typed
state. `world_pack_manifest.js` accepts defined record families, not arbitrary
life-profile keys. `rule_modules.js` currently admits the `village.mix@2`
resolver and a narrow fact/target vocabulary; it is **not** a ready interpreter
for every admission rule, spell, smuggling inspection or timeline reset. Express
supported work through existing commands/effects/facts. For unsupported semantics,
name and implement the smallest actual domain/resolver seam, register its consumers
and save behavior, then author the content. Renaming predicates or adding prose
does not create a working handler.

**Worked contrast, authored HP-like supply operation, not a canon claim:**
a student requests a supervised practice allocation; its actual keeper checks
current terms, stock and availability. A licensed supplier transports a sold
lot under a real agreement. A smuggler can physically carry the same lot where
their body/container/route allow it; the local policy can prohibit it, while a
present inspector needs actual means to discover it. Completed delivery changes
custody once and creates payment only under a supported buyer's agreement. A
borrowed school item remains its owner's property. The operation does not award
casting mastery, institutional permission or supernatural progression merely
because the actor selected one of these life labels.

### BF85: representing many specialties reasonably

**Proposed model:** professions are social/economic circumstances; specialties
are meaningful differences in how a person performs particular work. Both can
overlap. The same sealing knowledge may help a brewer, preservation worker or
courier, while the local physical law, apparatus and purpose decide the actual
effect. Category resemblance is a search hint; compatibility comes from the
mechanisms and evidence. No closed list of careers or allowed outcomes follows.

Author a supported operation along these axes rather than one bespoke system
per profession. This is an authoring vocabulary, not nine new saved meters:

| Facet | Examples | What it actually changes |
| --- | --- | --- |
| Work/verb | transport, inspect, heat, mend, teach, negotiate | Existing transaction/effect or a named missing resolver |
| Method/technique | maintain alignment, control a heat ramp, sample without damage | Procedure, prerequisites, stages and measurable outcome |
| Subject/material | living seedling, brittle glass, loaded ward, person's claim | Actual properties/source support; tags locate candidates without supplying physics |
| Tool/facility | insulated box, jig, licensed archive, calibrated detector | Real capability, custody, availability and sometimes access |
| Circumstance | moving cart, damp room, rushed deadline, public lesson | Supported conditions, attention, uncertainty and witnesses |
| Purpose/specification | keep viable, hide identity, meet a tolerance, preserve evidence | A later consumer's actual acceptance criteria, not a universal success score |
| Learned means | held method, bodily control, apparatus familiarity, partner's contribution | Actual supported execution and learning route; not job-title bonuses |
| Rights/agreements | school allocation, commissioned work, illicit transport | Institutional terms, payment and evidence-driven responses, separate from physical effect |
| World/local law | particular source, conversion, restriction, grant or clock | World-domain semantics with source qualification and local exceptions |

The engine need not persist the Cartesian product. Default: keep broad learned
means in their current owner, pin a niche variant/familiarity only when a
meaningful observed distinction affects a real consumer, and derive current
performance from actual context. Dial granularity by the world's mechanisms and
player decisions; reason: differences should repay the memory, authoring and UI
cost. No universal learning-transfer percentage, quality scalar or fixed
specialty ceiling follows. Several weaker methods, better preparation, a tool or
a collaborator may supply the same needed function through different mechanisms.

**Scale through reusable resolution plus authored exceptions.** A transport
operation, a fragile-object property contract and a source-qualified preservation
method can support many cargo niches. A new kind of cargo using the same contract
is content. A cargo whose actual physics requires a different law needs a handler
or an explicit authored operation. A named unique power can stay bespoke; do not
flatten it to force a generic template. Two different uses test a shared seam,
not a requirement to invent an abstraction before the first useful slice.

**Open-ended does not mean already implemented.** If an idea can be resolved by
supported mechanisms, compose them even when nobody authored that profession.
If the necessary mechanism has no executing consumer, record it as
implementation-unavailable, distinct from unknown-to-character or impossible by
world law. The authoring workflow then qualifies the claim or labels an original
mechanism, adds the smallest operation, and saves its discovery/exception under
stable IDs. A proposed action, model-generated story or successful name match
does not bypass stock, timing, cause, source or custody. This preserves room for
new possibilities without falsely claiming the engine simulates all physics.

### BF87: finite authoring and implementation loop for an open design space

1. **Describe the actual difference.** Name the intended effect and what could
   change it: method, subject, tool, context, purpose, right or local law.
   Recover existing content/source owners before adding a niche or new skill.
2. **Resolve with actual mechanisms.** Use current verbs, capabilities, custody,
   material and knowledge facts. Extend a resolver only for a demonstrated
   missing semantic operation, not because a new profession has a new name.
3. **Connect one useful result.** A product, finding, taught method or service
   needs a later reader with actual means/demand. Record source/inference/original
   status and the exact supported envelope, including exceptions.
4. **Prove variation at the boundary.** Compare the ordinary case, a meaningful
   niche/context change and one incompatible or unsupported case; check actual
   inputs, completion and relevant current-state round trips. Test shared
   contracts and demonstrated failure combinations instead of every possible tuple.
5. **Promote reusable detail after evidence.** A second different consumer can
   justify a shared authoring adapter. Generate unnamed detail lazily inside
   qualified mechanisms, freeze encountered facts and preserve the remaining
   unimplemented design space in the owner.

Technical work budgets limit computation per frame/pass, not what a player may
reasonably attempt. Long work retains pending state under the incumbent owner.
Keep the whole-world catalogue broad while each engineering slice ends in a
playable checkpoint. Optional drafting/local AI can propose content from admitted
facts; it is not required for core play and does not adjudicate transactions or
invent canon at runtime. No new local-model run is launched by this round.
